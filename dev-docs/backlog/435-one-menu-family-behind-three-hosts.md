# Row 435: One menu-family implementation behind three hosts

## Item

DropdownMenu, ContextMenu and Menubar should behave the same wherever APG says they do (item selection, focus, close-on-select, submenus), but their item code is copied per host and has drifted: a plain item's `value` has three types, selection is committed on `onclick` in one and on `pointerup` in another, and typeahead text differs. Construction, in this order: (1) one shared submenu for Dropdown and Context; (2) one value type, one selection model (`SelectOn::Click | SelectOn::PressRelease`) and one typeahead rule behind a three-host parity spec; (3) one `MenuPanel` / `MenuItem` / `MenuSub` family that reads a small `MenuHostContext`, each host keeping only its trigger, root and positioning. A fix to an item then lands once.

## Detail

Source: [final sweep note, P10](../research/final-sweep-2026-10-25.md); state re-measured 2026-10-31 on `248f35cb` after rows 477-479 (PR #156). The riskiest item: it needs the cross-component spec run on a release build, not a code read.

- **Sizes (2026-10-31):** `primitives/src/dropdown_menu.rs` 2,371 lines, `context_menu.rs` 2,358, `menubar.rs` 1,569; the shared files are `menu_root.rs` 173, `menu_item.rs` 914 and `menu_sub.rs` 441. Dropdown and context share about 504 normalised lines (host name normalised); dropdown and menubar about 202.
- **Already shared:** `menu_root.rs`, `menu_item.rs` (checkable, separator, group, shortcut) and `menu_sub.rs` for the three hosts (row 53; `menu_root.rs:1-60` records the keep-separate decision), placement (`top_layer::use_anchor_position_fallback`; `use_point_anchor_placement` for ContextMenu), top-layer sync (`use_popover_sync`) and `use_outside_dismiss` (`lib.rs:391`).
- **Value types (verified):** dropdown `ReadSignal<T>` (generic `DropdownMenuItem<T>`), context `ReadSignal<String>`, menubar a plain `String` cloned per closure.
- **Selection:** `DropdownMenuItem` selects on `onclick` and does not clear the focus collection. `ContextMenuItem` and the Menubar item record `pointerdown` and commit on `pointerup` (the long-press guard) and call `clear_focus()` before `set_open(false)`. Whether the missing `clear_focus` in Dropdown is a bug is inferred, not tested.
- **Typeahead:** Dropdown uses `selection::option_text_value(&value, text_value, "DropdownMenuItem")`; Context and Menubar use `text_value.unwrap_or(value)`.
- **Per-host copies:** each host has its own `*_checkable_item` (about 90-110 lines each). The Dropdown and Context submenu code is near-identical: `SubTrigger` 52/53 lines, `SubContentRendered` web arm 59/61 and `Sub` 25/26 normalised lines, about 140 identical logic lines (about 450 raw), doubled on the native arm.
- **Step 1, the submenu (S-M, lands first):** merge the identical Dropdown/Context submenu lines into one shared submenu in `menu_sub.rs` that both hosts call; Menubar joins when its differences are named. It does not depend on the value-type or selection work, and it is the cheapest cut of the duplication.
- **Step 2, one model (M):** one value type, `SelectOn::Click | SelectOn::PressRelease` as an explicit per-host choice (touch and the long-press guard decide it), one typeahead rule, one `clear_focus` rule; the three `*_checkable_item` copies collapse into the one in `menu_item.rs`. Lands behind the three-host parity spec of the Gate below, written first.
- **Step 3, the family (M-L):** one `MenuPanel` / `MenuItem` / `MenuSub` family reading a `MenuHostContext`; each host keeps its trigger, root and positioning.
- **Subsumes:** the three `value` types, the two selection models, the typeahead rule, the checkable-item copies, and the web/native arm duplication of the shared parts. **Does not subsume:** `Navbar` and `NavigationMenu` (row 53 scoped them out; measured overlap 24-29%), positioning (`top_layer` keeps one call per host), the host triggers, and Escape, outside dismiss and focus return, which row 487 unifies across every overlay (menu hosts included).
- **Reverses row 53.** Row 53 decided not to build one shared menu component. The owner approved this proposal on 2026-10-25 ("All ten"), so that keep-separate decision is reversed.
- **Independent of** [row 477](./477-anchored-overlays-placed-in-document-coordinates.md) (the placement call per host is unchanged). The Base UI defaults of [row 478](./478-overlay-defaults-to-base-ui.md) (checkable items keep the menu open) have landed in `menu_item.rs`, so the shared item already carries them.
- **Gate:** one parity spec iterating the three hosts (click, keyboard and touch-tap selection; close-on-select; typeahead on a valued item; checkable items). A line-overlap check is not worth a gate.

- **As built (lane `menu-family-435`, 2026-10-31).** Line counts, all lines: hosts `dropdown_menu.rs` 2,371 -> 1,275, `context_menu.rs` 2,358 -> 1,181, `menubar.rs` 1,569 -> 1,235 (the rest of each is the doc comments and the doc-test examples of its public components); shared `menu_root.rs` 173 -> 313, `menu_item.rs` 914 -> 1,339 (350 of them unit tests), `menu_sub.rs` 441 -> 688. Code lines (no comments, no blanks): hosts 2,738 -> 1,236, shared 730 -> 1,344, total 3,468 -> 2,580.
- **The family.** `menu_root::MenuHost` is the host context the shared parts read (open, disabled, the collection items register in, direction, the open-submenu count, `SelectOn`, `close`, `blur`); each host provides one from its root (`MenubarMenu` for each menu). `menu_item::render_menu_item` is the one item (plain, submenu, checkbox, radio), `menu_sub::{render_sub, render_sub_trigger, render_sub_content}` the one submenu, `menu_root::use_menu_panel` the one panel (role, state, accessible name, popover promotion and placement as one attribute list; one component per host for the web and native arms, the web-only calls behind `cfg`), `menu_root::nav_key` the one arrow / Home / End / typeahead rule. A host keeps its trigger, root keys, placement and its `use_outside_dismiss` / `use_refocus_on_close_unless` call sites (row 487's).
- **Decisions.** (1) `SelectOn` has three variants, not two: `Click` (Dropdown), `PressRelease` (Context) and `PressStart` (Menubar). The Menubar item does not record `pointerdown` and commit on `pointerup`; it commits on `pointerdown` itself (measured), because it closes and hands focus back to the trigger inside that press (row 140); the row text above said otherwise. Moving the Menubar to `PressRelease` (so a touch scroll that starts on an item stops selecting it) is a behaviour change left for its own row ([row 489](./489-menubar-items-select-on-pointerdown-touch-scroll.md)). (2) One `clear_focus` rule: a selection clears its submenu's focus (if any) and calls the host's `close`, which clears the root collection and closes; Dropdown gained the `clear_focus` it lacked. (3) One typeahead label: `selection::option_text_value` for every item (the `String` instance is what Context and Menubar computed before). (4) One value type: `menu_item::MenuItemProps<T>`; `ContextMenuItemProps`, `ContextMenuSubItemProps` and `MenubarItemProps` are `MenuItemProps<String>`, and `MenubarItemProps::value` is a `ReadSignal<String>` (a plain `String` call site compiles unchanged). Every public component and prop name is kept; the props structs of the item, sub, sub-trigger and sub-content are type aliases of the shared ones, the way the checkable props already were. (5) An item resolves its collection from where it is rendered (inside a `*SubContent` it registers in the submenu), so `*SubItem` is the plain item under another name. (6) The Props reference tables of the three docs pages had lost the moved structs, because `preview/build.rs` `props_sources` scanned only `<name>.rs`. Fixed in lane `menu-props-fix` (2026-10-31): a menu host's table also reads `menu_item.rs`, `menu_sub.rs` and `menu_root.rs` (structs only, not their private helpers), and a struct a host exports under a `pub type` alias carries those alias names ("Also exported as").
- **Intentional differences kept** (each one asserted in the parity spec's "differences" blocks): the selection commit moment above; ContextMenu's point anchor, long press, `tabindex="-1"` trigger and scroll lock; the Menubar's trigger row (ArrowLeft/ArrowRight, Home and End on an open menu move between menus, hover switches menus, no submenus); the DropdownMenu trigger toggle with ArrowDown/ArrowUp on the closed trigger.
- **Small behaviour changes.** While a ContextMenu panel is closing, ArrowDown, Home and End no longer move its focus (the arrow, Home, End and typeahead keys share one `open()` guard). An item shows `data-highlighted` only while its menu is open (the Menubar's rule, now everywhere). An open submenu of a DropdownMenu sets `pointer-events: auto` inline, as ContextMenu's always did (the Dropdown stylesheet never sets `none`, so nothing changes visibly).
- **Row 479 piece.** `CONTEXT_MENU_SCROLL_BLOCK_JS` (the second wheel/touchmove blocker beside `ScrollLockGuard`) is gone with the Context panel's two arms becoming one: `check-js-volume` drops `context_menu.rs` from its baseline (js_lit 10 -> 0, install 2 -> 0). `oracle/tier3-radix/scroll-lock.spec.ts` is its proof.
- **Proof.** Debug SSG build of the lane: `test:changed` over `725cfcbd..HEAD` (44 specs, 906 tests) 897 passed, 8 skipped, 1 red, the parity spec's ContextMenu checkbox test (a click on a disabled item while another item held keyboard focus closed the menu: the press focused the disabled item and the blur of the focused one cleared the roving focus; inferred from the original code, which also returned before `prevent_default` for a disabled item, not run on a baseline build).
