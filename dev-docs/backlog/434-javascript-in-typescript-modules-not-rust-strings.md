# Row 434: Cut JavaScript to what Rust cannot do

## Item

The owner's principle (2026-10-25): the point of Dioxus is to drive the UI from Rust/wasm, so JavaScript is the exception, not the default. The library has no `web-sys` dependency; every browser API Dioxus does not wrap goes through `document::eval`, the one route that works on web, desktop and mobile. 72 files carry eval. The owner chose **Rust first** over "Rust plus web-sys" (one code path per feature, every renderer) and over the original TypeScript move.

1. **Audit** every eval block and classify it: (a) Dioxus already has it in Rust (`MountedData::get_client_rect`, `scroll_to`, `set_focus`, event data, signals, `onvisible`/`onresize` where they exist), so move it; (b) Dioxus has no Rust API (`showPopover`/`showModal`, `matchMedia`, pointer capture, listener options such as passive/capture, `scrollend`, `getAnimations`), so it stays JS; (c) must run before wasm (`PREPAINT_JS`, the modality writer), so it stays JS; (d) JS on purpose for latency (one-frame measure-and-place in the anchor engine, scroll bridge, virtual find), so it stays only with a measured reason.
2. **Move** every (a) block to Rust, per cluster, with the components' specs on a release build as the proof (timing-sensitive paths compare long tasks before and after).
3. **What stays** (b, c, d) moves into typed `primitives/src/ts/` modules through the existing bundle chain (the original P9 construction), and the copies become one file.

## Step 3 design: one small generic JS bridge (owner 2026-10-26)

Superseded where it differs by "Step 3 adopted" below (the rule that the bridge cannot carry in-event decisions became the deadline-indexed placement rule and the named-behaviour registry).

The owner asked for a uniform small JS glue layer to Rust instead of many bespoke scripts, which is also how Dioxus frames `document::eval` interop. So step 3 is no longer "every remaining block becomes a TypeScript module". Instead:

- **Lane 3.0 builds the bridge.** One small typed module (`primitives/src/ts/bridge.ts`, through the existing bundle chain) with generic verbs only and no component logic. It covers listen, call, get, observe and match:
  - `listen(target, type, options, fields)`: window, document or element; `capture`, `passive` and `once`; it streams the named event fields to Rust over the eval channel and grows out of `js_listener.rs`'s `listen`, which already owns removal.
  - `call(el, method, args)`: `showPopover`, `hidePopover`, `showModal`, `close`, `setPointerCapture`, `focus({preventScroll})`, `scrollIntoView(opts)`, `setSelectionRange`.
  - `get(el, props)`: computed style values, `offset*`, `activeElement`, `visualViewport`.
  - `observe(el, kind)`: ResizeObserver, IntersectionObserver (with rootMargin and threshold), MutationObserver.
  - `matchMedia(query)`: a subscription.
  On the Rust side these are typed hooks and extension traits (`use_window_listener`, `el.show_popover()`, `use_media_query`), so the logic of every (b) block moves into Rust.
- **What the bridge cannot carry stays as named JS modules, each with a measured reason.** Bridge messages reach Rust asynchronously, so two kinds of work can't go through it. The first is a decision that must happen inside the listener call, such as a conditional `preventDefault` (wheel band, drag, Escape inside nested layers, OTP filtering). The second is read-then-write in one frame (anchor placement, the virtual scroll bridge unless 2D shows otherwise, carousel drag and wheel). Those become TypeScript modules as originally planned. The audit's (d) rows say which apply.
- **Expected effect:** class (b), about 25% of the JS, becomes Rust plus generic verbs. Class (d) shrinks to the parts that are genuinely synchronous. Class (c), pre-wasm, stays as is. Lane 3.0 is sized again once the bridge exists, and the per-cluster lanes then remove blocks against it.
- **Gate:** besides `check-js-in-rust.sh`, any new `eval` must use a bridge verb, or be a named module listed with its (c) or (d) reason.

## Step 3 adopted: a deadline-indexed placement rule, named behaviours, hardened gates (owner 2026-10-26, after five adversarial boards)

The owner asked whether the "synchronous" residue could be bridged too. Analysis: [`../research/sync-js-root-2026-10-26.md`](../research/sync-js-root-2026-10-26.md) (the plan, amended after five boards) and [`../research/sync-js-residue-2026-10-26.md`](../research/sync-js-residue-2026-10-26.md) (W8, C5, C1). The owner chose **Adopt**. This section is the current plan; the agent-facing form is [`../js-interop.md`](../js-interop.md). **Root:** the browser takes its irreversible decisions at fixed points (end of dispatch, gesture start, input routing, paint, compositor frame), so only code on the page's thread with data already there can affect them. Rule: never ask Rust at commit time; Rust publishes beforehand and the page decides locally. Dioxus element handlers are synchronous on web and on desktop/mobile only for `prevent_default` (133 Rust calls rely on it); everything else a Rust handler does, and the bridge, is async. **Every desktop claim is "web-verified; desktop inferred"** until a `desktop-pass/<tree>.pass` stamp exists (row 442).

- **The placement rule: classify each decision by its deadline, then by its kind.** The table (root doc section 2.2):

  | deadline (what a late answer costs) | placement |
  |---|---|
  | this event's default action (cancel or not) | an rsx handler if Dioxus delivers the event, every field the decision reads (`ToggleData` is empty, so `ontoggle` decisions do not qualify) and the serialized event stays small (a payload event such as `submit`, `input` or `paste` can silently lose its cancel on Android, where it travels in a header of about 12-16 KB); otherwise a named behaviour |
  | this event's task (pointer capture, focus routing for the next input) | a named behaviour's effect; never an async verb, never rsx `set_focus` on desktop; arrow-key focus is `aria-activedescendant` first, else one `roving` behaviour |
  | before paint (a same-frame layout write) | A where the platform does it (per-feature floors and a boot probe); a named behaviour where A does not cover every state (`stickToEnd`, on every engine); G only for one-shot placement where an invisible pending state is acceptable |
  | next frame (drag tracking, momentum) | bridge stream plus Rust under the order contract, and a latency budget the owner sets once from one real desktop latency distribution (rows 442/443); a named behaviour only if a measured verdict with the reason `lag` or `order` says so |
  | none | R: Rust over the bridge |

  **Four rules (rounds 4 and 5, root doc section 2.2):** (1) **the order contract**, one rule for commands, behaviours, reports and streams: on desktop a bridge fact and a Dioxus event are unordered and so are facts of two sessions (the scheduler runs scopes by height, `dioxus-core-0.7.9/src/scheduler.rs:106-110, 149-163, 247-258`), so there is **one epoch rule, two carriers and one inbound pump**: a Rust write to a slot the page also writes carries `based_on` (the last page epoch Rust has seen, epochs keyed by slot id) and the slot's owner applies it iff `based_on >= last_page_transition`; **a page transition that an rsx decision reads reaches Rust on the vdom's own ordered path, the transition port** (Dioxus events carry no epoch), while bridge facts carry the epoch of the slot they observed; every page-to-Rust fact goes through **one inbound pump**; the vdom is a writer of native slots too, so `value`, `checked`, `selected`, `hidden=until-found` and `<details open>` join the reconciled kinds; `MountedData` writes are an owner bypass and go through the focus owner and `scrollOwner`; "commutative" means an absolute set on a slot only Rust writes; (2) a decision includes computing its inputs and its later outputs are decisions of their own, Rust by default for a gesture's per-move output (the closure rule, C4); (3) roving focus is `aria-activedescendant` where the pattern allows, else one `roving` behaviour (only on a red witness); (4) Android payload events are not rsx-cancel candidates. L20's one-off carousel focus is the closed `focus_prevent_scroll` call, which lane 3.CA adds with its grant and a reasoned caller list.

  **Kinds:** a *listener* reacts to events; a *command* mirrors Rust state into the page (Rust publishes a `data-dx-*` attribute carrying `(scope, state, based_on)`; one **executor** applies it: popover open, modal open, `indeterminate`, `defaultChecked` and, after round 5, `value`, `checked`, `selected`, `hidden=until-found` and `<details open>`, the **reconciled kinds**; only browser-initiated changes are reported back; it removes the lost-command class, the stale toggle echo of row 115 and the two-writer `<dialog open>` trap); a one-shot call (focus a cell) is a bridge call, not a command. **Admission (rounds 4 and 5) is derived from the placement table, per effect, with two grounds, never a declaration:** the **counterfactual witness red**, or, **only where no probe in the available engines can observe the commit point**, a **cited platform rule row** (a W citation, the engine, a desktop-pass or manual check line and an owner-approved grant row at the merge base; browser-chrome defaults such as F6 and Ctrl/Cmd+B, and engine rules such as WebKit's clipboard gesture rule). For each effect a behaviour has at a Rust construction site's parameters, the adapter's witness mode moves only that effect to its next-best placement (dropped, installed in the bubble phase at the element, delayed by Rust's modelled latency, or reordered after the next vdom event or a page transition) and a library commit-point probe (`wrongPaint` by trajectory inclusion, `defaultAction`, `focusAtNextInput`, `outcomeOrder`) must go red, with a control arm that stays silent; the witness is an expected-failure test with a typed error, run on Playwright WebKit where it can observe and under fallback emulation where the effect serves another engine, and for the next-frame row it is the owner's `research/measure/<port>/verdict.json` (`{verdict, reason, devices, traces}`), where only the reason `lag` or `order` admits. Structural detection is the inventory, not a ground (a generated `Decision<E>` type from one closed effect list, behaviour modules compiled without the DOM, an adapter that refuses an undeclared effect). There is no allowlisted-module category. **The executor is decided by `reconcile`'s witness, which phase 0 runs first:** an unshown `[popover]` is `display: none`, so a late open paints nothing wrong and the witness is probably green, in which case the executor is a Rust-side `transaction` in the bridge; otherwise it is the page reconciler, one document-scoped observer installed at boot (eight of eleven popover consumers mount the panel in the render that opens it, so a per-element observer attached later sees no change). Either way there is one executor per element applying closes before opens, a batch ordered by tree (closes deepest first, opens shallowest first, with a layer-cascade invariant), the one show writer (its open step reports `applied{gen, rects}`), and the dialog exit wait (L5) on the page. No `volatile`: the epoch makes every Rust decision a changed value. **Verbs are single member calls** (one member call or read plus at most one guard `if`; a gate checks each row); a program such as L16's open-focus policy is a behaviour (`openFocus`), not a verb, and reducers are a closed `REDUCERS` table. An rsx handler takes only `prevent_default` (the `DataTransfer` setters are silent no-ops on desktop, so clippy bans them). When Dioxus delivers an event and its fields (0.8 `onbeforeinput`), the behaviour moves to rsx. The registry (planned; none exists in the tree yet): `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`, `settle`, `openFocus`, `stickToEnd`, `scrollOwner`, `labelClick`; `reconcile` only if its witness keeps it out of the bridge; `scrollStep`, `roving`, `place` and `wheelBand` (C5's fallback) only on a red witness or a `lag`/`order` verdict; `dialogKeyForward` reserved. The first version's predicate interpreter and round 1's three-way rule by listener location are both dropped.
