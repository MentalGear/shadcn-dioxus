# Row 434: Cut JavaScript to what Rust cannot do

## Item

The owner's principle (2026-10-25): the point of Dioxus is to drive the UI from Rust/wasm, so JavaScript is the exception, not the default. The library has no `web-sys` dependency; every browser API Dioxus does not wrap goes through `document::eval`, the one route that works on web, desktop and mobile. 72 files carry eval. The owner chose **Rust first** over "Rust plus web-sys" (one code path per feature, every renderer) and over the original TypeScript move.

1. **Audit** every eval block and classify it: (a) Dioxus already has it in Rust (`MountedData::get_client_rect`, `scroll_to`, `set_focus`, event data, signals, `onvisible`/`onresize` where they exist), so move it; (b) Dioxus has no Rust API (`showPopover`/`showModal`, `matchMedia`, pointer capture, listener options such as passive/capture, `scrollend`, `getAnimations`), so it stays JS; (c) must run before wasm (`PREPAINT_JS`, the modality writer), so it stays JS; (d) JS on purpose for latency (one-frame measure-and-place in the anchor engine, scroll bridge, virtual find), so it stays only with a measured reason.
2. **Move** every (a) block to Rust, per cluster, with the components' specs on a release build as the proof (timing-sensitive paths compare long tasks before and after).
3. **What stays** (b, c, d) moves into typed `primitives/src/ts/` modules through the existing bundle chain (the original P9 construction), and the copies become one file.

## Step 3 design: one small generic JS bridge (owner 2026-10-26)

Superseded where it differs by "Step 3 adopted" below (the rule that the bridge cannot carry in-event decisions became the deadline-indexed placement rule and the named-behaviour registry).

The owner asked for a uniform small JS glue layer to Rust instead of many bespoke scripts, which is also how Dioxus frames `document::eval` interop. So step 3 is no longer "every remaining block becomes a TypeScript module". Instead:

- **Lane 3.0 builds the bridge.** One small typed module (`primitives/src/ts/bridge.ts`, through the existing bundle chain) with generic verbs only and no component logic. It covers listen, call, get, observe and match:
  - `listen(target, type, options, fields)`: window, document or element; `capture`, `passive` and `once`; it streams the named event fields to Rust over the eval channel and grows out of `js_listener.rs`'s `listen`, which already owns removal.
  - `call(el, method, args)`: `showPopover`, `hidePopover`, `showModal`, `close`, `setPointerCapture`, `focus({preventScroll})`, `scrollIntoView(opts)`, `setSelectionRange`.
  - `get(el, props)`: computed style values, `offset*`, `activeElement`, `visualViewport`.
  - `observe(el, kind)`: ResizeObserver, IntersectionObserver (with rootMargin and threshold), MutationObserver.
  - `matchMedia(query)`: a subscription.
  On the Rust side these are typed hooks and extension traits (`use_window_listener`, `el.show_popover()`, `use_media_query`), so the logic of every (b) block moves into Rust.
- **What the bridge cannot carry stays as named JS modules, each with a measured reason.** Bridge messages reach Rust asynchronously, so two kinds of work can't go through it. The first is a decision that must happen inside the listener call, such as a conditional `preventDefault` (wheel band, drag, Escape inside nested layers, OTP filtering). The second is read-then-write in one frame (anchor placement, the virtual scroll bridge unless 2D shows otherwise, carousel drag and wheel). Those become TypeScript modules as originally planned. The audit's (d) rows say which apply.
- **Expected effect:** class (b), about 25% of the JS, becomes Rust plus generic verbs. Class (d) shrinks to the parts that are genuinely synchronous. Class (c), pre-wasm, stays as is. Lane 3.0 is sized again once the bridge exists, and the per-cluster lanes then remove blocks against it.
- **Gate:** besides `check-js-in-rust.sh`, any new `eval` must use a bridge verb, or be a named module listed with its (c) or (d) reason.

## Step 3 adopted: a deadline-indexed placement rule, named behaviours, hardened gates (owner 2026-10-26, after two adversarial boards)

The owner asked whether the "synchronous" residue could be bridged too. Analysis: [`../research/sync-js-root-2026-10-26.md`](../research/sync-js-root-2026-10-26.md) (the plan, amended twice) and [`../research/sync-js-residue-2026-10-26.md`](../research/sync-js-residue-2026-10-26.md) (W8, C5, C1). The owner chose **Adopt**. This section is the current plan; the agent-facing form is [`../js-interop.md`](../js-interop.md). **Root:** the browser takes its irreversible decisions at fixed points (end of dispatch, gesture start, input routing, paint, compositor frame), so only code on the page's thread with data already there can affect them. Rule: never ask Rust at commit time; Rust publishes beforehand and the page decides locally. Dioxus element handlers are synchronous on web and on desktop/mobile only for `prevent_default` (133 Rust calls rely on it); everything else a Rust handler does, and the bridge, is async. **Every desktop claim is "web-verified; desktop inferred"** until a `desktop-pass/<tree>.pass` stamp exists (row 442).

- **The placement rule: classify each decision by its deadline, then by its kind.** The table (root doc section 2.2):

  | deadline (what a late answer costs) | placement |
  |---|---|
  | this event's default action (cancel or not) | an rsx handler if Dioxus delivers the event and every field the decision reads (`ToggleData` is empty, so `ontoggle` decisions do not qualify); otherwise a named behaviour |
  | this event's task (pointer capture, focus routing for the next input) | a named behaviour's effect; never an async verb, never rsx `set_focus` on desktop |
  | before paint (a same-frame layout write) | A where the platform does it (per-feature floors and a boot probe); otherwise a named behaviour (`stickToEnd`, placement on fallback engines); G only for one-shot placement where an invisible pending state is acceptable |
  | next frame (drag tracking, momentum) | bridge stream plus Rust under a latency budget the owner sets from the row 442/443 measurements; a named behaviour only if the measured lag exceeds it |
  | none | R: Rust over the bridge |

  **Kinds:** a *listener* reacts to events; a *command* mirrors Rust state into the page (Rust publishes a `data-dx-*` attribute, one page reconciler applies it: popover open, modal open, `indeterminate`, `defaultChecked`; only browser-initiated changes are reported back; on desktop it runs before paint in the frame the edit lands, so an open saves a frame, and it removes the lost-command class, the stale toggle echo of row 115 and the two-writer `<dialog open>` trap). **Admission:** a named behaviour must contain a commit-sensitive effect (prevent, capture, focus, a same-frame write), checked from its generated effect set. **Verbs are single member calls** (a gate checks each verb row); a program such as L16's open-focus policy is a behaviour (`openFocus`), not a verb. When Dioxus delivers an event and its fields (0.8 `onbeforeinput`), the behaviour moves to rsx. The registry: `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`, `settle`, `scrollStep`, `openFocus`, `stickToEnd`, `reconcile` (and `dialogKeyForward`, `place` reserved). The first version's predicate interpreter and round 1's three-way rule by listener location are both dropped.
- **Order per decision:** delete what is dead, then an rsx handler (or a command), then A, then R, then G, then a named behaviour. "No residue" is withdrawn: about 880 lines of (d) JavaScript plus the (b) behaviours stay page-side, as a **closed** registry whose size is reported in `STATUS.md` and held down by the ratchet.
- **Delete dead JavaScript first.** About 16 eval sites sit in `#[cfg(not(feature = "web"))]` arms that every supported build compiles only for Blitz, where eval is a no-op: all three focus-trap evals plus `ts/focus-trap.ts`, 5 of 6 `use_global_escape_listener` calls, one context-menu scroll-block install. L23 (Label double-click) is already `user-select: none` in CSS. The typed sink makes the class a compile-time error afterwards.
- **A, behind floors.** Baseline dates each engine's first release, and those releases carry placement bugs (Firefox 147 lacks `position-try-order`; Safari 26.0 and 26.1 fail to anchor on reopen, 26.2 fixes it, nested anchors need 27). A is used behind **per-feature floors plus a boot probe** (edge shift, reopen x3, nested submenu, anchor under a scaled parent); a failing engine is a fallback engine and gated.
- **G, hardened twice.** Gate by `:popover-open:not([data-dx-anchored]):not([data-dx-placed])` (the tier predicate, with a per-surface list because the navbar, navigation menu and toast animate differently); the pending style selects its **own fail-open animation** (not `animation: none`, which kills a delay-based fail-open, and the theme's `[data-dx-motion-key] * { animation: none !important }` defeats it for nested popups) plus a **page-side watchdog**; the pending flag is cleared in the **`show` verb's own JavaScript turn**, not `beforetoggle` (absent for `<dialog>` on Chrome before 132, Firefox before 133, Safari up to 18.7); the **generation is page-owned**. Two tiers: placement-critical (fallback engines, the iOS keyboard clamp) is gated; decoration (placed side, arrow, available height) never is. Pending states are opacity-only. T8 keeps a Rust "verify the outcome" step (Firefox once reported anchor support and failed).
- **W8, C5, C1, in the owner's order.** W8 is a Rust invariant ("end sentinel visible, else scroll to end") with native `overflow-anchor` as the accelerator where verified and the **`stickToEnd` named behaviour** (about 40 lines, a ResizeObserver callback writing `scrollTop` while the Rust-published mode is `following-bottom`) for the same-frame write on engines without it (Rust over the bridge alone is 1-2 frames late on desktop, and Safari enabled anchoring only in 27); Rust keeps the mode machine, intent, opening position and the invariant. C5 stays a Rust attempt (flush per event task, a "Rust busy 30 ms" scenario, the replay harness's phase fixed); the owner measures it with the old/new switch (`?dx-impl`), and **if Rust loses it becomes an allowlisted TypeScript module**. C1 dissolves. **Lane 3.FZ freezes all legacy paths** (message scroller, C2 to C5, macros) into `ts/legacy/` behind a non-default `legacy-impl` feature that only preview enables, wrapped and behaviour-neutral, in phase 0; removal is **keyed to the owner's measurement stamp, not a date**; the shipped feature-off arm gets its own clippy and test arm.
- **Enforcement closes sinks, not spellings.** One `eval` call site (`bridge/transport.rs`, typed by a `Program` enum, not a `&str`) plus three named pre-wasm exceptions (`eager_head.rs:86`, `theme_seed`, the runtime modality writer, generated from one `.ts`); clippy `disallowed_methods` for `document::eval`/`Document::eval`/`Script` outside it, with a per-file `expect` until the last eval line goes; a `git ls-files -co` universe; an allowlist of `Script { src: asset!() }` constants; no inline-marker escape; TypeScript scanned with the compiler API. **A ratchet raise needs a grant row present at the merge base** (`js-grant:` front matter), and "a new behaviour needs a row" means a row at the merge base, open, naming the kind in `adds:`; what ships (bundle bytes and Rust-held JS) is counted, not tests, `.d.ts`, generated files or display snippets; the landed gate's holes (`/vendor/`, `.min.js`, `.md`/`.svg`, untracked files, `dd::eval` as a fn pointer, physical-line counting) are closed; the older listener, interval and blocking-scroll gates retire on a fate table, not when their allowlists reach zero; `check-hot-events` counts event names app-wide and includes `onmounted`. **One gate owner** (lane 3.0, or 3.0b).

A desktop-cadence web build, Playwright WebKit and Firefox, and one WebKitGTK or real-desktop pass per batch recorded as `desktop-pass/<tree>.pass` close the gap (row 442); a batch merges on "web-verified; desktop inferred" with the stamp a post-merge debt list. New specs: `bridge-cost`, `g-latency`, registry leak, first-frame, open/close/open, the stuck-channel fail-open (with an `animation: none !important` ancestor), the boot probe, a nested-submenu and a reopen x3 spec. The owner measures the three feel-critical ports with `__dxPerf`, a bridge round-trip histogram, `?dx-bridge-delay=N` / `?dx-bridge-spin=ms` and the `?dx-impl` switch (row 443).

Five phases. **Phase 0:** merge lane 3.0 (bridge) and lane R (ratchet); **3.0b** the verb and behaviour-skeleton sweep (the missing table rows, ten behaviour skeletons, the wider adapter, removal of the `setPointerCapture`, `releasePointerCapture`, `focus` and `commit` verbs, the typed transport and ordering, the gate work above); **3.FZ** the freeze and the `?dx-impl` switch; the **row 443 kit**. **Phase 1** (four lanes, one deploy): **3.DJ** dead JavaScript (merged first), **3.PL** placement with T4-T7 (`popover_sync.rs`) and the G pieces, **3.OV** overlay core, **3.VS** virtual settle (after lane 2D merges). **Phase 2:** **3.SL** scroll lock, **3.GS** gestures and toast, **3.FC** form and input primitives, **3.OB** observers. **Phase 3:** **3.CA** carousel, **3.HV** the existing frame-rate vdom handlers (about 20 sites), **3.PV** preview glue with V19, **3.SC** `collection.rs` and `activity.rs`. **Phase 4, the owner measuring after each, one at a time:** **3.MS** message scroller, then **3.WB** wheel band, then the legacy removal. ## Lane 3.0 result: the generic bridge and the named-behaviour mechanism (2026-10-26, branch `lane/js-bridge-3-0`)

What exists now, for the step 3 lanes to build on. No component block is migrated; `js_listener.rs` (rebuilt on the bridge's scope) is the one consumer, and there are ZERO real behaviours (one test fixture).

- **JS half:** `primitives/src/ts/bridge.ts` (script bundle `js/bridge.js`, installs `window.__dxBridge`, version 3): `scope`/`channel`/`serve`/`pump`, `listen` (always passive; a hot event is coalesced to one message per frame), `call`/`get`/`set`/`observe`/`media`/`sample` (coalesced and batched fields, batched flushed per frame or per event task), `transaction` (synchronous, one JS turn), and the behaviour engine (`register`, ref-counted listener hub, epochs, leases, per-install `memory` that a decision's `remember` extends, teardown when the host element disconnects). There is no `commit`, and `focus`, `setPointerCapture` and `releasePointerCapture` are not `METHODS` rows (round 2 of the board: a call lands after the event's dispatch, so they are rsx handlers). Everything a name reaches goes through closed own-property tables with a receiver kind per row (`EVENTS`, `FIELD_GETTERS`, `METHODS`, `PROPS`); `set` takes only `--dx-*`.
