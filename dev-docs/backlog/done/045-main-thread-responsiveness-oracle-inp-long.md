# Row 45: Main-thread responsiveness oracle (INP / long tasks). Install a PerformanceObserver for longtask (and event…

## Item

**Main-thread responsiveness oracle (INP / long tasks).** Install a `PerformanceObserver` for `longtask` (and `event` timing with `durationThreshold`) in the page before each overlay's open/close and each form control's primary interaction, then assert no task over 50 ms and no interaction over 200 ms was recorded during the gesture — the thresholds from the reference in [`recommended-implementations.md`](../../recommended-implementations.md) §11 (kciter, *The Browser's Main Thread Is Expensive*). Rules 1–5 of that section (no same-handler layout read+write, passive listeners unless `preventDefault`, compositor-only animation unless bounded and frame-sampled, no busy-wait, no atomic heavy work inside render) are review-enforced only until this exists

## Status / trigger

**LANDED 2026-09-19 (batch 3; first note below)** -- original trigger: A device report of a late tap or stalled animation that the existing frame samplers (`accordion-animation.spec.ts`) and position oracles do not explain; or the first component that does real work per interaction (Command palette filtering, [`component-backlog.md`](../../archive/rounds/component-backlog.md))

## Detail

Chromium-only in this sandbox, so the numbers are a regression guard, not an iOS measurement — the same caveat as every other tier-2 oracle here. `longtask` entries need `buffered: true` or an observer installed before the interaction; Playwright's `page.evaluate` can do both. **Landed 2026-09-19 (batch 3):** `oracle/tier2-html/main-thread.spec.ts` (823 lines, 58 tests: 19 overlays × open/close + 20 form-control gestures including real pointer drags for Slider/Resizable/Drawer) plus its paired helper `playwright/main-thread.ts` (339 lines: `installMainThreadObserver` via `page.addInitScript`, `withGesture`, `assertResponsive` — best-of-3, never lowering the threshold to compensate for scheduling noise, every measurement recorded via `test.info().annotations` regardless of outcome). Cites the W3C Long Tasks API (a long task is, verbatim, any occurrence whose duration exceeds 50ms) and the W3C Event Timing API (`durationThreshold`, clamped to a 16ms floor by spec, not an arbitrary choice) — both reachable, HTTP 200, checked 2026-09-18. Thresholds unchanged from this row's own original wording: 50ms/task, 200ms/interaction. Red proof without a build (kept out of the repo, per this row's own instruction): a synthetic 120ms busy `pointerdown` handler turned the drawer/slider drag tests red (137/147ms); a synthetic 250ms busy `click` handler turned dialog-open red (312ms). **55/58 green** across four full runs (Chromium-only skip for the rest, this row's own original caveat, unchanged). **Three subjects RED BY DESIGN, load-independent** (measured at loadavg 1.2 through 17+, same signature every time): `combobox: open` 59-75ms, `command: open` 59-83ms, `date_picker: open` 60-88ms — over the 50ms long-task threshold, under the 200ms interaction one. A dedicated debug lane (open-cost, no commits) root-caused the mechanism: DOM-node counts on open (dropdown_menu +10, combobox +10, select +14, command +39, date_picker +247 — 35 day cells each with dynamic attributes plus an `onmounted` effect) point at ONE mechanism behind two trigger sites — `top_layer.rs`'s `use_anchor_position_fallback`'s `reposition()` (combobox/select/date_picker) and native `showModal()` via `use_dialog_open_driver` (command) both perform a synchronous DOM mount plus a forced-layout read inside the same event-handler task (this row's own §11 rules 1 and 5). A one-frame deferral of combobox's `initial_focus` write was implemented and measured (66-139ms → 57-63ms — real, insufficient) then reverted, not committed. Three proposals for a dedicated future batch, none applied here: (1) defer the mount itself to the frame after `open` flips — most complete, HIGH risk, since `top_layer.rs`'s own comments record a rAF-wrapped `reposition()` that "silently never ran at all on a real Firefox build"; (2) defer `showModal()` promotion by one frame in `use_dialog_open_driver` (shared by Dialog/AlertDialog/modal Popover/Sheet) — partial win, medium-high risk; (3) give Combobox the menu family's deferred-collection-focus shape `collection.rs` already has. Needs a symbolicated wasm profile (debug info/sourcemap) to name the exact Rust function still costing ~55-65ms on a 10-node mount before any of the three proposals should be attempted. Methodology note for future scripts: `PopoverNonModalContent` sets no explicit `role` attribute, so a raw `[role="dialog"]` CSS selector matches nothing against it even though Playwright's `getByRole("dialog")` (implicit role) works fine. **Standing review line, same class as rows 74/75** (unscoped Playwright locators silently resolving against more than the intended element once a page grows more instances): building this oracle found `virtual_list.spec.ts`'s own unscoped `page.getByRole("list").first()` resolving the docs sidebar's first `<ul>` instead of the demo's own `.dx-virtual-list-container` once the sidebar (batch 2) added seven of its own `<ul>` elements ahead of the demo in DOM order — fixed at integration (`1462e9d`) by scoping through the demo's own class. The same class recurred a fourth time once RTL fixtures made every RTL-aware component render two variants on one page at once: `menubar.spec.ts`, `navbar.spec.ts`, and `keyboard-matrix.spec.ts`'s Menubar Left/Right-Arrow rows all called `page.getByRole('menubar').focus()` unscoped, now resolving 2 elements; fixed at integration (`5953405`) by scoping through `#component-preview-frame`. **This is now a four-occurrence class (rows 74, 75, and this row's own two instances) — per this repo's own stated rule for recurring problems, a review line is a stopgap, not the construction.** Candidate construction for a future session: a small lint/test-helper restricted to `playwright/*.spec.ts` (not `oracle/`, which often deliberately queries page-wide) that flags a bare `page.getByRole(...)`/`getByText(...)` with no `.first()`/container-scoping chained — the same shape `check-self-subscribing-effects.sh` (row 79) became once row 73's own "standing review checklist line" recurred enough to justify automating it. Not built this round. **Review line for every future spec in the meantime:** scope role/name queries on any component page — a route can render more than one variant of the same component at once, and a shared-chrome landmark can carry the same implicit role as a demo's own content **2026-10-05 (round 3 final verification) note, thresholds on a loaded box:** in the full release run (4 workers) the sheet, drawer and command open/close cases measured 51-53 ms against the 50 ms long-task bound and PASSED when re-run serially, so a red at 51-53 ms under 4-worker load is a load flake, not a regression (the same shape as the `main-thread.spec.ts:807` drawer case in row 116's account). Do not widen the 50 ms bound; judge a main-thread red by its serial rerun, and keep timing specs on release builds only (debug builds give false reds, row 116).
