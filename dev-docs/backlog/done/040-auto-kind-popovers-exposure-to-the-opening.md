# Row 40: Auto-kind popovers' exposure to the opening-gesture light-dismiss false positive — audited 2026-09-03; Navbar…

## Item

**`Auto`-kind popovers' exposure to the opening-gesture light-dismiss false positive — audited 2026-09-03; Navbar half FIXED 2026-10-04 (`d9bcfda`), the Menubar/DropdownMenu/Select/Popover half closed as refuted 2026-10-03.** `DropdownMenu`/`Menubar`/`Select`/non-modal `Popover` (`PopoverKind::Auto`) rely on the browser's own native light-dismiss algorithm; an engine whose touch-to-click synthesis can retarget a click at whatever DOM mutation just occurred under it (the same class of quirk `native-dialog.spec.ts` Rule 8 fixes for the modal arm's own JS listener) could in principle read the tap that opened one of these as "outside" too, since none of their triggers declare a `popovertarget` invoker. Not reproducible in this sandbox's Chromium (confirmed by execution, touch-emulated)

## Detail

**2026-09-26 (audit correction):** audit-only by design — no action expected here without a real-device report confirming the issue actually occurs. `popovertarget` (WHATWG's own declared-invoker answer) was evaluated and rejected for this round: every one of these four triggers is a *toggle* button (`onclick`/`onpointerup` computing `!open`), and `popovertarget`'s default action is `"toggle"` too — layering a second, browser-native toggle onto the same click as this crate's own Rust-driven one risks a double-toggle race with no way to verify the outcome without a real device. Switching to `Manual` + `use_outside_dismiss` (Combobox's own precedent, `combobox/components/list.rs`) was also considered and deferred: it would lose `auto`'s free cross-instance exclusivity (opening one closes unrelated open ones) for four components with green existing suites, a larger behavior change than a single unreproduced device report justifies on its own. **2026-10-03 re-audit (main @ 2241da8) -- the premise is refuted for the click-open family; a different, real exposure was found and a probe added; fix deferred until the probe is run.** (a) **Refuted:** the WebKit quirk this row (and `native-dialog.spec.ts` Rule 8) worries about retargets a *synthesized `click`*. The browser-native light-dismiss algorithm never reads `click`; it uses only trusted `pointerdown` + `pointerup` (WHATWG HTML "popover light dismiss", fetched 2026-10-03), and a popover that is not yet open at `pointerdown`/`pointerup` is ignored entirely ("if topmost auto popover is null, return"). `DropdownMenu` (`dropdown_menu.rs:530` `onclick`), `Select` (`select/components/trigger.rs:244` `onclick`) and non-modal `Popover` (`popover.rs:871` `onclick`) open from `click`, i.e. after `pointerup`, so they cannot be dismissed by their own opening gesture on any engine; `Menubar` opens from `onpointerup` (`menubar.rs:621`), the same. No `popovertarget` is needed, which also dissolves the double-toggle worry in the 2026-09-26 note. (b) **The real exposure the audit missed:** `NavbarTrigger` opens on `onpointerdown` (`navbar.rs:621-632`) and its content is `popover="auto"` (`navbar.rs:907`). If `showPopover()` lands between that gesture's `pointerdown` and `pointerup` (any hold longer than Dioxus's render+effect, which a real finger always is), `pointerup` sees an open auto popover, `sameTarget` is `null === null` = true, and the browser hides it. `navbar.spec.ts` 'mobile navigation' cannot see it (Playwright `tap()` has zero hold); on a real device `NavbarNav`'s compat `onmouseenter` can re-open it and mask the flash. NOT confirmed by execution (no build this lane). **Probe:** `playwright/oracle/tier2-html/auto-popover-opening-gesture.spec.ts` (CDP touchStart, 250ms hold, touchEnd; asserts no `toggle`->closed on any `[popover]`; Navbar = suspected red, DropdownMenu = green control). **If the Navbar case is red the fix by construction is to stop opening an `auto` popover from `pointerdown`:** open `NavbarTrigger` on `click` (keeping the pointerdown `prevent_default()` for the blur guard, `navbar.rs:624-630`), or move `NavbarContent` to `manual` + `use_outside_dismiss` (Combobox precedent). That subsumes row 40's Navbar half and the class "auto popover opened mid-gesture"; it does not subsume the genuinely device-only iOS retarget case for the modal arm (already fixed, Rule 8). If green, close this row as refuted **2026-10-04 resolution (NAVBAR lane; Navbar half FIXED by construction, probe confirmed RED on a release build before the fix):** `toggles=[{open},{closed}]` for a 250ms-held touch on `NavbarTrigger` (HTML light dismiss: pointerdown target popover null === pointerup null), DropdownMenu green. Fix = option (a): `NavbarTrigger` now toggles on `onclick` (after `pointerup`, so a native light dismiss can never see its own opening gesture); `onpointerdown` keeps only `prevent_default()` (blur guard: tapping a child menuitem must not blur the trigger) plus a snapshot `open_at_down = Some(is_open())`, which `onclick` consumes. The snapshot is needed because on touch `NavbarNav`'s compat `onmouseenter` hover-open fires between `pointerup` and `click` -- toggling off live `is_open()` would close the menu the tap just opened; desktop hover-open precedes `pointerdown`, so the snapshot is `true` and click closes, as before. A click with no snapshot (Space activation, AT) falls back to live state; any `keydown` clears a stale snapshot. Keyboard (Enter/ArrowDown/ArrowUp on `NavbarNav`, Escape, roving focus) and hover-open untouched; native (non-web) arm shares the same trigger code, no cfg change. Class audit: grep of every `popover="auto"` consumer (`dropdown_menu` content + sub, `context_menu` sub, `menubar`, `popover`, `select`) -- none other opens from `pointerdown` (they open from `click`/`pointerup`/hover timers/keyboard); `ContextMenu` main content is `manual`. Class made a written contract on `top_layer::PopoverKind::Auto` ("auto popovers are shown only from click/pointerup/keyboard/hover-compat/timer, never `onpointerdown`"), pinned by the probe. Row 40's Menubar/DropdownMenu/Select/Popover half stays closed as refuted (2026-10-03). Verification still owed by the build lane: probe + `navbar.spec.ts` + keyboard-matrix + top-layer. **2026-10-04 verification record:** the probe was RED on release 9f8399d before the fix (`toggles=[{open},{closed}]` for a 250 ms held touch on `NavbarTrigger`, i.e. open -> closed; `DropdownMenuTrigger` GREEN control and the spec's non-vacuity assertion passed; `baseline/RELEASE.md` section 3b), so the exposure is real on release, not just in reading. Verification of the fix `d9bcfda` against the final build: on the release build of `b9e9580` (2026-10-04) the probe `auto-popover-opening-gesture.spec.ts` is 2/2 GREEN (Navbar: no `open`->`closed` toggle under the 250 ms held touch; DropdownMenu control still green, non-vacuity assertion passed) and `navbar.spec.ts` 5/5, `keyboard-matrix.spec.ts` 77 passed / 1 skipped, so the red-before / green-after pair on the same build type confirms the fix.
