# Row 96: scroll-snap-stop: always caps a browser-driven scroll but NOT this crate's own pointer-drag release

## Item

`scroll-snap-stop: always` caps a browser-driven scroll but NOT this crate's own pointer-drag release

## Status / trigger

Landed 2026-09-20 (round 5) after the user chose a CSS-only no-skip guarantee over matching embla's velocity model

## Size

DONE as far as it goes; the residual gap is deliberate, not outstanding work

## Detail

**2026-09-26 (owner re-evaluating):** the owner is re-evaluating this row's non-loop edge-overscroll framing in the bench (`dev-docs/research/carousel-overscroll-bench.html`; the live bench artifact is newer than the committed 2026-09-23 write-up) — approach E ("native room": real scroll room past the ends that the browser itself scrolls into, with a compensating transform following WebKit's own stretch curve, and the browser's own snap releasing at lift) is under consideration to replace B3 and the owner said it "feels right"; a clip fix for E is being chosen. This row's drag-release/flick framing is therefore under re-evaluation, not settled — see row 102's matching addendum. The user's call was explicit: "the exact velocity is not important, since we use native css and there is some difference expected, we can only set no overscroll of slide css property if the browser supports it", and then "lets not go overboard with parity where it does not matter and where the basis is different". So `scroll-snap-stop: always` is set on every slide behind `@supports`, and no JS velocity model was built. **What it does cover, measured twice independently:** a browser-animated scroll is capped to one slide pitch — `scrollBy({left: 1000, behavior: 'smooth'})` travels 1008px (3.00 slides) without the property and exactly 336px (1.00 slide) with it, at a 333px pitch. **What it does not cover:** our own drag release. The drag path holds `scroll-snap-type: none` for the whole gesture (so per-move instant `scrollBy` calls don't fight snapping), so there is no in-progress scrolling operation for the property to constrain; restoring the type afterwards is a static re-evaluation of an already-stopped position, and the settle lands on whichever slide is numerically nearest — a 2.5-pitch drag settles at 2 pitches, identical to the property being absent. A same-tick zero-distance nudge and a 1px smooth nudge after restoring the type were both tried and neither routed the correction through the constrained path. **Also not covered:** the short-fast-flick symptom that originally motivated the lane (a quick flick settling back to the origin instead of advancing) is inherently velocity-shaped — no CSS property can observe release speed, so this is unreachable CSS-only by construction. Closing either gap means a JS distance-or-speed threshold, i.e. the velocity model under another name, which the user declined. Reopen only if the user asks for it.  **CORRECTION, same day: the first implementation of this was inert and the row above described an intent, not a shipped behaviour.** It set the property via a scoped `<style>` tag rendered from `CarouselContent`. Against a real release SSG build, `getComputedStyle(slide).scrollSnapStop` read `normal` on every slide and a 1000px smooth `scrollBy` travelled 1008px (3.03 slides) — completely uncapped. The `<style>` element was present with the correct id, and the id matched the live element pre- and post-hydration, but `styleElement.sheet.cssRules.length` was **0**: Dioxus emits hydration marker comments *inside* the element's text (`<!--node-id413-->@supports (…) { … }<!--#-->`), and in CSS `<!--`/`-->` are CDO/CDC tokens, so the ident between them begins a qualified rule whose prelude swallows the real `@supports` rule and the browser drops the lot. Injecting the byte-identical CSS without markers gives `cssRules.length === 1` and computes `always` immediately. It would have worked in pure CSR, where no markers are emitted — which is why it looked correct in a dev loop. **Fixed** by declaring `scroll-snap-stop:always` inline on `CarouselItem` beside its existing `scroll-snap-align:start`; the `@supports` guard was deleted rather than relocated, because an unrecognised property in a `style="…"` attribute is dropped by the parser by definition, which satisfies the user's "if the browser supports it" requirement without a stylesheet at all. Verified live post-hydration: computed `always` on all five slides, and 1000px / 2.5-pitch / 3-pitch scrolls all cap to 336px. **The test that shipped with the broken version was a false green:** it scrolled 2.5 pitches and asserted slide 2, which is the nearest snap point with or without the property; it passed 54/54 against an inert build. Replaced with a 3-pitch scroll, where capped (slide 2) and uncapped (slide 4) diverge. The two limitations recorded above (drag release uncovered; short-fast-flick velocity-shaped) remain true and unchanged.  **UPDATE 2026-09-21, round 6.** The drag release now animates: it is routed through the same `scrollIntoView` paging path `CarouselPrevious`/`CarouselNext` use, and the `scroll-snap-type` restore is deferred until that scroll finishes (`scrollend`, with a timeout fallback), with a fresh `pointerdown` cancelling any pending restore so it cannot fire mid-gesture. Measured: 18 samples across a release, **11 distinct `scrollLeft` values** from 228 to 336, against exactly 2 before. **The cap-to-one-slide gap persists, for a restated reason.** It is no longer "restoring snap-type is a static re-evaluation"; it is that the release picks the nearest slide by `getBoundingClientRect` geometry and that search has no "cap from the gesture's origin" concept, so a long drag can still land several slides away. Closing it still means a JS distance-or-speed threshold, i.e. the velocity model the owner declined, so it stays open by choice. The short-fast-flick case is likewise unchanged and remains unreachable from CSS. Note the release now performs one `getBoundingClientRect` read per gesture — deliberately not a `scrollLeft` read, which is the RTL hazard this file avoids everywhere, and outside the pointer-move hot path.
