# Row 58: Sidebar block-demo iframe rendered empty on live production; homepage Sidebar card now exposes live config…

## Item

**`Sidebar` block-demo iframe rendered empty on live production; homepage Sidebar card now exposes live config for the real site nav — LANDED 2026-09-15, user-reported + user-requested.** Visiting `/component/?name=sidebar&` on the deployed site showed the demo's own Side/Collapse settings panel rendering and responding to clicks, but the actual `Sidebar` preview never appeared — no `[data-slot="sidebar"]` node anywhere, just empty space, on every collapse/side combination. **Root cause:** `Sidebar`'s own responsive check (`component.rs`, `MOBILE_BREAKPOINT = 768`, `use_is_mobile()`) reads `window.innerWidth` of whatever document it's running in — for an `<iframe>`, that's the iframe's own content window, not the outer page's viewport. The block demo's iframe (`BlockComponentVariantHighlight`) was `width: 100%` inside the page's content column; once row 56 (above) narrowed that column with the new site-nav sidebar, the iframe's measured `innerWidth` dropped to ~684px — under the 768px breakpoint — flipping `Sidebar` into its mobile branch, which renders a closed `Sheet` (nothing painted) rather than the desktop branch. Proven directly on the live, unmodified production site: widening the existing iframe in place from 684px→820px via the exact `resize`-event path `use_is_mobile()` listens for flipped the rendered sidebar count 0→1. **Fixed** by giving the shared iframe a `min-width: 820px` (comfortably clear of the breakpoint) plus `overflow-x: auto` on its wrapper (`html,body{overflow-x:clip}` in `main.css` would otherwise silently clip rather than scroll) — one shared construction point (`BlockComponentVariantHighlight`), so it covers every current and future `ComponentType::Block` component's iframe, not just Sidebar's. **Second part (user-requested):** the homepage's Sidebar gallery card previously just linked out ("Open full preview") instead of showing anything live. `DocsLayout` now takes optional `side`/`collapsible` signals (every other call site still gets its own fixed local defaults, seeded identically to before, so no behavior change there); `Home()` owns and provides them via a `HomeSidebarControls` context; `ComponentGalleryPreview`'s `Block` branch, only for `component.name == "sidebar"` (`try_consume_context`, degrading gracefully to the old link anywhere else), swaps the link for `SidebarGalleryCardControls` — the same Side/Collapse button shape as the demo's own `DemoSettingControls`, but writing straight to those signals, so clicking them visibly reconfigures the real, on-page site sidebar live. Confirmed no state leakage across navigation (Dioxus remounts `DocsLayout` fresh per route). **A second, unrelated-but-newly-exposed layout bug found while verifying this:** at a plain 1280px viewport the new card's Side/Collapse controls rendered genuinely off-screen and unclickable (not a scroll issue — `document.documentElement.scrollWidth` was *less* than `clientWidth`, so the content was clipped, not scrollable-to). Root-caused to a classic Flexbox pitfall, not this card's own layout: `.dx-sidebar-inset` is `flex: 1 1 0%` with no `min-width` override, so its *automatic* minimum width defaults to its content's min-content size rather than 0 (CSS Flexbox spec) — any wide-enough content anywhere inside the inset (here, the pre-existing, unrelated `WidgetMasonry` homepage widget, confirmed by live DOM bisection removing subtrees one at a time) makes the whole inset refuse to shrink and silently overflow (`overflow-x: clip` on `html`/`body` hides it rather than scrolling), which in turn widens every sibling section sharing that inset's `width: 100%` — the gallery card whose own content happened to reach flush to its card's now-off-screen edge was just the first thing to make it visible and unclickable. **Fixed by construction, at the one flex item that needs to shrink** (`min-width: 0` on `.dx-sidebar-inset`) rather than re-constraining whichever content exposes it — covers `WidgetMasonry` today and any future wide content by the same mechanism, per this repo's standing "class not instance" rule. **A pre-existing, unrelated `dx build --ssg` tooling race found and guarded against during verification:** an independently-reproduced, systematic 9-build A/B test (alternating branch/baseline source, full `rm -rf target/dx/preview` each time) showed **100% correlation between build speed and correctness, 0% correlation with source content** — every build that had to actually recompile the `preview` crate (cold cache) came out correct on both branch and pristine baseline; every build that hit a warm cache (~10s, skip straight to bundling/SSG) came out with every non-home SSG route missing its `<script type="module">` hydration bootstrap tag entirely on both branch and baseline. This is a `dx`-cli/dioxus-fullstack race (the SSG render pass fires all routes' requests at the freshly-started fullstack server concurrently, seemingly before some server-side dependency of the client-bundling phase is ready) — not caused by, or fixable from, this app's own code. Guarded against rather than left latent: `scripts/deploy-preview.sh` now greps every built route's `index.html` for the bootstrap script tag right after the build and exits 1 with the affected route list before touching `/docs` if any are missing — verified both halves for real (a genuine cold `cargo clean` + full rebuild passes silently; re-running immediately after, cache now warm, naturally hit the same race and the script correctly caught it and exited 1 without touching `docs/`). **Verified by execution, independently re-checked twice more by the orchestrating session after two rounds of subagent-reported-but-unverified issues** (the SSG race initially mis-attributed to the diff; the card-overflow bug initially mis-attributed to the card's own layout) — both corrected via direct measurement before landing: `cargo check --workspace`/`cargo fmt --check` clean; `check-preview-composition.sh`/`check-dx-class-prefix.sh`/`check-css-literals.sh` clean; final clean `deploy-preview.sh` run passed its own new sanity check (6/6 routes); iframe `innerWidth: 820-822`, sidebar count 1, for all three Sidebar demo variants; homepage card's `Right`/`None` buttons clickable without `force`, `data-side` flips `left`→`right` live, `/docs` still defaults `left` after navigating away (no leakage); `document.documentElement.scrollWidth <= clientWidth` at 1280px
