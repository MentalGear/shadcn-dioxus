# Row 89: Selected/active state losing to :hover on click — a user-reported hover-over-state specificity class, swept…

## Item

Selected/active state losing to :hover on click — a user-reported hover-over-state specificity class, swept and partly fixed (calendar-state lane)

## Status / trigger

Landed 2026-09-19 (calendar, tabs); **residue closed 2026-09-20 (round 4, `7fdfacb`)** — toggle/toggle_group hardened (was never actually broken), pagination confirmed benign, both honest non-fix outcomes

## Size

S

## Detail

**User report:** "date picker: active state on selected date must be over hover state, otherwise active states are not visible after click" — a click leaves the pointer resting on the day it just selected, so hovering-what-you-just-selected is the common case, not an edge case. **Root cause, a real class, not one instance** (per this file's own "two or more is a class" rule): a component's plain `:hover` rule picked up extra specificity from a `:not([data-disabled="true"])` clause (raising it to (0,4,0)) and outranked a persistent-state selector like `[data-selected="true"]` or `[data-state="active"]` ((0,2,0)/(0,3,0)) that never anticipated needing to beat it — an accident of which selector happened to carry an extra clause, not a deliberate priority order. **Fixed by construction in two components**: every interactive-only `:hover` rule in `calendar/style.css` and `tabs/style.css` is now wrapped in `:where(...)`, which matches the exact same elements but forces its specificity to the lowest possible (0,0,0), so every persistent-state selector in the file outranks it unconditionally regardless of source order or accidental extra clauses — cheaper and more durable than reordering rules or reaching for `!important`. `:focus-visible` deliberately left un-wrapped in both files (it was never part of the bug and must keep winning on its own terms). Two real defects fixed: `calendar/style.css`'s dark-mode selected-day hover had drifted to different token values than its light-mode branch (a duplication that was the actual defect, not just a specificity accident) and a range selection's in-range "between" day had no hover companion at all, so the generic hover rule always won; `tabs/style.css`'s active-tab hover silently dimmed the active text color in both themes. **Swept, not fixed (recorded rather than silently dropped):** `pagination`'s own equivalent rule pair has a subtle token mismatch left on the watch list (not the same specificity accident, so not folded into this construction); `toggle`/`toggle_group`'s active-vs-hover tie is order-dependent rather than specificity-driven, a different shape of the same symptom, not fixed here. **Test-methodology trap found and worked around while writing the regression specs, worth recording for the next person:** clicking a real `<a href="#">` in a Playwright test navigates the page (breaking the rest of that test), and reading `getComputedStyle` mid-transition can catch an interpolated, neither-old-nor-new color value — both new tests wait past the false-signal cases before asserting. Evidence: `playwright/calendar.spec.ts`'s two new tests and `playwright/tabs.spec.ts`'s two new tests (light+dark) all confirmed RED on the unmodified tree with exact computed-color values, GREEN after the fix; full `calendar.spec.ts` 9/9, `tabs.spec.ts` 5/5, `date-picker.spec.ts` (the two pre-existing row-21 anchoring reds unrelated), `oracle/tier2-html/native-dialog.spec.ts` all re-verified green on the integration server. **Residue closed 2026-09-20 (round 4, `7fdfacb`), with two honest non-fix outcomes, not two more bug fixes:** `toggle`/`toggle_group` were diagnosed before reaching for `:where()`, per this lane's own discipline, and turned out NOT to be misbehaving — unlike calendar/tabs's accidental specificity bump, `.dx-toggle:hover`/`.dx-toggle[data-state="on"]` (identically for `toggle_group`) tie exactly at (0,2,0), and an ON control already keeps its "on" background while hovered on the unmodified tree, purely because `[data-state="on"]` happens to be declared after `:hover` and wins the tie by source order — fragile (order-dependent), not broken. Applied the same `:where(:hover)` construction anyway, scoped to only the `:hover` branch (`:focus-visible` untouched, since it was never part of the bug), so the win becomes unconditional (specificity, not accidental order) — confirmed byte-identical computed background-color values before and after, in both themes: a hardening, not a visible-bug fix, and the new Playwright tests in `toggle.spec.ts`/`toggle_group.spec.ts` document it as exactly that. `pagination`'s own watch-listed mismatch is confirmed benign, not fixed: the background token pair (`[data-active="true"]`'s own vs. its `:hover`'s) is indeed mismatched, real if subtle (exact RGB values captured, both themes) — but the actual "you are here" signal is the 1px border `[data-active="true"]` alone sets, which `:hover` never touches in either state and which no non-active link ever gets in any state; the CSS was left unchanged and the computed border-color/border-width evidence recorded in a new `playwright/pagination.spec.ts` (4 tests), per this row's own "genuinely benign is a legitimate outcome" allowance rather than a manufactured fix. Evidence: `toggle.spec.ts`/`toggle_group.spec.ts` full suites re-verified green (5/5 each, incl. axe); `cargo test --workspace` (433 passed, 0 failed), `check-css-literals.sh`/`check-css-logical-properties.sh`/`check-dx-class-prefix.sh`, and `cd preview && npx stylelint "src/**/*.css"` all re-run and clean after the CSS-only change, per this repo's own "every gate before every commit" rule rather than assumed unaffected
