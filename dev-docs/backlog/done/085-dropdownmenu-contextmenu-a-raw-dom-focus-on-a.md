# Row 85: DropdownMenu/ContextMenu — a raw DOM .focus() on a sub-trigger closes the whole menu

## Item

DropdownMenu/ContextMenu — a raw DOM `.focus()` on a sub-trigger closes the whole menu

## Status / trigger

**Landed 2026-09-20 (round 4, `3ba793b`)** — fixed by construction across DropdownMenu, Menubar, and both Sub levels

## Size

S to verify

## Detail

Not an RTL defect — reproduces identically on the untouched `main`/LTR variant of both `DropdownMenu` and `ContextMenu`, found only because this round's own RTL oracle exercises submenus more thoroughly than any prior spec. Calling `.focus()` directly on a submenu's own sub-trigger element (as a test driving focus programmatically would, and as an assistive-technology focus-restoration path plausibly could) closes the entire menu and reverts focus to the ROOT trigger, rather than simply focusing the sub-trigger in place. Not investigated further or fixed this round (out of rtl-rust's own remit); worth a dedicated look at `menu_sub.rs`'s focus-out/blur handling the next time either menu family is touched. **Closed 2026-09-20 (round 4, `3ba793b`), root-caused as a class rather than the single instance this row named:** every affected site shared one shape — a synchronous `onblur` deciding "did focus leave" by reading a Rust-tracked roving-focus signal (`ctx.focus.any_focused()` / `menu_ctx.focus.any_focused()` / `sub.focus.any_focused()`) that only this crate's own click/keyboard paths ever write (state-first, DOM-focus-second), and that no item in this "menu button" pattern family reconciles via its own `onfocus` — so a focus move arriving any other way (a test's raw `.focus()` call, or an assistive-technology focus-restoration path) read stale "nothing focused" state and closed the whole menu. `DropdownMenuTrigger`'s root and, independently, `MenubarTrigger`/`MenubarItem` and the shared submenu level (`DropdownMenuSubTrigger`/`ContextMenuSubTrigger`, `menu_sub.rs`'s `SubMenuState`) all carried the identical shape — Menubar's was the most directly reproducible of all (arrow-down onto an item then `.focus()` on its own trigger closed the content unconditionally, no mouse-opened precondition needed). **`ContextMenu`'s own root — this row's original, named instance — could not be reproduced red in this pass**: it already dismissed via `use_outside_dismiss` (DOM-containment-based, immune to the same-tick blur-before-focus ordering hazard by construction), so this row's original claim of a ContextMenu-root defect does not hold up under direct testing, stated plainly rather than smoothed over. Fixed by construction anyway, for uniformity: `DropdownMenu`'s root and `Menubar`'s own per-menu wrapper now get the identical `use_outside_dismiss` construction `ContextMenu`'s root already had (a new `root_id` on each), plus a new two-id variant (`menu_sub::use_sub_outside_dismiss`, since a `Sub`'s trigger and content are two siblings, never one wrapped element) for the shared submenu level in both `DropdownMenu.Sub` and `ContextMenu.Sub`; every displaced `onblur` branch was removed rather than left as a second, still-fragile path to the same conclusion. The new `ContextMenu`/`ContextMenu.Sub` tests are documented in-file as construction-parity, not a reproduced defect. **`navigation_menu.rs` shares the identical underlying constraint** (its own module doc already cites the same `dioxus-html` 0.7.9 missing-`related_target` gap this fix cites) but already answers it with a different, correct construction of its own — a debounced close plus every element's own `onfocus` cancelling it, robust to an external `.focus()` call by construction — checked during this investigation and deliberately left untouched. Evidence: RED confirmed for `DropdownMenu` (plain item and sub-trigger) and `Menubar`, exact before/after `data-state`/DOM-count values in the commit body; full existing suites re-verified green (`dropdown-menu.spec.ts` 2/2+axe, `context-menu.spec.ts` 13/13, `menubar.spec.ts` 3/3+axe, `oracle/tier1-apg/menu-submenu.spec.ts` 16/16, `keyboard-matrix.spec.ts`+`menu-roles.spec.ts`+`focus-restore-reference.spec.ts` 87/88 with one pre-existing intentional skip); `cargo test --workspace` 433/0. **This row's own landing then introduced a regression, found and fixed the same round:** `3ba793b` gave `DropdownMenu`'s root `div` and `MenubarMenu`'s own wrapping `div` a literal `id: root_id.cloned()` (plus, on `MenubarMenu`, a literal `role:`) beside the unmerged `..props.attributes` spread already on that element, with a comment claiming a caller-supplied `id` "still wins (spread order)" — false: SSR emits both, a WHATWG duplicate-attribute parse error (`dev-docs/conformance-harness.md` hydration-parity Rule 4, extended). It shipped into the prerendered site as `docs/component/top_layer/index.html`'s `<div id="dxc-1091" ... id="clip-dropdown-menu-root" ...>`, caught by `playwright/oracle/hydration-parity.spec.ts`'s "Rule 4 (extended)" when the main loop ran it against a freshly regenerated site after round-4 integration. Fixed by `f2be1d7` (`fix(menu): dedupe the id/role duplicate 3ba793b introduced on DropdownMenu/Menubar roots`): both elements' full literal-attribute sets now route through `merge_attributes`, the same construction `context_menu.rs`'s own root already uses (`b35d671`). Two new Rust SSR tests (one per component) assert a caller's `id` renders exactly once — both proven RED on the pre-fix tree (2 `id="` occurrences, e.g. `<div id="dxc-0" ... id="my-menu-root">`) and GREEN after (1) — and the fix was re-verified end-to-end against the documented SSG recipe (`dx build --ssg --features fullstack --platform web`, no `--base-path`, served at `/` on :8090, `SSG_SITE_DIR` set): `oracle/hydration-parity.spec.ts` **11/11 green**, the fixture now carrying a single `id="clip-dropdown-menu-root"`. **Corrects this row's own evidence above:** the "full existing suites re-verified green" list this row cites (`dropdown-menu.spec.ts`, `menubar.spec.ts`, etc.) ran CSR-only against a live `dx serve` dev server and could never have caught this regardless of how thoroughly it was run — the browser DOM coalesces sequential duplicate `setAttribute` calls into one, so the second attribute is only ever visible in SSR/SSG's raw text output; the hydration-parity SSG lane is the only thing in the whole harness able to catch this class at all
