# Row 61: Sidebar toggle icon lived in its own strip below the main site navbar instead of inside it — LANDED…

## Item

**Sidebar toggle icon lived in its own strip below the main site navbar instead of inside it — LANDED 2026-09-17, user-reported.** `Navbar` (`main.rs`) was rendered in `NavigationLayout` as a sibling of, and *before*, `Outlet::<Route> {}` — never a descendant of `DocsLayout`'s `SidebarProvider`, which is what actually owns the `SidebarCtx` a `SidebarTrigger` needs (`use_sidebar()` panics without an ancestor provider). `DocsLayout` compensated by rendering its own separate `header { class: "dx-docs-inset-topbar", SidebarTrigger {} }` strip below the navbar — the bug. **Fixed by construction:** made `Navbar` an actual descendant of the `SidebarProvider` on every route that has one, via one defensive check (`try_consume_context::<SidebarCtx>().is_some()`) instead of two separate code paths — this single check subsumes the desktop nav row, the `in_iframe` chromeless nav row, `Demos` (no sidebar at all), and `ComponentDemo`'s "component not found" early-return branch (also bypasses `DocsLayout`, previously lost its navbar entirely once `NavigationLayout` stopped rendering one unconditionally — now gets the same trigger-less `Navbar {}` as `Demos`). **The CSS trap this ran into:** `SidebarProvider`'s own render is just `div { class: "dx-sidebar-wrapper", {children} }`, and the base `.dx-sidebar-wrapper` rule (`sidebar/style.css`) is `display: flex` — a ROW sized for exactly two children, `Sidebar` + `SidebarInset`. Dropping `Navbar {}` in as a third child of that same row rendered it as a third flex item sitting beside them, not a full-width row stacked above. Fixed by grouping `Sidebar`+`SidebarInset` under one new wrapper, `.dx-docs-shell-body` (`main.css`), and making `.dx-sidebar-wrapper.dx-docs-shell` itself a `flex-direction: column` of exactly two children: `Navbar`, then that body row — the former outer-wrapper geometry (width/border/centering/the sidebar-row min-height) moved down onto `.dx-docs-shell-body`, since it's now the box that must match the navbar's own centered, content-width inner row. The base `@media (width >= 768px) { .dx-sidebar-wrapper:has([data-side="right"]) { flex-direction: row-reverse } }` rule (keyed on `:has()`, so it matches ANY `.dx-sidebar-wrapper` containing a right-sided sidebar anywhere inside it) would otherwise have reversed `Navbar` and the body row too, now that they share the same outer wrapper — cancelled at that level and reapplied one level down on `.dx-docs-shell-body`, where it correctly mirrors just the `Sidebar`/`SidebarInset` pair without moving `Navbar`. Neither of the *other* two `.dx-sidebar-wrapper` call sites (the block-demo iframe, the email-client dashboard) were touched — their selectors were left exactly as-is, only the docs-shell-specific ones were rescoped. **Verified by execution, independently re-checked by the orchestrating session, including tracking down a false alarm before landing:** `cargo check --workspace`/`cargo fmt --check` clean; `check-preview-composition.sh`/`check-dx-class-prefix.sh`/`check-css-literals.sh` all clean; `sidebar.spec.ts`/`navbar.spec.ts`/`preview.spec.ts`/`oracle/tier2-html/top-layer.spec.ts`/`oracle/tier3-radix/scroll-lock.spec.ts` re-run — the two `top-layer.spec.ts` "flip above bottom-edge trigger" failures reproduced identically against the unmodified baseline (`git stash`), confirming them pre-existing and unrelated (the real docs sidebar, dogfooded onto the `top_layer` oracle fixture page by row 56, intercepting a hover at that specific fixture layout — not caused by this change); a `navbar.spec.ts` "keyboard navigation" failure seen only when all five specs ran together turned out to be parallel-worker contention, not a real regression (passed cleanly alone and in smaller batches). **The false alarm, disclosed rather than silently discarded:** independently measuring the homepage's Sidebar gallery card after this fix initially showed its "Right"/"Left" controls rendered ~1250px off-screen and `.dx-sidebar-wrapper.dx-docs-shell`'s computed `flex-direction` reading `row` instead of `column` — looked exactly like a real regression (the same class of Flexbox/masonry-interaction bug row 58 already fixed once). Root-caused instead to this session's own `dx serve` dev-instance serving a stale cached CSS bundle that was missing the new rule entirely, confirmed by rebuilding via the production `dx build --ssg` recipe (`scripts/deploy-preview.sh`) and re-measuring against that: `flex-direction: column`, card at `x: 77.5` (matches baseline's `x: 76.5`), `Right` click correctly flips `data-side`, no console errors — this class of dev-server staleness is a known, already-documented `dx` tooling quirk (row 58's SSG cache-warm race is the closest precedent), not a new construction to add here
