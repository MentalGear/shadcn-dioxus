Differences from the bench, all approved: axis gating (vertical page scroll over a horizontal carousel never draws a band), notched wheels release after 140ms of silence, vertical orientation and RTL, no band on the seamless virtual loop or under reduced motion, telemetry only behind `localStorage["dx-carousel-debug"]="1"`. Verified by 21 rewritten tests in `carousel.spec.ts` (13 fail on B3) and replays of 9 of the owner's real recorded bursts plus 2 synthetic ones (`playwright/carousel-wheel-replay.spec.ts`; the same recordings also pass against the bench's own D). **Open:** Safari (and possibly Firefox on some platforms) may bounce a scroll container that is at rest at its edge, stacking with D's band (double bounce); needs a real-device check (see the carousel's docs.md). The pointer-drag rubber-band is unchanged. **2026-09-26 (owner re-evaluating):** see row 96's matching addendum — approach E ("native room", benched in `dev-docs/research/carousel-overscroll-bench.html`, whose live artifact is newer than the committed write-up) is under consideration to replace this row's own B3 mechanism, per the owner's "feels right"; a clip fix for E is being chosen, and row 112 now depends on this decision. **Design closed; implementation LANDED 2026-09-25 (below), later superseded by mode D.** Full write-up in [`dev-docs/research/carousel-overscroll-2026-09-23.md`](../../research/carousel-overscroll-2026-09-23.md), with the bench checked in beside it. Root cause of every glitch across ~20 bench revisions is ONE thing: during a wheel/trackpad gesture the scroll position has **three would-be writers** — the compositor's momentum animation (where `preventDefault` is only advisory), the snap engine on its own schedule, and our code — and two of the three are neither observable nor sequenceable from JS. The negative evidence is decisive: the *mouse-drag* path stayed clean for 20+ revisions untouched, because a mouse drag has no native scrolling and our code is then the only writer. **THE RULE:** where the browser is already the scroller, never write the scroll position and never disable snapping — express the overdrag as a transform only; where there is no native scrolling, owning it is safe. Nuance for the port: the contest exists only while momentum is live, so a spring-back ease may own the offset once a burst is spent — detecting that end accurately is the remaining difficulty. **B3 is the choice and the reason is arithmetic, not taste:** B2 (damped margin) cannot resist, because damping means slowing the scroller, which means owning its position, which is exactly the fight the rule removes — with the fight gone its room fills 1:1 with raw travel, measured as a 25px/event gesture consuming the whole 260px room while 145 and 121px/event gestures at the other edge produced 3px and 0px. B3 has no wall: depth is bounded by the platform curve's asymptote (`L = track width / 0.55` = 582px on a 320px track) instead of by a `padding` value. Mode C felt closest to native and is subsumed by B3 — same mechanism on the track rather than the root, which is what dissolves C's z-index problem. Eight binding port invariants are listed in the research doc §6, each one the generalisation of a named bench regression (never `scrollLeft`; edge test synchronous from layout gaps; no smooth `scrollIntoView` for spring-back; never restart a spring-back in flight; no spacer children; suspend `scroll-snap-type` once per gesture; never change measurement and timing in the same revision; no pixel threshold below the device quantum). **LANDED 2026-09-25 (round 8):** ported as mode B3, per the rule above. The pointer-drag path keeps owning `scrollBy` (there is no native scrolling to contest there: it requests the full delta and treats any refusal as overdrag). A new, separate wheel/trackpad bridge, `use_carousel_wheel_bounce`, never calls `scrollBy`/`scrollLeft`/`scrollTop`/`preventDefault`/touches `scroll-snap-type` — edge detection is synchronous from `getBoundingClientRect` gaps, and overdrag is expressed only as a transform on `CarouselContent` itself (not the root — this is what dissolves mode C's z-index problem, per the research doc). Both paths write `style.transform` via `eval` outside the vdom, so hydration parity is unaffected; `prefers-reduced-motion` disables the bounce entirely; invariant 4 is enforced via a token counter (`bounceToken`) rather than the bench's own boolean flag. Tests were written red-first: 7 of 8 new tests failed on the pre-port code; after the port, `playwright/carousel.spec.ts` is 65/65 and the tier-1 APG oracle is 11/11. **Test-methodology finding worth keeping on record:** `page.mouse.wheel(0, deltaY)` does not scroll a horizontal scroller in headless Chromium at all — `deltaX` does; a test asserting wheel-driven behaviour on a horizontal carousel needs the X axis regardless of how a real trackpad gesture would be expressed. **Open, stated plainly, not silently dropped [2026-10-05: the feel-test happened for mode D -- the owner benched D and E on real hardware and chose D -- so only the Safari double-bounce real-device check from the first note stays open]:** the owner still needed to feel-test this on real hardware (mouse and trackpad, both axes, both edges) — synthetic wheel events cannot reproduce momentum, so this is not something Playwright can close out; the cross-browser rubber-band constant used is WebKit's own curve (row 103's measurement), unverified against Chromium's or Gecko's actual constants; arrow-paging while a bounce is already in flight is unexercised by any test; and there is no extra clipping wrapper around `CarouselContent` (it self-clips), which still wants a real-device visual check. **ADDENDUM 2026-09-25 (lane `carousel-rb-clip`), both flagged risks above materialized on the owner's real hardware, exactly as this row's own "still wants a real-device check"/"unverified against Chromium's or Gecko's" language warned they might.** (1) The "no extra clipping wrapper — `CarouselContent` self-clips" claim was wrong: an element's `overflow` clips relative to its OWN box, and a `transform` moves that box (clip region included) as one unit, so translating the scroller moved its clip boundary right along with it — a trackpad overdrag pushed the whole visible slide track ~750px past the carousel, unclipped, overlapping the rest of the page. Fixed by giving `CarouselContent` a stationary, presentational `div[data-slot="carousel-viewport"]` wrapper (`overflow: clip`, inline in the primitive itself, not `hidden` — a `hidden` box is still a scroll container, which would make the paging path's `scrollIntoView` scroll the wrapper too and permanently offset the content); both bridges now translate the scroller inside a clip boundary that never moves. (2) The port's own wheel-path curve constant was mis-transcribed: `L·x/(x+L)` with `L=d/c` is NOT algebraically identical to Apple's `x·c·d/(d+c·x)` as this row's own §4 source table claimed — they differ by a factor of `c` throughout (slope 1 vs `c` at `x=0`; asymptote `d/c`≈1.8·`d` vs `d`), so the shipped curve was roughly twice as sensitive and reached roughly twice the depth of the curve it was meant to port. Fixed in `CAROUSEL_WHEEL_BOUNCE_JS` only (`CAROUSEL_DRAG_JS`'s pointer-drag curve is untouched — the owner's report was trackpad-specific, and "mouse drag feels natural" as shipped). Both fixes and the corrected algebra are recorded in `dev-docs/research/carousel-overscroll-2026-09-23.md` §9's own dated entries. A separate, still-open concern from the same report — trackpad momentum overshoot needing damping beyond the curve fix — is deliberately NOT part of this addendum; the owner is deciding between that heuristic and a different construction, so it is being tracked and implemented separately rather than bundled in here.
