## Detail

Investigated 2026-09-01: hook-side settle-loop bug fixed, scroll-at-open quirk worked around test-side; this residue looks like a browser-build engine bug, deliberately not papered over. **2026-09-03 addendum:** the same failure shape (a `toBeCloseTo` position mismatch after CSS-native anchor tracking) now also reproduces on `date-picker.spec.ts`'s two anchoring tests in this sandbox, confirmed pre-existing and unrelated to the row 34 axe-coverage round (reproduces identically against `git stash`-ed, unmodified `HEAD`) — this is the same engine-level class, not a new, separate defect, and not something the axe round touched. **2026-09-04 addendum, re-measured with a working Playwright container for the first time:** date-picker's two anchoring tests and `top-layer.spec.ts`'s two Rule 8 scroll-tracking tests failed **100% (0/23 across reruns)**, up from the ~40% previously recorded here, all with the same "frozen after scroll" signature (content offset drifts by exactly the scroll delta). Chrome build 148.0.7778.96 (headless shell). None of `top_layer.rs`/`date_picker.rs`/`calendar.rs` were touched this session, so this is not self-inflicted. One of the four failing tests is the **JS fallback** path specifically (`use_anchor_position_fallback`, `top-layer.spec.ts:814`), which is this repo's own code rather than native `anchor()` — its participation in the identical failure signature deserves a separate look at whether it is a distinct bug in that hook's own scroll listener, rather than simply inherited bad initial state from the native-anchor case. Also measured, for the date-picker case specifically, a separate/narrower observation (not a competing explanation for the scroll-tracking failure above): the content is 278px tall while only ~275px of room exists below the trigger at the 720px-tall default viewport, so a native `flip-block` fires 3px short of fitting; at a 1000px-tall viewport the same content places correctly below with an 8px gap. **2026-09-19 addendum (batch 2 integration, row 82):** both of `date-picker.spec.ts`'s anchoring tests are now named explicitly, closing the ambiguity row 82's own docs-pass notes flagged — this row's class covers "anchors the popup next to its trigger, not viewport-centered or offset" (the one already tracked here since 2026-09-03) and "offset to trigger is unchanged after scrolling (CSS anchor tracks scroll natively)" (seen failing in one full-suite run and absent in another, consistent with this row's own load-timing correlation rather than a new, separate defect). **2026-09-19 addendum (batch 3, date-picker lane, re-measured with more precision):** content 278px vs. 275.03px of room below the trigger (2.97px short, not just "~275px" as recorded above) — the native `flip-block` fallback consequently places the popover ABOVE the trigger (measured `contentTop` 138.97 vs. `triggerBottom` 444.97), which is the exact, now-confirmed mechanism behind "anchors the popup below" failing; the scroll-tracking test's own jump was remeasured at 314px. Not independently re-investigated further this round, per this row's own standing instruction not to paper over a browser-engine-level residue **2026-10-05 (round 3, FINAL VERIFICATION) -- THE ENGINE DIAGNOSIS ABOVE IS WITHDRAWN for both cases, kept only as history:** `top-layer.spec.ts` Rule 8 (ColorPicker) and `date-picker.spec.ts` `:73`/`:144` were never an engine bug or a frozen anchor. They were test geometry plus a selector bug: the panels do not fit below their trigger at the default 1280x720 viewport (date picker 278 px tall against 274 px of room below a trigger at y=446; ColorPicker 386 px tall under a trigger at y~453), so `flip-block` correctly opens them ABOVE the trigger, and a 150 px scroll frees room and flips them back, which read as "frozen / drifted" (the 314 px and 436 px jumps recorded above are the flip, not a tracking failure); and, since the header theme picker landed (`b9b8e1f7`), `document.querySelector('[style*="anchor-name"]')` matched that header button first, so the tests measured the wrong trigger. Fixed in the specs (a taller viewport, a precondition assert, the real locators; row 172 has the account), and `top-layer.spec.ts` Rule 8 (ColorPicker) now PASSES, so it is no longer red and round 3's earlier "still red, pre-existing" note is superseded. The JS-fallback case (`top-layer.spec.ts:814`) was not among the final release run's failures. Nothing here needs a different machine or an upstream fix.
