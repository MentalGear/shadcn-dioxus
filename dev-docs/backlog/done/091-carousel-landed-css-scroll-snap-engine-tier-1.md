The construction: both call sites replaced with a new `CAROUSEL_SCROLL_TO_JS`/inline `endDrag` helper that computes the physical `getBoundingClientRect()` delta between the target slide and the carousel's own scroller and calls `scroller.scrollBy({ left top: delta })` directly on the scroller — `scrollBy`, unlike `scrollIntoView`, only ever writes the element it is called on, so there is no ancestor for it to reach; RTL stays sign-flip-free (invariant 1, `dev-docs/archive/research/carousel-overscroll-2026-09-23.md` §6) since the delta is physical either way. Two latent bugs surfaced and fixed by execution while building this, neither present in the `scrollIntoView` original: (a) `scrollBy({ behavior: 'smooth' })` on a `scroll-snap-type: mandatory` container truncates a multi-slide jump at the first intervening snap point (measured: a bare 672px request landed at 336px) — fixed by suspending `scroll-snap-type` for the scroll's duration and restoring it on `scrollend`/a timeout fallback, the same construction `CAROUSEL_DRAG_JS`'s own release settle already used, with the pending-restore handoff stashed on the scroller element (`__dxCancelSnapRestore`) since independent `document::eval` calls share no closure; (b) that same suspend/restore, applied naively, fired mid-drag too (`use_carousel_scroll_tracking` reports a changing `selected` continuously while dragging) and re-enabled mandatory snapping before the gesture ended, sending drags flying 2 slide-pitches past the release point — fixed by skipping the discrete-paging bridge entirely while the scroller carries `data-dragging`, deferring to the drag's own release settle. `primitives/src/carousel.rs`'s own `CAROUSEL_SCROLL_TO_JS` doc comment has the full account and the live measurements.
