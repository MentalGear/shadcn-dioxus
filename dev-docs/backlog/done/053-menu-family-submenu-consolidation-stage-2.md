## Item

**Menu-family submenu consolidation, stage 2 — LANDED 2026-09-14, verified by execution.** Following stage 1 (row 52), the earlier assessment of whether `DropdownMenu`/`ContextMenu`/`Menubar` should share more plumbing concluded **extract three narrow bands, not a whole shared component** — that scope is what actually got built, in a new module `primitives/src/menu_root.rs` (registered via one `mod menu_root;` line in `lib.rs`), the same "identical plumbing here, host-private everything else" shape `primitives/src/menu_sub.rs` (row 54) already established as this crate's precedent. **The construction, band by band:** (1) `use_open_focus_sync` — the "open-index container": the effect that resyncs a menu's own `open` boolean from whether its roving-focus collection currently holds DOM focus (gated on no descendant submenu being open) was **byte-identical, word for word**, between `DropdownMenu`'s and `ContextMenu`'s root components before this change — now one shared function, called from both. **Deliberately not extended to `Menubar`**: that host's analogous effect resyncs a *which-index-is-open* signal (`Signal<Option<usize>>`), not a plain boolean, and has no `submenu_open_count` concept at all (`Menubar` doesn't support `DropdownMenuSub`-style nested submenus) — forcing the two shapes into one generic function would either lose the index `Menubar` needs or invent a translation layer with no existing duplication to justify it, so `Menubar`'s own version stays exactly where it was. (2) `use_menu_content_lifecycle` — the "content lifecycle/positioning pipeline": id resolution (`use_unique_id` + `use_id_or`, honoring a caller-overridden id) plus `use_animated_open`'s open/close-hold render gate, identical across all three hosts' `*Content` components — now one shared call in each, returning `(id, render)`. The *positioning* half of the name stays host-private, for the identical reason `menu_sub.rs`'s own doc gives for its own submenu content: `top_layer.rs` hard-codes a fixed list of `dx-anchor-*` marker classes, so the actual `use_anchor_position_fallback`/`use_point_anchor_clamp` call still has to live in each file's own `#[cfg(feature = "web")]` leaf render function — this band only factors the lifecycle gate that runs *before* that call. (3) `content_labelledby_attributes` — the "trigger id-plumbing": the APG-required accessible-name-from-trigger-id block (row 25) was duplicated across all six `*ContentRendered` web/native arm pairs (three hosts × two arms) — now one shared function called from all six. **What stayed host-private, exactly as the original assessment said it should:** the keyboard state machine (`MenubarMenu` still concentrates its whole contract in one handler; `Navbar` still splits it three ways) and the item components (`NavbarItem`'s routing-aware `Link` vs. `MenubarItem`'s plain `div`) — neither was touched, and `Navbar` itself was **not** made a consumer of `menu_root` at all, matching the original scoping to `DropdownMenu`/`ContextMenu`/`Menubar` only. `menu_sub.rs` was read for precedent and left untouched, per this row's own file-ownership rule — its nested-submenu state machine shares no code with this extraction (different level of nesting, already its own module). **The Escape-refocus divergence, investigated and root-caused, not left open:** `Menubar` explicitly refocuses its trigger on Escape; `Navbar`'s Escape handler did not. Root-caused as a **genuine oversight, not a deliberate hover-model exemption** — `Navbar` fully supports keyboard-driven opening (`NavbarNav`'s ArrowDown/ArrowUp move focus into the open content exactly the way `MenubarMenu`'s do), so a keyboard user who arrows into an open nav and presses Escape faces exactly the same "where does focus go" question Menubar already answers, and no test asserted either behavior before this fix. Fixed in `Navbar`'s own `onkeydown` (host-agnostic, not gated behind `#[cfg(feature = "web")]`, so it applies to both arms): read the open index before clearing it, then re-focus that trigger through the collection, mirroring `MenubarMenu`'s own "clear then set to force a real transition" construction exactly. **A genuine surprise found during verification, worth recording:** on this sandbox's Chromium, the new red-first test for this fix (see below) passed even with the fix *reverted* — root-caused, not just observed: `NavbarContent` (like `MenubarContent`) renders via `popover="auto"`, and the WHATWG Popover API's own "focus fixup" behavior already restores focus to the element that was focused before the popover opened whenever it closes (native light dismiss *or* a scripted `hidePopover()` call), which for `Navbar` happens to be the trigger itself in every case this bug could occur. So on the **web arm**, this specific defect was already invisible to Chromium's native popover behavior, independent of this fix. The fix is still real and still needed: it is not gated to the web arm (unlike `use_anchor_position_fallback`-style code), so it is the only thing providing this contract on the **native (Blitz) arm**, which has no Popover API and thus no such platform behavior — the same reason `MenubarMenu` doesn't rely on the platform either, and does the refocus explicitly itself. This could not be verified on Blitz in this sandbox (no such test harness exists here); the finding is disclosed rather than presented as a red→green proof on the engine actually exercised. **Red-first verification (per `dev-docs/plan.md`'s definition of done):** (a) For the three shared bands themselves: rather than inventing redundant coverage, existing specs already exercise all three hosts' open/close and positioning behavior end to end — `playwright/dropdown-menu.spec.ts`, `playwright/context-menu.spec.ts` (including its "touch tap outside closes the open menu" case, which exercises band 1's exact codepath), `playwright/menubar.spec.ts`, and the full `keyboard-matrix.spec.ts` open/close rows for all three hosts — all of which stayed green through the refactor, proving the extraction preserved behavior. The one genuinely new piece of coverage this row adds for bands 2/3 is the "trigger id-plumbing" band's `aria-labelledby` value, previously asserted only for `DropdownMenu` (`menu-roles.spec.ts`) — **new assertions added for `ContextMenu` and `Menubar`** (mirroring `DropdownMenu`'s existing one), which would catch a future drift between the three hosts' now-shared `content_labelledby_attributes` call. (b) For the Escape-refocus fix: a new `keyboard-matrix.spec.ts` case, `NavbarNav — Escape`, graded against `MenubarMenu`'s identical contract — confirmed it passes with the fix in place; per the finding above, it does not distinguish fixed-from-reverted on this sandbox's Chromium (both pass, for the platform-behavior reason described), so it is disclosed as a regression guard and a stated contract, not a red→green proof on this engine. **Verified by actual execution (Chromium, this sandbox), 2026-09-14:** `cargo check --workspace` and `cargo check --workspace --features web -p dioxus-primitives` both clean (only the two pre-existing, unrelated `preview` warnings present on `main`); `cargo fmt --check` clean; `cargo clippy --workspace --tests --examples -- -D warnings` fails exactly as this task's own brief predicted — 5 pre-existing `doc_lazy_continuation` errors in `menu_sub.rs` (a file this row did not touch), and **zero** new warnings or errors anywhere else, confirmed by grepping the full clippy output for every touched file. `npx playwright test --project=chromium oracle/tier1-apg/keyboard-matrix.spec.ts oracle/tier1-apg/menu-roles.spec.ts dropdown-menu.spec.ts context-menu.spec.ts menubar.spec.ts navbar.spec.ts` (97 tests, Chromium only, `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` already matching this repo's pinned Playwright 1.60.0/chromium-1223): **96 passed, 1 skipped (a pre-existing, unrelated `test.skip` in the Accordion section), 0 failed.** Firefox/WebKit not attempted (disallowed in this sandbox, per row 4)
