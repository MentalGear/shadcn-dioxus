# Row 10: Phase 5 — collision detection

## Item

**Phase 5** — collision detection

## Status / trigger

**5.1 REFRAMED by the 2026-09-01 bits-ui/Radix source comparison, FLIP sub-problem landed same day, PR #17**: both delegate to Floating UI (identical flip/shift/size/arrow/hide pipelines; bits-ui is a line-for-line Svelte port of Radix's Popper). Since CSS Anchor Positioning is now in our stack, `position-try-fallbacks: flip-block, flip-inline` covers the FLIP sub-problem natively (Chrome/Edge 125+, FF 147+, Safari 26+), zero JS, additive to the existing @supports blocks — landed, and `use_anchor_position_fallback` makes the same flip decision from viewport math on engines without native support. **2026-09-03: the JS-fallback path's first piece of shift also landed** (user device report — the home page widget-masonry `ColorPicker` clipping against a small screen's edge; `top-layer.spec.ts` Rule 12): `use_anchor_position_fallback` now clamps `target.left` into the viewport with a small edge margin, on top of the existing flip decision, closing the gap for `side="top"`/`"bottom"` placements (whose horizontal position comes from `align` alone and was never checked against the viewport on *either* engine before this). **2026-09-04: the vertical shift and size clamp landed too**, in `use_anchor_position_fallback` — new **Rule 15** in `top-layer.spec.ts`, passing. Two pieces, the exact mirror of the horizontal fix: (1) a `side="left"`/`"right"` placement's *vertical* position — like a `side="top"`/`"bottom"` placement's horizontal one — came only from `align` and was never checked against the viewport, clamped into `[EDGE_MARGIN, vh - EDGE_MARGIN - ch]` the same way; (2) when the content's natural height exceeds `vh - 2*EDGE_MARGIN`, an inline `max-height`/`overflow-y: auto` is set (and `box-sizing: border-box` forced alongside it, since `offsetHeight` is always border-box but `max-height` is defined relative to whatever `box-sizing` the element carries — under `content-box`, padding/border would silently under-clamp), cleared again once no longer needed. Deliberately **not** mirrored into the CSS `@supports` contract, and the reasoning is worth keeping on record: `position-try-fallbacks` has no shift primitive and no shipped primitive shrinks an anchor box to fit, so a conforming engine has the identical latent gap — this is not Firefox/WebKit-specific, it is a real gap in the standard as shipped today. The size clamp uses an inline style rather than the width contract's `--dx-anchor-width` custom-property approach (row 47) specifically because a zero-specificity `:where()` rule can never beat a component's own `overflow: visible` (`select/style.css`'s own comment: "never scrolls ... collision-aware ... positioning belongs upstream" — this clamp is that upstream). **2026-09-14: 5.2, `ContextMenu`'s point-anchor clamp, has now landed too — the one piece of this row that was left deliberately open.** `ContextMenu` opens at a raw click/long-press point (`ContextMenuCtx::position`, set by `ContextMenuTrigger`'s mouse `contextmenu` handler and its manual touch/pen long-press timer) with no anchor element at all — `use_anchor_position_fallback` above cannot cover it regardless of engine, not because of a Firefox/WebKit gap but because that function is keyed on resolving an anchor element via `document.querySelector('[style*="anchor-name: ..."]')`, and `ContextMenuContentRendered` never wires up an `anchor-name` for this content in the first place (see that component's own doc, the `manual`-vs-`auto` section, for why: there is no persistent trigger to key positioning off of). Closed by a **new, parallel construction** in `top_layer.rs`, `use_point_anchor_clamp` — not a branch threaded through `use_anchor_position_fallback` itself: that function's script is already long, heavily cross-referenced, and execution-verified around anchor-relative `place()`/`matches()`/flip machinery this case has no use for, so adding a no-anchor special case there was judged a real risk to its own passing oracle coverage (rules 5-7, 9, 11-15) for a case that shares only the final clamp *arithmetic*. The new hook reuses exactly that arithmetic — the same `EDGE_MARGIN` (4px) convention, the same `Math.max` viewport-too-small-to-fit-at-all fallback, the same `border-box`-forced max-height/`overflow-y: auto` clamp `use_anchor_position_fallback`'s own 2026-09-04 vertical-shift-and-size-clamp addendum above describes — against the raw `(x, y)` point directly instead of an anchor rect, measuring `ContextMenuContentRendered`'s own rendered size once it's promoted to the top layer (called right after `use_popover_sync` in that component, the same ordering requirement `use_anchor_position_fallback` documents for its own call sites). No scroll/resize tracking and no multi-frame settle loop, unlike `use_anchor_position_fallback`: `ContextMenuContent`'s items are ordinary synchronously-rendered children, not `DatePickerPopover`'s asynchronously-growing calendar grid, and the menu already suppresses page scroll while open (its own pre-existing wheel/touchmove effect) rather than following it. `menu_sub.rs`'s `ContextMenuSub`/`ContextMenuSubTrigger`/`ContextMenuSubContent` were checked and confirmed **not** to share this bug: a submenu anchors to its own `ContextMenuSubTrigger` (an ordinary menu item sitting inside the already-positioned root content), the same anchor-relative shape `DropdownMenuSub` uses, so it already goes through `use_anchor_position_fallback` like every other anchored overlay — untouched by this fix. Regression oracle: two new `playwright/context-menu.spec.ts` cases ("clamps the menu into the viewport for a mouse right-click near a corner" / "... for a touch long-press near a corner"), covering both of `ContextMenuTrigger`'s `position.set(...)` call sites — not `top-layer.spec.ts`, whose own header doc explicitly disclaims this exact case (Migration A slice 2/3's note: "Phase 5.2's point-anchor case is explicitly out of scope for this file"). **Verified by actual execution (Chromium, this sandbox), 2026-09-14:** `cargo check --workspace` and `cargo fmt --check` clean (no new warnings beyond the two pre-existing, unrelated ones already on `main`); `cargo clippy` raises no new warnings anywhere outside the confirmed pre-existing, unrelated `menu_sub.rs` doc-lint failures (present unchanged on `main` at `124c4d5`). The two new cases pass. **A third case regressed and was root-caused, not just re-run until green:** the pre-existing `menu lands at the tap coordinates on touch long-press` case started failing after this fix landed (menu Y off by ~187px) — verified by a direct baseline comparison (same test, same browser, run against `124c4d5` before this fix: passes) that this was a real, reproducible difference correlated with the fix, not a flake. Root cause, confirmed by instrumented execution: **not a bug in `use_point_anchor_clamp`.** The test's own premise (push the trigger down with `padding-top: 300px` on `<main>` so the tap point sits "away from any edge") had gone stale — on this component's current preview-page chrome, that padding places the trigger's center at `y ≈ 735` against a 720px-tall default viewport, 15px *past* the bottom edge, not away from it. That was already true on `124c4d5`, before `use_point_anchor_clamp` existed — nothing corrected it yet, so the unclamped menu simply rendered past the fold and the test's tap-coordinate assertion passed vacuously (it never checked on-screen visibility, only that the menu's top-left matched the tap point). `use_point_anchor_clamp` landing gave the clamp something to correct for the first time, and it correctly pulls the menu back on-screen (measured: `vh=720`, `tapY≈735`, content height `168`, for which `top + ch > vh - EDGE_MARGIN` is genuinely true) — a real, intended behavior change exposing a latent bad premise in the test, not a regression in the fix. Fixed by pinning the trigger to an explicit `position: fixed; top: 120px; left: 160px` instead of relying on ambient padding, making "nowhere near an edge" true by construction rather than by an increasingly-stale coincidence. **All 13 cases in `context-menu.spec.ts` pass together** after this correction. A firefox/webkit run has not been attempted. Still open in this row: only the acknowledged conforming-engine CSS gap described above (no CSS primitive exists for the point-anchor case either — a raw click point was never something `anchor()` could place, so there is nothing for a future `@supports` rule to cover here even in principle) **2026-10-20 sync: checked, nothing new landed since 2026-09-04; 5.3 CSS clamp still pending.** **2026-10-23: the collision-detection half of this row is closed; only the two adoptable ideas under Detail remain.** (1) The conforming-engine shift/size gap recorded above (no CSS shift or shrink-to-fit primitive, so an engine that resolves `anchor()` could leave a panel past the viewport edge) is already closed on `main` by row 210's exclusion-zone hand-off in `use_anchor_position_fallback`: a CSS-anchor placement that leaves the visual viewport or covers its anchor hands the call to the JS path, which shifts and clamps. It had no oracle of its own (Rules 12 and 15 run only under `stripAnchorSupportsBlock`), so `top-layer.spec.ts` **Rule 16** now runs the same fixtures with the engine's anchor positioning left in place: 4/4 green on `main` (Chromium, debug SSG of `bcb4a29`), and 3 of 4 red with the hand-off mutated off (`const outside = false && (...)`; Tooltip/Popover land at `left: -85px`/`-73px`, the 500px-filler Popover reaches `bottom: 806px` on a 400px viewport; HoverCard stays in bounds either way, a guard as in Rule 12), so the rule pins the hand-off rather than passing vacuously. (2) 5.3, the CSS clamp from `fix/preview-a11y-ux` (`429fa3a`, `max-width: calc(100vw - 2rem)` on the dropdown menu and select list), is on `main` already: both sheets carry its rule and comment (`dropdown_menu/style.css` as `calc(100vw - var(--dx-space-8))`), and Context Menu, Menubar, Hover Card and Navigation Menu carry the same cap, so nothing is left to port. A firefox/webkit run is still not possible here (only Chromium is installed).
