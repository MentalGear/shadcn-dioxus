# Row 154: Shared virtualization engine: ONE engine in primitives/src/virtual/ (core, strategy, DOM bridge) that every…

## Item

Shared virtualization engine: ONE engine in `primitives/src/virtual/` (core, strategy, DOM bridge) that every virtualized or windowed component consumes, rather than merging the components

## Status / trigger

**DESIGN NOTE** -- first note recorded 2026-10-05 from the owner question whether the virtualized components should share an implementation; the **owner's three-layer outline was added the same day**. Not scheduled: it waits for row 143 to land, and its first consumer is `message_scroller` (with row 146). No code change here. **Owner decision 2026-10-05: stays BACKLOG, with a REQUIRED first step: research the impact on Carousel before any migration (first paragraph of the notes)**

## Size

S (note); the build is not estimated

## Detail

**REQUIRED FIRST STEP (owner decision 2026-10-05): research the impact on Carousel before any migration onto the engine.** Carousel is not a plain windowed list. Besides the virtual loop it carries trackpad and wheel behaviour no other consumer has: `playwright/carousel-virtual-wheel.spec.ts` (and its sibling `carousel-wheel-replay.spec.ts`, which replays real MacBook trackpad recordings), the wheel/trackpad gesture handling in `primitives/src/carousel.rs`, and the virtual loop itself. In the source: a browser-idle gate (`CAROUSEL_SCROLL_TRACKING_JS`, `CAROUSEL_INPUT_QUIET_MS`) that counts every wheel event as input and treats `scrollend` as NOT idle while a trackpad still delivers momentum (~`:1112-1160`); trusted-wheel handling of the pinned state; the mode-D edge band and the `window.__dxCarouselWheel` trace flag; the virtual window's re-align deferred until input has gone quiet (~`:796-802`); and a carousel-owned bridge that registers `scroll`, `wheel`, `touchstart`, `touchend`, `pointerdown`, `keydown` and a `dx-carousel-rest` listener on the container (~`:1296-1304`), against the engine bridge's planned one scroll listener and one ResizeObserver. **The research must answer, in writing and in this row, whether the engine's DOM bridge (one passive scroll listener plus one ResizeObserver, scope-owned, a render-signal write only when the range changes) can host that behaviour, or whether Carousel stays a consumer of only the core `window()`.** It should: list each carousel input path (wheel, trackpad momentum, touch pan, drag, keyboard, `scrollend`) and say for each whether it is a scroll-bridge concern or a carousel-physics concern; check whether the engine's range-change write can be held until input is quiet (the carousel's window moves wait for idle, a list's do not) without a carousel-only branch inside the bridge; and run `carousel-virtual-wheel.spec.ts`, `carousel-wheel-replay.spec.ts` and the tier-1 carousel oracle against a throwaway prototype before any verdict. **Decision rule:** if hosting needs carousel-specific branches inside the bridge, Carousel stays on the core `window()` alone (as today), the consumer list below loses its Carousel entry, and the order below skips the Carousel step. No consumer migrates before this verdict is recorded. **Design note (owner outline, 2026-10-05).** **Today:** `primitives/src/virtual/` has `window()`, the `Virtualizer` and the new Fenwick `size_index.rs` (this round, uncommitted at time of writing); `VirtualList` uses all of it. Carousel uses only `virtual::window` for its virtual loop. `message_scroller` has its own JS anchoring; its content-visibility moves to the shared `virtual/cv_chunks.rs` this round. Select, Combobox and Command render every item. There is no 2D grid. **Proposal: one engine, three layers.** **(1) Core,** pure Rust, DOM-free, unit-tested: `SizeIndex` (estimates plus measurements, O(log n) offset <-> index), `window(offset, viewport, overscan)`, anchoring (keep an item's on-screen position when sizes above it change or items are prepended), and `scroll_to(index, align)`. One axis; a grid is two indices, which gives x/y virtualization. **(2) Strategy,** i.e. how out-of-window items exist: Windowed (a range plus spacers), ContentVisibility (all rendered, chunked cv), Auto (a threshold between the two). Later: Windowed + find-in-page (row 153: `hidden="until-found"` text stubs, with `beforematch` calling `scroll_to`). **(3) DOM bridge,** one `use_virtualizer` hook: a passive scroll listener, one ResizeObserver, scope-owned cleanup (the construction of row 159), and a render-signal write only when the range changes. **Consumers:** VirtualList (done), MessageScroller (a reverse list; stick-to-bottom is an anchor policy), Carousel (**only if the required Carousel research says so**; it keeps its own snap, drag and wheel/trackpad physics either way, and the loop would become a modular index map over the core), long Select, Combobox and Command lists, DataTable rows, and a future Grid. **By construction:** measurement, anchoring, listener hygiene and performance live in one place, so every consumer gets the Fenwick and cv-chunk wins, and a new consumer cannot reintroduce the jank and leak classes (rows 143, 149, 159). **Not covered:** carousel physics, drag-and-drop autoscroll and sticky headers. **Order:** the Carousel research first (nothing migrates before its verdict), then `message_scroller` (with row 146), then the Carousel's loop only if the verdict says the bridge can host it, then the list components when a long-list need appears. Row 153 (windowed find-in-page) stays a dependent row. **First note (2026-10-05, kept; its "do not merge the components" conclusion stands, the outline above says how the shared part is layered):** **What is already shared:** `primitives/src/virtual/` (`window()` in `window.rs`, `Virtualizer` in `virtualizer.rs`, `types.rs`, `utils.rs`). `VirtualList` uses the full engine (scroll offset, measured sizes with prefix sums, `get_virtual_items`). Carousel's `CarouselVirtualContent` uses only `crate::r#virtual::window` (pure index windowing with loop rotation, `carousel.rs:4655-4661`: `window(n, anchor(), anchor(), radius, loop_now)`, and `window(n, 0, n - 1, 0, false)` when not virtualized). `message_scroller` uses none: its stage 1 is `content-visibility: auto` (row 146). **Recommendation:** keep one engine and put the new capability there as engine-level features: the content-visibility mode helper and the quantized range signal (row 143), and the `until-found` search placeholders (row 153), so `VirtualList` and any later windowed consumer inherit them. **Do not merge the components:** their scroll models differ in kind (free scroll with variable heights and a measured size cache, versus snap pages with loop rotation and a fixed slide pitch, versus stick-to-bottom with follow-the-stream, prepend preservation and a jump button), so a single component would be a union of three state machines. **What this subsumes:** the duplicated windowing math (already one `window()`), and any second implementation of a content-visibility or find-in-page mode, which would otherwise be written once per component. **What it does not:** the per-component scroll handling and focus behaviour, which stay where they are. **2026-10-05 (round 3):** row 143 built the first engine pieces under `primitives/src/virtual/`: `cv_chunks.rs` (chunked content-visibility, shared with `message_scroller`) and `size_index.rs` (a Fenwick tree for item geometry, O(log N) measure and lookup), and row 159's `use_js_listeners` is the listener helper a bridge should use. Read them before outlining; the REQUIRED Carousel research is unchanged.
