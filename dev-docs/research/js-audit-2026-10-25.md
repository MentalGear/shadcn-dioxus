An upgrade to 0.8 unlocks one block fully (S9, `default_checked`, via the SSR fix in alpha.1), half of another (S11, `onbeforeinput`), and Blitz support for the (a) moves. It would cost more than the whole of step 2 (section 8).
- **Big risks:** anchor placement (T8, 499 lines, visible on every open), the virtual bridge (W1), the carousel (1,612 lines, concat!-built), toast heights (row 421), modal open/close (L1, L5), and the style-ordering invariant behind T1. None was measured here.
- **Recommended shape:** step 2 is 5 small lanes (about 26 agent-hours, one of them an experiment with a keep-JS exit); step 3 is 1 prerequisite plus 7 lanes in two batches (about 66 agent-hours). Details in sections 7 and 8.

**The structural consequence (I, from the rows above):** any block that reads layout and writes styles in one go, listens above the app root, needs the event target, or needs a listener option cannot be rewritten in Rust without changing behaviour. A Rust read is cheap on web but a Rust write is a signal write, so it paints a frame later; on desktop every read is also an IPC round trip.

## 5. Per-cluster plan for class (a)

Only the clusters that have (a) blocks. Every Rust version goes through `MountedData` handles kept in context or a `Signal<Option<Rc<MountedData>>>` filled by `onmounted` (the pattern `toggle.rs`, `slider.rs`, `collection.rs` already use).

**Styles (T1, T2, L12, O4; 460 lines, 350 CSS).** Replace each `ensure_*` eval with a component that renders `document::Style { id, "css" }` once, behind the existing `thread_local` flag so ten Popover users do not insert ten tags (`Style` dedupes by `href`, not `id`; V). Keep the CSS in `.css` files and `include_str!` it so the text is reviewable and stylelint can see it (I: stylelint scans `.css` files only). Not an `asset!` link: a `<link>` loads asynchronously and T8 measures right after open. **Risk is the ordering in `styles.rs:103-121`:** on web `create_style` runs from `queue_effect` (after the render), not inside the same script as `showPopover`; verify with `top-layer.spec`, `first-paint-styles`, `layout-stability` that no panel is measured before the sheet applies, or insert the tag from the same effect that opens. (I)

**Focus (L17, L18, L19, L20, S5, S6, V15; about 40 lines).** `MountedData::set_focus(true)` on stored handles. Three caveats, all V: `set_focus` has no `preventScroll` (L20 focuses a visible scroller, so harmless in practice; W7 needs it, so it stays JS); L17/L18 skip the refocus after touch/pen by reading `data-dx-modality` from `<html>`, so they need either a Rust `use_modality()` signal fed by the modality bridge or they stay JS; keyed rows that move are re-inserted, so a stored handle must be re-read after the render (V15, `onmounted` fires again). The four submenu-trigger focuses (L19) are the lowest-risk start.

**Scroll and measure (S2, S3, S4, S19, V6, W2).** S2: `onscroll` + `onresize` on the list (S2's `window` resize listener is not needed because the list resizes with the popup). S3: `get_scroll_offset` then `scroll(.., Instant)` per tick (web: synchronous; desktop: two IPC calls per 16 ms tick, so measure there). S4: `get_client_rect` of option and list plus `get_scroll_offset`/`scroll`; replace the `matches(':hover')` guard with the option's own pointer-over flag; the 10-frame retry becomes `crate::sleep(16ms)` ticks. S19: the indicator's two custom properties from `get_client_rect` of the item and its list, direction from `use_direction`. W2: `scroll(PixelsVector2D{x,y}, Instant)` always sets BOTH axes, so pass the untouched axis from `get_scroll_offset` and the RTL sign from `use_direction`. All I.

**Toast (O2).** Pause from `onpointerenter/leave` (`pointer_type() != touch`) and `onfocusin/out` on the region; `FocusData` has no `relatedTarget`, so a focus move inside the region fires out then in, which must be debounced by a tick or the countdown flickers. (I)

**Virtual engine (W1, W2).** The one contested move. `onscroll` (ScrollData has everything the report needs), `onresize`, `crate::sleep` or `onscrollend` for the 600 ms flag, `scroll` for the corrections. Blockers: the cap by `window.innerWidth/innerHeight` (no API; use a viewport probe element with `onresize`), and the comment in the JS that the scroll report is 'sent at once, no rAF batching, so Rust sees it before the next render', which a Rust handler satisfies on web (the handler IS that tick) but not necessarily on desktop. Web is plausible, desktop unknown. **Do it as an experiment with a keep-JS exit:** same engine, new bridge behind a cfg or a prop, compare `main-thread` and `scroll-main-thread` long tasks and `virtual-engine` on a release build before deleting the JS. W3, W5, W7 (selector-found, possibly unmounted targets, rAF settle loops) stay JS.

**Carousel.** Only L20 (two root focuses). C2-C5 stay: `scrollBy` by delta with `scroll-snap-type` suspended for the write and restored on `scrollend`, window `pointermove`, passive wheel, rAF band animation; `MountedData::scroll` is absolute and cannot suspend snapping atomically.

**Preview (V15, V16).** V16: seven demos use `eval("await new Promise(setTimeout)")` as a sleep; `crate::sleep` is a private `mod sleep` (`primitives/src/lib.rs:85`), so a one-line `pub mod sleep` (or `pub use`) is the prerequisite. V15 as in Focus.
