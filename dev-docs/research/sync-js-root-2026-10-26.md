## Executive summary (for the owner)

**The question.** The earlier plan kept two kinds of JavaScript as bespoke modules, because the bridge to Rust is asynchronous. The first kind is a decision made inside an event, such as "cancel this wheel". The second is a measure-then-place step that must finish within one frame, such as popup placement. You asked whether that is really true, or whether those two can also be bridged or abstracted.

**The root, in one sentence.** The browser takes its irreversible decisions at fixed points: the end of event dispatch (the default action), gesture start, input routing, the paint after layout, and the compositor frame. A value can affect one of them only if it is computed on the page's own thread before that point, from data that is already there. Everything else follows from this.

**What that means for Dioxus (verified in the 0.7.9 sources; web-verified, desktop inferred).**
- Dioxus's own event handlers already run synchronously, on web *and* on desktop/mobile. On desktop the webview blocks on a synchronous request to Rust for every event. So `prevent_default()` in a Rust handler works on both, and 133 handlers in this repo rely on that. `stop_propagation()` reaches the DOM on neither.
- What is **not** synchronous is the bridge. Messages from JS to Rust go over `dioxus.send`, and Rust's replies go back the same way. On desktop and mobile that crosses to another process, and edits reach the webview only in a rAF. On web it only queues microtasks: these happen to finish before paint, but nothing guarantees it, so nothing should be built on it.
- So the real rule is not "async can't work". It is this: **never ask Rust at the moment of commit. Publish what the decision needs before the event, and decide locally.**

**Four constructions, applied per decision in this order (section 5.1).**
1. **Delete what is dead.** About 16 eval sites sit in `#[cfg(not(feature = "web"))]` arms that every supported build compiles only for Blitz, where `document::eval` is a no-op. They include the whole focus trap and its only TypeScript file. Label's double-click script is shadowed by the shipped CSS but is the unstyled primitive's contract (`label-double-click.spec.ts`), so it stays as a behaviour.
2. **(A) Let the browser decide.** CSS anchor positioning has been in all three engines since January 2026 (Chrome 125, Firefox 147, Safari 26), and `overflow-anchor` since September 2026. Baseline dates each engine's first release, and those releases carry placement bugs, so A is used **behind per-feature floors and a boot probe**; an engine that fails the probe is a fallback engine. A never carries a correctness claim alone: it keeps a Rust invariant or a Rust "verify the outcome" step behind it.
3. **(B) A placement rule indexed by deadline and kind, and a closed registry of named behaviours.** Each decision is classified by what a late answer costs (this event's default action, this event's task, the paint, the next frame, nothing), then by kind: a *listener* reacts to events, a *command* mirrors Rust state into the page.
   - A decision whose only commit-time effect is `prevent_default`, on an event and fields Dioxus delivers, is an rsx handler (and the serialized event stays small: Android drops a payload event over about 12 KB, so submit, input, change, paste and drop are not rsx-cancel candidates on mobile).
   - A decision with a commit-sensitive effect Rust cannot take in time is one named, typed behaviour: `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`, `settle`, `openFocus`, `stickToEnd`, `reconcile` (which leaves the registry if its witness is green), and `scrollStep` and `roving` only if their witness is red. **Admission is derived from the placement table, per effect: the counterfactual witness red, or, only where no probe in the available engines can observe the commit point, a cited platform rule row** (browser-chrome defaults such as F6 and Ctrl/Cmd+B, and engine rules such as WebKit's clipboard gesture rule, each with a W citation, the engine, a manual check line and an owner-approved grant row). For each effect a behaviour has at each Rust construction site, the adapter's witness mode moves only that effect to its next-best placement (dropped, installed in the bubble phase at the element, delayed by R's modelled latency, or reordered after the next vdom event or a native transition), and a library commit-point probe must go red: it reads a state that the real arm never paints (never a latency number, a spec-authored assertion or an author-written predicate), and a control arm must stay silent. Structural detection is the inventory, not a ground: a per-site effect typestate, a per-kind `Decision<E>` type, behaviour modules compiled without the DOM library and an adapter that refuses an undeclared effect per install keep the code's effects inside the declared set. Witnesses are expected-failure tests that run in `test:changed` and in the deploy suite, on Playwright WebKit where it can observe the commit point and under fallback emulation where the effect serves another engine. There is no allowlisted-module category: bridge internals are admitted like behaviours.
   - A command (popover or modal open, `indeterminate`, `defaultChecked`, and every native page-written slot that Rust writes: `value`, `checked`, `selected`, `hidden=until-found`, `<details open>`) is published by Rust as a `data-dx-*` attribute carrying `(scope, state, based_on)` and applied by **one executor in a fixed order**: the document-scoped page reconciler installed at boot, or, for a kind whose `reconcile` witness is green (a late popover open paints nothing wrong; a late `indeterminate` does), a Rust-side `transaction` in the bridge. It reports browser-initiated changes and, on a gated surface, `applied{gen, rects}`, so there is one show writer.
   - A next-frame stream goes through the bridge under a latency budget the owner sets from one real desktop latency distribution; a named behaviour only where the measured lag exceeds it. Never a vdom handler. **Rust decides over the bridge under one order contract** (section 2.2): one epoch rule (a Rust write carries `based_on`, and the slot's page-side owner applies it iff `based_on` is not older than the slot's last page transition); two carriers (a page transition that an rsx decision reads reaches Rust on the vdom's own ordered path, the transition port, because Dioxus events carry no epoch; bridge facts and Rust-to-page writes carry epochs); every native slot that Rust writes goes through its owner, with one focus owner and one `scrollOwner` per Rust-written scroller, and `MountedData` writes behind them; one inbound pump is the only page-to-Rust bridge path; and "commutative" means an absolute set on a slot only Rust writes, decided per property.
   - Three construction rules sit beside the table: the order contract above; a roving-focus widget uses `aria-activedescendant` where its pattern allows and one `roving` behaviour otherwise; a decision includes computing its inputs, and its outputs are separate decisions (a gesture's per-move output is Rust over the bridge unless a `lag` or `order` verdict says otherwise).
4. **(G) A paint-safe gate, hardened twice.** The unsettled state is invisible until Rust answers. A separate fail-open animation plus a page watchdog, armed for every declared pending state, open it if Rust never does; the open step is one JavaScript turn that clears the pending flag, shows, reads the rects and reports them with the epoch Rust minted. The engine tier is classified by a probe attribute on `html`, not by a vdom attribute. Only placement-critical work on engines where the platform did not place the panel (and on the surfaces Rust always places) is gated; decoration (placed side, arrow, available height) never is.

## 1. Root cause

### 1.1 The two commit points (W, platform semantics)

1. **Default actions are decided when dispatch ends.** `preventDefault()` only sets the event's *canceled flag*. The browser reads that flag after the last listener returns. A call after dispatch has finished does nothing. Inside a passive listener the call is ignored: the *in-passive-listener* flag is set around the callback, and the microtask checkpoint runs while it is still set. A wheel or touchmove listener that is not passive also makes the compositor wait for the main thread. This is the cost this repo measured in rows 149/159 (`scroll_lock.rs` module docs, V).
2. **Pixels are committed after style and layout in the "update the rendering" step.** Inside one rendering opportunity, the order is: run rAF callbacks → style and layout → ResizeObserver callbacks (which may loop back to layout) → paint. A microtask checkpoint follows each callback. A DOM write lands in the frame being drawn only if it happens before paint, which means inside an rAF or ResizeObserver callback, or in microtasks queued by one. A write that arrives in a later task misses that frame. If the pre-write state was painted, the user sees the flash.

**Invariant (the root):** *A decision can affect a commit only if it is computed on the page's main thread before that commit, from inputs present there at that time.* "Present" means event fields, the DOM, and anything Rust **published into the DOM beforehand**. Rust's own memory is not present, and neither is a message that is still in flight.

**The root, restated (board).** Irreversible decisions are taken at fixed points, each from state present there: the end of dispatch (default action), gesture start (`touch-action`, listener passiveness), input routing (focus), an activation window, paint, and the compositor frame. Section 1.4 lists what that does to the bridge verbs.

**What the table says (I).** The asynchronous hop is *the bridge*, not Dioxus's event path. On desktop and mobile it is a real cross-process hop. On web it is a microtask hop: for UA-dispatched events and rendering-step callbacks, that hop *happens* to finish before both commits. It is not a contract. It breaks for events dispatched from script, which get no checkpoint until `dispatchEvent` returns. It also breaks if dioxus-web re-enables its idle/rAF scheduling, or if any hop ever uses a macrotask. So: **on web the premise is mostly false in practice, on desktop it is true, and a design for all renderers must assume it is true.** Post-paint triggers are the other hole in "zero frames on web": IntersectionObserver callbacks (and so `onvisible`), popover `toggle` and dialog `close` are queued tasks that run after a paint, so a chain that must finish before paint starts from a pre-paint trigger (`beforetoggle`, a rAF or ResizeObserver callback).

### 1.4 The desktop timing contract (web-verified; desktop inferred)

Desktop's edit cadence is part of the root: it decides what a gate costs, and in which order two renders reach the page. Read from `dioxus-interpreter-js-0.7.9/src/ts/native.ts` and `dioxus-desktop-0.7.9/src/{webview,element}.rs` ([root-and-timing finding 1](./board-2026-10-26/root-and-timing.md); round 2 added the lower half of the table, [platform-desktop findings 6, 7, 9](./board-2026-10-26-r2/platform-desktop.md)). `mobile = ["dep:dioxus-desktop"]` (`dioxus-0.7.9/Cargo.toml:122-125`): there is no separate mobile crate, so every desktop row applies to iOS and Android, plus the Android row.

| step | desktop / mobile (wry webview) | web (wasm, same thread) |
|---|---|---|
| Dioxus event | synchronous XHR, blocks the webview (`native.ts:353-395, 568-593`) | synchronous inside the DOM event (`dom.rs:88-116`) |
| render to DOM | applied in the **next rAF**, at most one render per frame (`native.ts:444-458`); the webview acknowledges (`:495-499`) and Rust sends no new render before it (`webview.rs:537-590`) | the next microtask |
| tasks and effects | only after the acknowledgement: `poll_vdom` does not call `wait_for_work` while a render is in flight (`webview.rs:537-590`; `wait_for_work` and `poll_tasks`, `virtual_dom.rs:445-536`, have no gate of their own) | the next `wait_for_work`, after the flush |
| eval and queries (`evaluate_script`: bridge `call`/`get`, `MountedData` getters) | a webview task on arrival, **unordered with pending edits** (`element.rs:30-80`) | the eval body runs synchronously at the call |
| `dioxus.send` | queued on the event loop (`webview.rs:308-317`, `app.rs:309-319`); a later Dioxus event is handled inline (`protocol.rs:62-63`), so a streamed `pointermove` can be processed after the `pointerup` that followed it | microtask |
| edit delivery | edits arrive as a WebSocket binary frame, a `Blob`, and `data.arrayBuffer().then(rafEdits)` (`native.ts:476-484`): one more task hop before the rAF is registered, so a late arrival can miss the next frame; the loopback socket (`edits.rs:117-125`) is a platform dependency (local firewalls, iOS sleep kills it) | none |
| a hidden or occluded webview | no rAF, so no render acknowledgement, so no task, effect or Rust timer runs until it is visible again (`webview.rs:563-572`): the whole runtime stalls, `crate::sleep` included | rAF is throttled; microtasks and timers keep running |
| listener scope | one listener per event name on the app root, no options (`core.ts:109-130`): one `onpointermove` or `onwheel` anywhere makes every such event in the app a blocking request and non-passive. `onmounted` is a synchronous request sent from inside the edit application, in the rAF callback (`unified_bindings.rs:183-193`): 113 sites in `primitives/src`, one per list item in `collection.rs:738`, so a mounting batch of N rows is N blocking round trips in one rendering step | the same root listener, nothing blocks |
| Android | events are handled on a webview IO thread under a global mutex (`webview.rs:82,571,583`, `android_sync_lock.rs`); the header limit drops a vdom event over about 12 KB raw (`native.ts:586-587`) | - |
| event routing | an event is routed by `data-dioxus-id` to the **current** vdom, which can be one render ahead of the DOM: a render in flight is not yet applied, and ids come from a reclaiming slab (`dioxus-core diff/node.rs`, `dom.reclaim`; I), so a click on the old, still visible element can reach the handler of the element that reused its id, and an rsx handler reads Rust state newer than what the user saw. Events route to the vdom ahead of the DOM | the DOM and the vdom agree at the event |
| Rust to page | **one `evaluate_script` per message**, with the JSON inside the script text (`query.rs:104-106`, `rustSend({data})`); the order of two messages is the order of the `evaluate_script` calls, which each platform backend provides and no Dioxus code guarantees (I) | the eval body runs synchronously at the call |
| scheduler order | each bridge session's receive loop is a task `spawn`ed in its caller's scope (lane 3.0, `bridge/session.rs:424-426`); tasks are polled by `ScopeOrder`, height then id, FIFO only inside one scope (`dioxus-core-0.7.9/src/scheduler.rs:106-110, 149-163, 247-258`; `virtual_dom.rs:445-536`), and every fact that arrives while a render is unacknowledged is delivered to its own channel (`query.rs:118-137`) and polled together after the acknowledgement. So facts of different sessions are processed in owning-scope height order, **not arrival order**: a root-owned executor's report runs before a descendant's `hotkey` fact of the same batch, and C3's facts (the carousel root) before `pan`'s rest report (the content scope); one inbound pump is therefore the only page-to-Rust bridge path (section 2.2, order contract) | two facts sent in one page task land in one batch the same way (I) |
| `MountedData` as a channel | each method calls `evaluate_script` at the moment it is called (`dioxus-desktop-0.7.9/src/query.rs:45-60`, `element.rs:26-160`): a second Rust-to-page channel that the bridge pump (flushed after the render) does not order, so `bridge::set(scrollTop)` followed by `mounted.get_scroll_offset()` reads the old value on both renderers; its writes (`set_focus`, `scroll`, `scroll_to`) are the same unordered channel and are banned by clippy outside the owners (section 2.2, order contract) | synchronous at the call |
| bridge flushes | ack-gated like tasks: a verb flush is an effect, and effects run only after the acknowledgement (the `edits.rs` comment "We don't run the virtual dom while this is true to avoid running effects before the dom has been updated"), so a handler's bridge write waits for the render it caused | the next `wait_for_work` |
| a failed edit application | an exception inside the rAF callback means `markEditsFinished()` never runs (`native.ts` `rafEdits`, no try/catch): **no acknowledgement and a permanent stall** of every task, effect and Rust timer; only a page-side fail-open recovers, and `__dxBridgeStats` reports an unacknowledged render older than a few frames as a diagnostic | the exception is logged; the run loop continues |
| Windows file drop | with the default config (`disable_file_drop_handler: false`, `config.rs:127`) WebView2's HTML5 drag events are replaced by synthetic ones: `dragover` only when the element under the pointer changes, no `dataTransfer`, a fake `file.txt` on drop (`webview.rs:329-347`, `launch.rs:61-90`, `native.ts:256-326`) | native drag events |
| release builds | `disable_context_menu` defaults to `!cfg!(debug_assertions)` (`config.rs:117`): a document `contextmenu` listener calls `preventDefault()` before any component code (`webview.rs:441-456`), so the desktop listener inventory differs from the web baseline | none |

What follows (I, from the V chain above):
1. **Two Rust renders never land in one frame on desktop.** Render k+1 is sent only after render k's rAF callback has acknowledged, so row 421's "height, style flush, flag" order is automatic there. **Web is the renderer that needs the separation**: successive renders are successive microtasks inside one frame. So the first version's `commit()` verb (rAF plus forced style flush) is dropped: on desktop it is redundant, and on web it costs a whole frame when called from a rAF or ResizeObserver callback. Web keeps a "flush between renders" helper that is a forced style read, never a rAF.
2. **G costs at least one frame on desktop, typically two,** and one more for every sequential awaited read: render (mount plus pending) lands in frame N, the acknowledgement arrives, an effect runs the eval (`showPopover`), a measuring query, render (done), frame N+1 or N+2. "Show plus measure" is therefore **one JavaScript turn that returns the rects**, the executor's open step (section 2.3), so a gated open costs exactly one round trip and one frame.
3. **An eval issued from an event handler runs before the edits of the render that handler caused** (task before the rAF on desktop; the body runs synchronously and the render follows in a microtask on web). An eval issued from an effect runs after its render on both. Lane rule: a bridge op that depends on a render's DOM is issued from an effect or `onmounted`, never from the handler that caused the render.
4. **The root has more commit points than two.** Gesture arbitration at pointerdown/touchstart (`touch-action` and listener passiveness are read when the gesture starts; pointer capture applies at the next pointer event and throws `NotFoundError` for a released touch pointer), input routing (a key goes to whatever has focus at dispatch), activation windows (`DataTransfer`, `clipboardData`, transient-activation APIs), the compositor (threaded scroll updates pixels without the main thread, so only A tracks scroll frame-exactly), and post-paint deliveries (IntersectionObserver callbacks and so `onvisible`, popover `toggle` and dialog `close` are queued tasks, not rendering-step callbacks). Hence **commit-sensitive effects are never async `call` verbs**: `preventDefault`, `DataTransfer` writes, pointer capture and a `focus` meant for the next keystroke exist only as effects of a named behaviour. Pointer capture and activation-gated calls are not "wrong when late by construction": a capture applies at the next pointer event and works while the pointer is down (W, Pointer Events 3, <https://w3c.github.io/pointerevents/#setting-pointer-capture>), and transient activation lasts seconds (W, HTML, <https://html.spec.whatwg.org/multipage/interaction.html#transient-activation-duration>), so a capture takes the witness ground of admission like any other effect (a late capture loses the moves in between, which is the red), while an **activation-gated call** takes the **platform rule row** where the witness cannot see the commit point: WebKit requires a clipboard write inside the user gesture (W, <https://webkit.org/?p=10855>) and Safari 18.x rejects even a synchronous call from a `select` `input` event (W, <https://developer.apple.com/forums/thread/772275>), while Chromium keeps transient activation for seconds (I), so a Chromium-only witness would go green, demote the effect to an `evaluate_script` call outside the gesture and ship it broken on Safari and WKWebView (admission, section 2.2). V14's clipboard write has no behaviour: it is a preview-only allowlist entry (section 3.3), and a library copy button would be a new behaviour (`copyText`) admitted by that platform rule row. **An rsx handler takes exactly one commit-time effect, `prevent_default`** (round 2, [core-construct 1](./board-2026-10-26-r2/core-construct.md)): on desktop everything else a Rust handler does reaches the page later (`MountedData::set_focus` is a webview query that runs after the handler's synchronous request returns, `element.rs:137-160`; renders land in the next rAF; `dioxus-html` has no pointer-capture API). **The `DataTransfer` setters are in the same class**: `set_data`, `clear_data`, `set_effect_allowed` and `set_drop_effect` do nothing on desktop and return `Ok` (`dioxus-html-0.7.9/src/data_transfer.rs:116-146`), and they ship at the drag sources of `drag_and_drop_list.rs:860-865`, `preview/src/components/data_table/reorder.rs:363-368` and `preview/src/components/virtual_list/variants/reorder/mod.rs:144-149` (plus `set_drop_effect` in dragover handlers). A clippy `disallowed_methods` rule by def path (the `check-hot-events` mechanism, section 5.3) keeps new ones out of rsx, and the drag source's write becomes the `dragSource` half of `dropAnywhere`. A G chain starts from a pre-paint trigger: the executor's open step, which is one JavaScript turn (`toggle` is a post-paint task, and `beforetoggle` does not exist for `<dialog>` on Chrome before 132, Firefox before 133 and Safari 18.x, exactly the engines that need G).
5. **The platform half is mostly unproven.** Android sends the event in a base64 header (16 KB per header, `native.ts:575-587`); edits are rAF-bound, so a hidden or throttled webview stalls every render. Synchronous XHR to a custom scheme on WKWebView is W: WebKit bug 186902 ("WKURLSchemeHandler doesn't handle sync XHR") is RESOLVED FIXED (r233113, 2018-06-22). WebKitGTK stays I. V for the code path, I for the rest.
6. **A hot vdom listener costs a blocking round trip per event, and Dioxus pays per event name, app-wide.** Every Dioxus listener on desktop is one synchronous XHR, `onresize` included (a `CustomEvent` per ResizeObserver entry, `core.ts:54-72`), so one frame with 50 resized rows (`virtual_list.rs:486`, `table_rows.rs:289`, `virtual_grid.rs:1526` attach `onresize` per row) is 50 blocking round trips inside the rendering step. Because a bubbling event has one root listener per name, a single `onpointermove` or `onwheel` anywhere makes that event a blocking request across the whole app, and `onmounted` is a blocking request inside the edit application (table above). A vdom listener is for an event that needs Rust's synchronous `prevent_default`, or that fires at human rate; frame-rate streams go through the bridge (section 5.2). The existing frame-rate vdom handlers are the lane 3.HV (section 5.4).
7. **Fail-opens are page-side, and streams need back-pressure.** While a render is unacked no Rust task runs, so any timeout that must fire while Rust is stalled (G's fail-open, a behaviour's lease) lives on the page. One bridge message costs two JSON parses and at least three event-loop turns on desktop, a few hundred microseconds of main-thread time (`native_eval.ts:49-56`, `webview.rs:308`, `app.rs:309`, `query.rs:39`; I): about 120 messages per second per stream at 120 Hz is acceptable if `sample`/`subscribe` are **latest-wins on the page, at most one message per frame per stream** (the built behaviour; there is no acknowledgement window), batched modes carry a cap and a drop-oldest rule that records the loss, and high-rate Rust output goes through `set` (CSS custom-property batches), not a message per frame. The channel is unbounded, so a stall builds a backlog that replays afterwards; an in-flight window (Rust acknowledges a stream sequence number) is added only if `bridge-cost`'s "Rust busy 30 ms at 120 Hz" case shows the backlog matters, and a stream that must order against vdom events shares one session with every fact it is combined with, and every other page-to-Rust fact goes through the one inbound pump with its page-minted sequence number (the order contract, section 2.2).
8. **A bridge fact and a Dioxus event are two unordered inputs on desktop, and so are facts of two sessions.** A Dioxus event is handled inline at once (`webview.rs:191`, routed at `protocol.rs:62-63`); a bridge fact is posted to the event loop (`webview.rs:315`) and consumed by a task that runs only inside `poll_vdom`, which returns early while a render is unacknowledged (`webview.rs:564`). A fact posted in an earlier page task can therefore be applied after a Dioxus event from a later task, up to one acknowledgement plus any Rust busy time later; on web the fact's handler runs in the microtasks of its own task, before any later event. The same input sequence resolves differently on the two renderers, which a Chromium-only CI cannot see. Facts of different sessions are not ordered among themselves either (the scheduler row of the table). This is an ordering class, not a latency one: section 2.2 states the one order contract (one epoch rule, two carriers, one inbound pump), with the instances. **Dioxus events carry no epoch** (the interpreter serialises a fixed field set per event, without dataset or timestamp, `dioxus-interpreter-js-0.7.9/src/ts/serialize.ts:279-313`), so an rsx handler that decides on a page-written slot has only Rust's lagging copy of it, and on desktop an epoch fence there would drop the user's input or let web and desktop end in different states. **A page transition that an rsx decision reads therefore reaches Rust on the vdom's own ordered path** (the transition port); epochs stay for bridge facts and Rust-to-page writes; and one inbound pump is the only page-to-Rust bridge path, so the facts that a decision combines share one session by construction.

## 2. Constructions, from the root

The invariant leaves these ways to satisfy it. They are applied per decision in the order of section 5.1 (a block may use several, for different decisions):

| | how it satisfies "decide at the commit, from data present" | logic lives in |
|---|---|---|
| **delete** | The block runs on no supported renderer (a `not(web)` arm compiled only for Blitz, or a script a shipped CSS rule already makes a no-op). | nowhere |
| **rsx** | The target is inside a Dioxus element, Dioxus has the event and every field the decision reads, the serialized event stays small (Android), and the only commit-time effect is `prevent_default()`: the handler is synchronous on web and on desktop/mobile and `prevent_default()` reaches the native event. | Rust |
| **A** platform-declarative | The browser owns the decision inside its own pipeline. A keeps a Rust invariant or a Rust verification step behind it. | the browser (no code) |
| **R** no real sync need | The block was never on a commit path (it reads and reports, runs a command, or drives a passive effect that may answer late). | Rust plus plain bridge verbs |
| **G** paint-safe gate | Removes the deadline for one-shot work: CSS keeps the unsettled state invisible, so a late answer paints nothing wrong. | Rust |
| **B** a closed registry of named, scoped behaviours | The decision has a commit-sensitive effect (cancel, capture, focus routing, a same-frame write) that Rust cannot take in time, or it is a command Rust mirrors into the page: one named behaviour decides locally from published config, each of its effects admitted by a counterfactual witness. | Rust owns config and lifetime; one tested TypeScript module owns the decision |
| **C** run Rust in the page | C1: the Dioxus sync event path. C2: a Rust kernel compiled to page-side wasm. C3: worklets. | Rust |

There is no "residue" row: what stays page-side is the registry (section 4), reported as a number.

- **The boot probe set** is R, not a behaviour: its deadline is none (an absent attribute counts as fallback, the gated and fail-safe side), so it is Rust-rendered probe nodes read through one `transaction`, never a page program. The nodes are `popover=manual`, because showing a `popover=auto` element closes an auto popover that is already open, and it starts from the first idle after hydration, so that its forced layouts are not on the first open's critical path. It runs once per load and is never cached across loads (the engine build is unobservable on a WKWebView, whose user agent is frozen: `Macintosh; Intel Mac OS X 10_15_7`, `AppleWebKit/605.1.15`, no `Version/`, so a "Safari 26.2 floor" cannot be read there and only the probe classifies): edge shift at the viewport edge, reopen three times, a nested submenu, an anchor under a scaled parent. **The probe classifies the engine tier.** Rust writes the result to a root attribute, `html[data-dx-anchor="a"]` or `"fallback"`, through one closed `documentElement.dataset` setter row (lane 3.PL adds the row with its grant), and an absent attribute (the window before the probe answers, which can include the first popup) counts as fallback. An engine that fails a probe **counts as a fallback engine**, and its popups are in the placement-critical (gated) paint tier of section 2.3. The floors cover the known bugs; the probe covers state-dependent ones that neither a one-time `CSS.supports` nor a post-hoc per-open check can see (`anchor_fallback.rs:21-28`; a post-hoc check on an engine G leaves ungated paints one wrong frame first). The per-open outcome measure stays for decoration and verification.
- **"Older" is not rare.** Safari 26 is the current WKWebView until OS 27 adoption; devices locked to iOS 18 or macOS 15, WebView2 109 and Android WebView without Play updates are a permanent fallback population (I).
- **Desktop and mobile:** WebView2 and Android WebView are evergreen Chromium. WKWebView follows the OS WebKit, so Safari 26.2 is the floor on macOS and iOS for anchor positioning and Safari 27 for nested anchors and `overflow-anchor` (I). **WebKitGTK is unverified**, so the fallback stays until a probe on Linux desktop shows support. The probe has never run on a webview: on Apple desktop the fallback engine tier is the default experience for months, and G there costs more than today's in-turn placement (section 2.3, latency).

**What the A-only run must cover on top of the conformance sweeps** ([ux-a11y-perf F9](./board-2026-10-26/ux-a11y-perf.md)): a 320 x 256 CSS-px viewport at 400% zoom (`max-height: 100%` of a `position-area` region beside the anchor can be about 100 px, where the JavaScript path clamps to the whole visual viewport), an RTL subtree (a physical `span-right` opens rightward in RTL; use the logical `span-inline-end` and drive direction from the same `use_direction` signal the carousel reads), and a keyboard-reduced `visualViewport` with an open combobox (the layout viewport does not shrink, so the list can sit under the keyboard until Rust republishes). A is verified on Chromium only: Firefox (147 and 148) and WebKit (Safari 26.0, 26.2 and 27) runs of a named subset, with a nested-submenu spec and a reopen-three-times spec, are part of [row 442](../backlog/442-desktop-cadence-harness-and-desktop-pass.md) and lane 3.PL.

### 2.2 (B) The placement rule (by deadline and kind) and the closed registry of named behaviours

**Why not a predicate language behind one delegated interpreter.** The first version of this document put every in-listener decision behind one capture-phase listener reading `data-dx-rule*` attributes, with four rule families. Four board members broke that form independently ([block-mapping F2, F6-F8](./board-2026-10-26/block-mapping.md), [simpler-alternative 3-4](./board-2026-10-26/simpler-alternative.md), [root-and-timing 3](./board-2026-10-26/root-and-timing.md), [ux-a11y-perf F5](./board-2026-10-26/ux-a11y-perf.md)):
- `closest('[data-dx-rule]')` finds only rules on the target's ancestor chain, which are exactly the events a Dioxus element handler already decides synchronously with full Rust state, on every renderer including Blitz. The sites that need page-side code (document Escape, F6, "outside the menu", window scroll lock, window Cmd+B, document `dragover`) have no such ancestor.
- At document capture nothing has run yet, so a `defaultPrevented` predicate (V22, L23 read it today because they run last) is always false, and a `stopPropagation` there cuts off every element listener and the Dioxus root. Dioxus delegates in the bubble phase (`core.ts:109-130`).
- A page-lifetime non-passive `wheel`/`touchmove` listener brings back rows 149/159 and fails `playwright/oracle/tier2-html/listener-inventory.spec.ts` (the multiset of listeners on window/document/html/body must equal the baseline taken before the first open).
- The families were unions of today's blocks: one user each for `can-scroll`, the regex filter and the metrics publisher, three different programs under "reveal/settle", four output modes under "pan". The interpreter would be about as long as the blocks it absorbed, plus a language, a serialisation format and a parity gate. Call the JavaScript that stays what it is: named modules.

**Why not a rule indexed by listener location (round 2).** Round 1's replacement sorted by where a listener sits: an rsx handler inside a Dioxus element, a named behaviour for a window, document or capture target or an event Dioxus lacks, a bridge stream for a continuous event. Five round-2 members found the same flaw from three sides ([core-construct 1](./board-2026-10-26-r2/core-construct.md), [blank-slate 1-2](./board-2026-10-26-r2/blank-slate.md), [platform-desktop 1](./board-2026-10-26-r2/platform-desktop.md)):
- **The plan contradicted its own rule.** The behaviour arm named `close` and `beforematch` and the capture phase, yet L2, W4, T12 and L3/L7/L8/L9 were mapped to bridge `listen`. C4 fitted all three arms, L11 and S2/S3 two, with no precedence.
- **"Synchronous on every renderer" holds only for `prevent_default`.** On desktop `set_focus` is an async webview query (`dioxus-desktop-0.7.9/src/element.rs:137-160`), renders land in the next rAF, and `dioxus-html` has no pointer-capture API.
- **The same gesture was placed two ways** (drawer drag R, toast swipe `pan`), and a same-frame layout write (W8 follow-bottom) was answered 1-2 frames late on WKWebView before Safari 27 by the Rust invariant alone.
- **Commands had no arm.** `showPopover`/`hidePopover`, `showModal`/`close`, `indeterminate` and `defaultChecked` were one-off bridge calls fired from effects, with a lane rule and no construction behind it.

The root sorts by **which commit point a decision feeds and by when it must land**, so the rule is rebuilt on that.

**The placement rule: classify each decision by its deadline, then by its kind.** Decided per decision (a block may have several decisions, each with its own row: T8, W8), and enforced by the gates of section 5.3. For one decision, read the table top to bottom; the first row whose deadline the decision has is its placement.

| deadline (what a late answer costs) | placement | examples |
|---|---|---|
| **this event's default action** (cancel or not) | an **rsx handler** if Dioxus delivers the event, every field the decision reads (`ToggleData`, `FocusData`, `CancelData` and `SelectionData` are empty and `MouseData` has no `detail`, so decisions on those do not qualify) **and the serialized event stays small**: on Android a payload event travels in a request header of about 12-16 KB and a failed request silently loses the cancel (`native.ts` `handleVirtualdomEventSync`; the page navigates), so `submit`, `input`, `change`, `paste` and `drop`, which carry user text or form values, are not rsx-cancel candidates on mobile (cancel declaratively with `method="dialog"`, `inputmode` or CSS, or page-side; `DemoForm` is immune by construction); otherwise a **named behaviour** | L1 (`onkeydown` on the `<dialog>`), L2 (`oncancel`); `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`'s click suppression |
| **this event's task** (pointer capture, focus routing for the next input) | a **named behaviour's effect**; never an async verb, never rsx `set_focus` on desktop | `pan`'s capture, `openFocus`, `roving`, `settle`'s focus |
| **before paint** (a same-frame layout write) | **A** where the platform does it, behind per-feature floors and a boot probe (section 2.1); otherwise a **named behaviour** (`stickToEnd`; placement on fallback engines if G's invisible pending state is not acceptable); **G** only for one-shot placement where an invisible pending state is acceptable | T8, T11; W8's follow-bottom; S1, O3, V19 |
| **next frame** (drag tracking, momentum, a finger-following value) | **bridge stream plus Rust** under the order contract (below) and under a latency budget the owner sets once from one real desktop latency distribution (section 5.6); a named behaviour only where the measured lag exceeds that budget, admitted by a verdict with the reason `lag` or `order` | L30, C3, C5 |
| **none** | an **rsx handler** if Dioxus delivers the event and every field the decision reads at human rate (L22: `PointerData::pointer_type()`, on the host elements; an rsx decision that read a bridge fact would depend on the arrival order of two inputs); otherwise **R**: Rust over the bridge (`listen`, `observe`, `sample`, `get`, `call`), under the order contract | L22 (rsx); L3, L5, L7-L9, L21, W1, W4, W6, T12, L27 |

An event Dioxus lacks (`close`, `beforematch`) no longer makes a behaviour by itself: a commit-sensitive effect does. Frame-rate events never take a vdom handler whatever their deadline (section 1.4, item 6). A block with several decisions is placed decision by decision; the layer order of section 5.1 is the preference among constructions for one decision, and where it and this table seem to disagree the table decides.

**Conditions on the table.** Four rules the board found the table needed; each is a construction, not a lane note.

1. **The order contract: one rule for commands, behaviours, reports and streams.** Two inputs reach Rust unordered on desktop (section 1.4, items 8 and the scheduler row): a Dioxus event is handled inline, a bridge fact waits behind any unacknowledged render, and facts of different sessions are processed in owning-scope height order, not arrival order (`dioxus-core-0.7.9/src/scheduler.rs:106-110, 149-163, 247-258`). So no decision may depend on the arrival order of two inputs. The contract is **one epoch rule, two carriers and one inbound pump**. It replaces round 3's separate "commutative only" condition, its "page-owned transitions accepted by epoch" condition, the reconciler's own generation story and round 4's "mint `seen + 1`" wording.
   - **Slot and epoch.** A **slot** is a piece of page state that a decision writes and the page can also write: open state, focus, scroll position, an input value, a behaviour's mode (`following-bottom`). Each has one counter, its **epoch**, kept on the page and **keyed by slot id** (the owning scope, or `document` for focus), never by element object: Dioxus re-creates elements, and the as-built `Epoch::next` is neither keyed by slot nor advanced by a page transition (one process-global Rust counter, `bridge/mod.rs:151-159`; the page compares Rust epochs only with Rust epochs, in a `WeakMap` keyed by element, `ts/bridge.ts:405-418`), so a Rust write could never lose to the page. Item 0.7 replaces it before item 0.4. A **page transition** (a light dismiss, the user's wheel, touch or key, a form reset, a detach) advances the slot's epoch (`current + 1`) and is reported.
   - **The rule.** A Rust write carries **`based_on`**, the slot's last page epoch that Rust has seen. The slot owner applies it iff **`based_on >= last_page_transition`**, and otherwise drops it and reports. Rust writes do not mint epochs; they are ordered among themselves by the pump's FIFO (a command by its level, the attribute's latest value), so a quick open then close both apply. Round 4's wording ("Rust mints `seen + 1`; the page applies a write only if its epoch is strictly newer") is withdrawn: it dropped the second command of every open-then-close between two page reports, and a Lamport "strictly newer" test does not express "decided from". On the command wire the field is `gen`, and it is `based_on`.
   - **Carrier 1, for a slot that an rsx decision reads or writes: the vdom's own ordered path.** Dioxus events carry no epoch: the interpreter serialises a fixed field set per event, without dataset or timestamp (`dioxus-interpreter-js-0.7.9/src/ts/serialize.ts:279-313`), so an rsx handler that decides on a page-written slot has only Rust's copy of it, which on desktop lags the page by up to one acknowledgement plus Rust busy time (on web the fact's microtask runs first, so the copy is current there). An epoch fence at that point only chooses which input to lose, and the same input sequence then ends in different states on the two renderers: a light dismiss followed by the trigger's own `onclick` in one gesture (`top_layer/popover_sync.rs:200-225`), or Escape and then Enter on the refocused trigger. So **a page transition that any rsx-handled decision reads reaches Rust synchronously on the vdom's own ordered path: the transition port**, one hidden element that the bridge's root renders once and that receives a synthetic `input` event carrying the transition (round 4's remedy (iii), promoted from a last resort to a first-class carrier). On desktop that is one blocking request per transition, so only **low-rate** transitions qualify (dismiss, toggle, reveal, reset, detach), never a stream, and Rust's `seen` is then current at every later Dioxus event on both renderers. The slot table below records for each slot whether it is **rsx-read** (its transitions take the port) or **bridge-only** (facts with epochs), and a gate rule checks the table.
   - **Carrier 2, for bridge facts and Rust-to-page writes: epochs.** (a) **Facts carry the epoch of the slot they observed**, read on the page at emission and stamped from the slot's level where one exists (`:popover-open`, `dialog.open`, `activeElement`), not only from the last observed event, because a dialog's `close` after a skipped `cancel` is a post-paint task (T12's scroll fact names the open-state epoch it saw; `hotkey{Escape}` names the target layer, resolved on the page from the top layer). (b) **A Rust write to a page-written slot goes through that slot's slot owner** with `based_on`, and the owner drops it if a page transition has made the slot's epoch newer.
   - **One inbound pump.** Every page-to-Rust bridge fact goes through **one** inbound pump: a page-minted global sequence number and one root task that dispatches to the subscribers' callbacks in sequence order (a `Callback` runs in its origin scope, I). Sessions keep their own outbound commands. So "the facts that one decision combines share one session" holds by construction, instead of as a per-decision judgement that no gate can check: the shipped Accordion in single mode combines the `beforematch` facts of N panel scopes, each with its own `use_js_listeners` session (`collapsible.rs:64-86`, `tabs.rs:499`), which the scheduler processes in scope-id order, and a re-keyed or inserted panel breaks that order (find-in-page cycling through panels opens the wrong one). A mixed design is worse than either pure one, because the root pump's facts (height 0) always overtake every session's facts in a batch (the scheduler row of section 1.4). A stream that stays on its own session (a drag's start, move and end) is combined with no fact of another source.
   - **The vdom is a writer too.** Dioxus writes native page-written attributes from the edit stream, outside every slot owner. `value` is volatile on `input`, `select` and `textarea`, and `selected` on `option` (`dioxus-html-0.7.9/src/elements.rs:1488, 1536, 1571, 1594`), so it is rewritten on every diff of its template (`dioxus-core-0.7.9/src/diff/node.rs:444-463`), and the interpreter assigns `node.value = value` whenever it differs (`dioxus-interpreter-js-0.7.9/src/ts/set_attribute.ts:24-35`), which also moves the caret. `checked`, `open` and this repo's `HIDDEN` attribute are written only when their value changes, while the page writes all three (the user, `form.reset()`, form-state restoration, `beforematch`), so Dioxus's memory diverges with no record (`collapsible.rs:122-124` documents the controlled-`open` case). Hydration rebuilds with `skip_mutations` (`dioxus-web-0.7.9/src/lib.rs:100-148`), so the vdom remembers the server's `value` while the DOM holds what the user typed before the wasm arrived, and the next render of that template wipes it (the combobox input re-renders on every `open()` or `active_descendant()` change, `combobox/components/input.rs:152-161`). The traced results, on both renderers: lost keystrokes on desktop under async results (a render in flight rewrites `value` over text typed after it), text that reappears after a form reset on a controlled input, text typed before hydration wiped on the SSG site, and an `until-found` veto that shows the panel open while `aria-expanded` is false (the live defects of section 6, filed as backlog rows). **Construction:** the **reconciled kinds become every native page-written slot that Rust writes**: `value`, `checked`, `selected`, `hidden=until-found` and `<details open>` join popover open, modal open, `indeterminate` and `defaultChecked`. Rust publishes `data-dx-*` (the desired state and `based_on`) and the slot owner applies the native property, or drops the write. Rust never echoes the user's own input back (an rsx `oninput` updates Rust, not the DOM). At install each owner reports the live level as a page transition, which covers typing before hydration and form-state restoration, and the value owner mints one on `reset` (it bubbles) through one document listener. A gate bans rsx `value:`, `checked:`, `selected:`, `open:` and `hidden:` on a page-writable element outside the `initial_*` forms (clippy or an rsx scan beside `check-hot-events`). The shipped sites are `combobox/components/input.rs:152`, `input_otp.rs:434`, `radio_group.rs:436`, `checkbox.rs:341` (which has a second writer, an eval of `input.checked` at `checkbox.rs:298-316`) and the `HIDDEN` slot in collapsible, accordion and tabs. The kinds beyond the first four are added by the row that owns their consumers (3.FC), on the executor of item 0.4.
   - **`MountedData` writes are a second owner bypass.** `set_focus`, `scroll`, `scroll_to` and `scroll_to_with_options` write focus and scroll position, and on desktop each is an immediate `evaluate_script` unordered with the pump (`dioxus-html-0.7.9/src/events/mounted.rs:167-200`, `dioxus-desktop-0.7.9/src/query.rs:45-60`). The workspace has 82 `set_focus(` sites in 36 files (78 of them in 32 primitives files) and 9 `scroll_to(` sites. They join clippy `disallowed_methods` by def path with a per-site `#[expect]` until each is ported, and go through the focus owner and the scroll owner. A read of a page-written slot that feeds a write goes through `bridge::get` with the slot epoch, never through `MountedData` (an epoch-less read feeding a write is the S4/V6 pattern).
   - **One focus owner, and one `scrollOwner` per Rust-written scroller.** Focus is one document-global slot: a per-element memory cannot see a click into another field, so a late roving write would steal focus back. The **focus owner** (a bridge internal on the document slot, with one page-lifetime `focusin` listener in the baseline, as `modality.rs` already has one) is what `openFocus`, `roving`, `settle`'s focus, the refocus on close and `focus_prevent_scroll` all call. `focus()` without `preventScroll` also scrolls ancestors, so one focus write lands on two slots, and the focus owner passes `preventScroll` wherever the scroll slot has an owner. Scroll position has page writers that no `scroll` event can tell apart: the user's compositor-threaded scroll, scroll anchoring, a snap re-snap, find-in-page, `#fragment`, `focus()` and the owner's own write (W, CSSOM View, the scroll event steps). Its epoch therefore needs an input classifier (wheel, touchstart, keydown and a scrollbar pointerdown on the scroller) and a memory of the owner's own writes. That is a stateful page program, not a verb row (a verb row has no listeners or memory, section 2.2 verbs), so each Rust-written scroller has one **`scrollOwner`** behaviour: it classifies input into transitions, applies `based_on` writes and reports settle. It subsumes `stickToEnd`'s detach, `pan`'s scroll writes, the setters of S4, V6 and W2, C2's writes if `scrollStep` becomes a `transaction`, and the carousel's autoplay tick against a user swipe (a native swipe mints a transition on `touchstart`; the autoplay tick otherwise pulls the scroller forward and it bounces back).
   - **(c) "Commutative" means an absolute set on a slot only Rust writes, decided per property.** A `--dx-*` custom property that the page also writes is a page-written slot (`anchor_fallback` publishes `--dx-anchor-width` and `--dx-available-*`; `pan` and `stickToEnd` write variables), and `set` refuses a property that a behaviour on the same element declares as an output. It is not an absolute set on a slot the user also writes: `set(Rust); set(user)` is not `set(user); set(Rust)`.
   - **The slot table**, one owner per row (an owner is built by the first row that consumes it, except the focus owner, which item 0.7 builds):

     | slot | page writers | owner | epoch source | carrier |
     |---|---|---|---|---|
     | open state (popover, dialog) | light dismiss, Escape, CloseWatcher (`close` is a post-paint task when `cancel` is skipped) | the executor | the toggle report, stamped from the level | the transition port where an rsx handler reads it (a trigger's `onclick`), else a fact |
     | focus | the user, the browser's focus fixup on removal, dialog and popover focusing steps, `autofocus` | the focus owner (document slot) | `activeElement` | a fact; the port if an rsx handler decides on it |
     | scroll position | the user, anchoring, snap re-snap, find-in-page, `#fragment`, `focus()` | one `scrollOwner` per Rust-written scroller | its input classifier | a fact |
     | value, caret, `checked`, `selected`, `hidden`, `<details open>` | the user, reset, autofill, restoration, IME, `beforematch` | the native slot owners of the reconciled kinds (`otpFilter` for the filtering it does) | `input`, `reset` and `beforematch` through one document listener, and the install-time level | the transition port for a controlled value that an rsx `oninput` reads, else a fact |
     | a `--dx-*` custom property | the page too, for the ones named above | "Rust only", decided per property | n/a | n/a |
     | dialog `returnValue`, media state | none in the library (V: no `video` or `audio`, no `returnValue`) | - | n/a | n/a |

   - **Instances.** The reconciler's report after a later click; `stickToEnd`'s detach, and the W8 invariant's `scroll(end)` backstop, which goes through `stickToEnd` carrying `based_on` (without it an invariant write in flight lands after the wheel-up); T12's close-on-scroll after a reopen, and Escape's "close the top of stack" after a light dismiss (both fenced by the open-state epoch, where round 3's "a late close is harmless" was false); a light dismiss followed by the trigger's own `onclick` in one gesture, and Escape then Enter (carrier 1); S4's and V6's `scrollTop` writes after an asynchronous `get` while the user wheels (the scroll owner); L2's dialog `close`, which goes only through the executor's report; the carousel's previous and next from the settled index (an absolute target computed from the fact's epoch, through the scroller's owner), and the autoplay tick against a swipe; `hotkey{Escape}` against an Enter typed right after it; combobox typing while results arrive, and a form reset with a focused controlled input (the native slot owners); Slider's and Resizable's drag, which starts in rsx (`move_interaction.rs:119-146`) and ends by a window `up` fact (`pointer.rs:33-48`): a mouse's `pointerId` is the same on every press (W, Pointer Events 3), so on desktop a stale `up` removes the next press's pointer and kills the next drag, and the fix is the plan's own rule (every phase of the drag through one bridge session, or through the pump); an Accordion's find-in-page across panels (the pump and the hidden owner); and the legacy fact sources `use_beforematch`, `use_form_reset_listener` (`lib.rs:571-588`) and `pointer.rs`, which send epoch-less facts through `Program::Legacy` and get an owner row in the ledger of section 3.3 and a port lane, ordered by exposure.
   - **What the contract does not cover:** the order inside Rust between a Dioxus event and a fact on a slot only Rust writes (the slider's arrow key against queued pointer moves, L21). The remedies, in this order, are (i) the platform for open and close toggles: an invoker relationship (`commandfor`, `popovertarget`), which light dismiss treats as inside its popover, **with an rsx `prevent_default` on the trigger's `click`** (the browser's own toggle would otherwise be a second show writer; a canceled click skips activation behaviour, W DOM dispatch); (ii) an already-admitted behaviour that sees both events in DOM order; (iii) the transition port above, for a low-rate fact that an rsx decision reads. Pure streams whose consumer is latest-wins (W1's windowing is absolute) are exempt. The page-side order counterfactual of admission (below) reorders facts against events **and across sessions** and gets one spec per instance; the desktop-cadence build of row 442 is its fidelity check.
2. **Two deadlines in one gesture: a decision includes computing its inputs; its outputs are separate decisions.** A decision takes the deadline of its earliest effect and includes everything it reads; the effects it causes later are decisions of their own, each placed by its own row. C4's cancel of the committed `pointermove` reads "committed", which is computed from the move stream (the slop threshold), so the recogniser stays on the page (the default-action row); its per-move `scrollBy`, coasting and rubber band are next-frame decisions placed by that row, and O5's `css-var` output likewise. **Default: a gesture's per-move output is Rust over the bridge** (`set` for a CSS variable, a `transaction` for `scrollBy`); a page-side output variant of `pan` is admitted only by a `lag` or `order` verdict for that gesture, and until the owner's verdict exists a block that has not been ported keeps its page-side output in its frozen legacy script (symmetric with C5: Rust is the attempt, the legacy arm stays until measured). O5 and L30 are one gesture class and are judged together against the provisional one-frame budget (section 2.2, admission) until the owner's budget exists.
3. **Roving focus: `aria-activedescendant` where the pattern allows, else one `roving` behaviour.** Every roving widget is arrow-key driven and arrow keys auto-repeat, so the "unless key repeat" condition holds for all of them (78 `set_focus` sites in 32 primitives files). On desktop `set_focus` is an async webview query and `tabs.rs:389` writes DOM focus back into Rust (`onfocus: ctx.focus.set_focus(Some(index()))`): a late focus event for item k+1 that arrives after Rust moved to k+2 resets the index, a key-repeat step is lost, and a native Enter or Space then activates the stale DOM-focused button. **Construction:** a composite whose ARIA role supports `aria-activedescendant` (listbox, menu, menubar, grid, tree, radiogroup, tablist, combobox popup) keeps DOM focus on the container and renders the active item as `aria-activedescendant` plus `data-highlighted` through the edit stream; key handling stays an rsx `onkeydown` on the container (`prevent_default` only), scrolling the active item into view is next-frame R, and the focus deadline disappears because focus never moves. Where roving `tabindex` must stay (Radix parity for tabs and radio; screen-reader support for `aria-activedescendant` differs, so this is an owner call), one **`roving`** behaviour moves focus in the keydown's task, admitted by its witness. A focus that no keystroke is waiting on (the L20 hand-off, section 3.2) is not roving. The 32 files are a row in the lane plan (candidate row `roving-focus`, about 28 agent-hours, sized in round 5), in the estimate and in the file order, not a "site by site" note; one focus owner serves every roving write (order contract).
4. **Android payload events** are the condition in the first row of the table, with the declarative cancels as the replacement; the gate that counts rsx cancels lists the payload event names (section 5.3, item 8).

**Kinds.**
- A **listener** reacts to events. The table above places it.
- A **command** mirrors Rust state into the page. Rust publishes the desired state as a `data-dx-*` attribute (never the native `open` attribute: two writers, `lib.rs:590-606`) and the page applies it. The **reconciled kinds** are popover open, modal open, `indeterminate` and `defaultChecked`, and (round 5) every native page-written slot that Rust writes (`value`, `checked`, `selected`, `hidden=until-found`, `<details open>`; see "The vdom is a writer too" in the order contract), whose rsx writes a gate bans; a one-off `show_popover()` call is legal only for an element that is none of them.
  - **Executor: the page reconciler or a Rust transaction, decided per kind by `reconcile`'s witnesses, which phase 0 runs first (item 0.6 owns them).** An open is not a before-paint write: an unshown `[popover]` is `display: none` (W, HTML rendering, <https://html.spec.whatwg.org/multipage/rendering.html#flow-content-3>), so a late open paints the old state one frame longer and nothing wrong. What the page half buys is a frame on desktop (the next-frame row, the owner's budget) and ordering, and the witness tests both. **If a kind's witness is green (a late popover open paints nothing wrong; a late `indeterminate` paints the wrong glyph and is red; `defaultChecked` never paints; so the kinds are decided one by one), that kind is a Rust-side level-triggered `transaction` in the bridge**: the open step is one `Transaction` that clears the pending state, shows and reads the rects (`show_popover_measured` already is one), and carries the epoch; the attribute, the epoch and the one-show-writer rule below are unchanged, and only the executor moves. `reconcile` is then part of the bridge, not a registry behaviour. The page reconciler below stays only against a `lag` verdict or a red order witness (a vetoed close, then a reopen, under the page-side order counterfactual).
  - **The page reconciler, where kept: one document-scoped observer, installed at boot.** `reconcile` is a single observer installed with the bridge (`subtree`, `childList`, and an `attributeFilter` over the command attributes), not one observer per element. Eight of the eleven popover consumers (tooltip, hover card, select list, combobox list, popover, navbar, navigation menu, toast) mount their panel in the render that opens it (`use_animated_open`, then `if render()`), so the element arrives already carrying its attribute, and an observer attached afterwards by an effect, or by Rust over the bridge, sees no attribute change and saves nothing over today's effect-driven open. The popover hooks therefore **return the attribute to spread** (`use_popover_sync` and `use_popover_shown_while_mounted` return `()` today, `top_layer/popover_sync.rs:109-113, 239-243`), so the attribute is a vdom attribute in each consumer's rsx, and item 0.4 owns the one-line spreads at their 13 call sites in 11 files. A `childList` record for the inserted node is delivered at the microtask checkpoint after the rAF callback that applied the edits (`native.ts:444-458`), before style, layout and paint, so the open lands in the frame the edit lands; the same discovery serves server-rendered markup. The reconciler reads the level at install for markup already in the page and at every added node that carries a command, so a command that is lost, early or reordered converges, including when the runtime loads late (#5919). A per-element attribute observer stays only for always-mounted or animated-exit content (`use_popover_shown_while_mounted`). Its cost (nodes scanned on a churning virtual list, observer count, records) is a `bridge-cost` case, and the observer count is an inventory beside `listener-inventory.spec.ts`. The observer is the bridge's one boot-installed `pageObserver` (the seam lane 3.0 leaves in `bridge.ts`); it also arms G's page-side watchdog for every node that enters a declared pending state (section 2.3, item 3), and it is that observer, watchdog only, when the Rust-side executor is used.
  - **An epoch on every command, and no `volatile`.** Dioxus writes an attribute only when its value changed (`dioxus-core` `diff/node.rs:416-470`), and a browser-initiated change (light dismiss, Escape) changes the DOM, not the attribute: a controlled `open` that vetoes `on_open_change(false)` leaves the attribute `true`, no record exists, the DOM stays closed while Rust says open, and a later re-attach would reopen a panel the user dismissed (with its enter animation and a focus move). So the attribute value carries `(scope, state, based_on)` (under the order contract above Rust mints nothing: `based_on` is the page epoch it has seen), and the executor records "the browser diverged at epoch e" **keyed by the owning scope's id (`scope`), not by element** (a panel that Dioxus re-creates while open, through a re-key or a responsive swap, would otherwise lose the memory and resurrect a dismissed panel), and applies a write only if its `based_on` is not older than that epoch. Rust either adopts the browser's state or vetoes by a new write that carries the epoch it has now seen, a deliberate and visible reopen, so a decision that follows a transition Rust has seen is a changed value (its `based_on` moved) and a record exists without rewriting equal ones, while a decision made before Rust saw the transition is dropped by the owner, correctly: `volatile` adds nothing once `based_on` exists (rsx builds custom attributes non-volatile, `dioxus-rsx-0.7.9/src/attribute.rs:191-196`, and a volatile attribute is rewritten on every diff, `dioxus-core-0.7.9/src/diff/node.rs:444-463`, one record per command per render on a churning virtual list). Every report carries the epoch it answers, and Rust drops a report older than a transition it has already applied, which also closes the window in which a streamed report is handled after a later click. This is G's epoch (section 2.3): one rule for commands and for the gate.
  - **One executor per element, in a fixed order, and a batch ordered by tree.** Several kinds can sit on one element (a `<dialog popover>` is the non-modal Popover of DatePicker and ColorPicker, `popover_sync.rs:300-305`, and `showModal()` throws `InvalidStateError` on a showing popover), so the executor owns all of an element's kinds and applies them closes before opens, `hidePopover` before `showModal`, focus last. `openFocus` runs inside the open step, so "same eval as `showModal()`" holds by construction. Across elements one record batch is applied by tree: closes deepest first, opens shallowest first, and a Rust layer-tree invariant cascades a close to the layers that are DOM descendants of the closing layer and refuses an open under an ancestor that closes in the same batch. The popup-boundary rule keeps a popup a DOM descendant of its trigger, a closed layer is `display: none`, and that removes the box of a descendant in the top layer while a modal descendant stays shown and inert (CSS Position 4, top layer, I): "open a dialog from a sheet button and close the sheet" and "a menu item opens an AlertDialog and the menu closes" would otherwise paint nothing and block input. A spec for each pattern. **The exit wait belongs to the executor** (L5): Rust's `close` command starts the closing state, the page waits for the element's animations to finish and then calls `close()`, and Rust's epoch fences a reopen. Rust cannot own the wait, because the `finished` fact would cross IPC and the invisible modal would keep the page inert for one to three frames; the wait is the one page-side step the Rust-side executor also keeps, as a bridge internal with an inventory row beside the watchdog.
  - **The only caller of show and hide for its element.** It suppresses the toggle events it caused and reports **browser-initiated changes** (light dismiss, Escape) back to Rust, reading `newState` on the page: `ToggleData` is empty and the HTML spec coalesces `toggle` tasks (a show and a hide before the task runs fire one event with old equal to new), so "Rust knows which state it asked for" misreads a light dismiss that follows an open. **On a gated surface its open step also clears the pending state, shows, reads the rects and reports `applied{gen, rects}`**: there is one show writer, which removes the contradiction between "the reconciler is the only caller" and a separate measured-show verb. `show_popover_measured` and `show_modal_measured` become internal to the executor for reconciled kinds, and `FORBIDDEN_VERBS` lists `showPopover` and `showModal` on them. A dialog's `close` event reaches Rust only through the executor's report (a separate bridge `listen` would carry no epoch and could close a reopen).
  - **Hydration and the pre-install window.** A hydrated page produces no attribute record (the hydration rebuild runs with `skip_mutations`), so convergence rests on the level read at install. The bridge loads after boot (section 5.2), so a server-rendered default-open panel is applied at install and reports queue on the page until the channel opens: a dismissal before the channel exists is not lost and the level does not reopen it. Behaviours have the same window on SSG pages: `otpFilter` sanitises the current value at install, and `reconcile` applies `indeterminate` at install.
  - It removes the lost or early command class, the stale toggle echo (row 115) and the two-writer `<dialog open>` trap.
  - One-shot calls (focus a cell, scroll an item into view, measure now) stay bridge calls carrying an element id as data; they have no level to reconcile.

**Admission is derived from the placement table, per effect: the counterfactual witness red, or, only where no probe in the available engines can observe the commit point, a cited platform rule row.** A declaration admits nothing, and a behaviour is not admitted as a whole: each effect it has is.
1. **The unit is the effect, at each Rust construction site.** The effect set is a type, not a check: effect-bearing parameters are typestate constructors (`Hotkey::<Prevent>`), so a construction with an empty effect set (`hotkey{prevent: false}`) is unrepresentable and that call site uses `listen`. A `const` check cannot do this job, because `Behaviour` is a serde enum with heap `String` fields (`bridge/behaviours.rs:46-66`), and `Decision<E>` is generated per kind, so TypeScript never sees a site's parameters (`behaviours.gen.ts:22`). `use_behaviour` is `#[track_caller]` and sends a **site id** with the install, plus the install's effect set, which the adapter enforces **per install, not per kind** (today its only per-install guard is passivity, `bridge.ts:691-699`). A debug coverage hook `__dxBehaviourCoverage` records (site, effect); the gate requires a witness per **site id** and effect, and stale entries fail, so a new site cannot borrow an old site's witness (a new `hotkey{prevent: true}` for a shortcut whose default is harmless would otherwise pass on L6's). A rider (`pan`'s per-move `setVar`, an `after(...)` loop, `otpFilter`'s `setValue`) is an effect like any other and needs its own witness.
2. **The effect vocabulary is closed and generated from Rust:** `prevent`, `stop`, `dataTransfer.{setData, dropEffect}`, `attrs`, `setVar`, `scrollBy`, `scrollTo`, `scrollIntoView`, `setValue`, `focus`, `capture`, `release`, `show`, `hide`, `setProp(indeterminate | defaultChecked)` and `after`; `send` and `remember` are exempt. `sameFrameWrite` is a deadline class, not an effect, and is retired as one: `stickToEnd` writes `scrollTop` (`scrollTo`), `settle` calls `scrollIntoView`, and the reconciler calls `show`, `hide` and sets the two properties. The built adapter's `attrs` effect (`bridge.ts:700-706`; it writes paint-relevant attributes such as `data-swiping`) is an effect like the others, not an unwitnessed rider. Each effect has one counterfactual and one probe:

   | effect | next-best placement (what the table does to it) | probe that must go red |
   |---|---|---|
   | `prevent` | dropped when the replayed event's target is outside the app (`body`, `document`, `window`); installed in the bubble phase at the Dioxus-rendered ancestor the event bubbles through otherwise (the rsx placement; this also checks a declared "capture phase" reason) | `defaultAction(occurred)`, or `outcomeOrder` |
   | `stop` | dropped | `outcomeOrder`: a later listener on the path ran (`stopPropagation()` does not change the canceled flag, W DOM <https://dom.spec.whatwg.org/#dom-event-stoppropagation>, so `defaultAction` can never go red for it and `dialogKeyForward` could never be admitted under it) |
   | `dataTransfer` | dropped | `outcomeOrder`: the drop target received the data or the drop was refused; run only on the engine where it matters (Firefox needs data set to start a drag of a non-link element, and Chromium starts the drag without `setData`), otherwise left to row 442 |
   | `attrs`, `setVar`, `scrollBy`, `scrollTo`, `scrollIntoView`, `setValue`, `show`, `hide`, `setProp` | delayed by R's modelled latency: provisionally 3 frames, set by the latency session's desktop distribution, never less than the row's deadline, counted in completed paints | `wrongPaint`, by trajectory inclusion (point 3) |
   | `focus` | delayed the same way | `focusAtNextInput`, the next key driven at the platform's key-repeat rate, dispatched at frame counts |
   | `capture`, `release` | delayed the same way: a capture applies at the next pointer event, so a late one loses the moves in between | `outcomeOrder`, on mouse and pen scenarios only (touch pointers are implicitly captured, W Pointer Events 3 <https://w3c.github.io/pointerevents/#implicit-pointer-capture>, so a touch-driven witness is green by construction) |
   | `after` | the re-entry routed through Rust (a `crate::sleep` and a command), the re-entered effects judged by their own rows | the re-entered effects' probes |
   | an order-ground decision (a close and a reopen, a step from a settled index) | the fact reordered after the next vdom event (point 7), or the Rust write delivered after a scripted native transition on its slot: a touch scroll, a dismiss, a find-in-page reveal, a form reset, an autofill | `outcomeOrder` |
   | a next-frame output | none in this container: the owner's measurement is the same counterfactual on hardware | `verdict.json` with a `reason` |

   `remember` and `send` stay synchronous, so a red cannot be an artefact of a corrupted state machine, except under the order counterfactual, which reorders a `send` by design.
3. **The probe is defined by the library, not by the behaviour's author.** A red counts only from a library commit-point probe (`wrongPaint`, `defaultAction`, `focusAtNextInput`, `outcomeOrder`, owned by the witness harness of item 0.6), never from a latency number, a spec-authored assertion or a predicate the author wrote.
   - **Trajectory inclusion is the one criterion for every write effect.** The harness records a library projection of the host subtree at the end of each frame, in both arms: rects, scroll offsets, computed `opacity` and `visibility`, and `document.activeElement`. A witness is **red iff the counterfactual arm paints a projected state that the real arm never paints** (an unplaced panel, a scroller not at the bottom while following). A lagging effect paints a time-shifted copy of the real trajectory and is green here: its row is then **next frame by derivation**, and only a `lag` or `order` verdict admits it. So the author no longer chooses between "before paint" and "next frame": the witness classifies. (An author predicate such as `wrongPaint(() => !effectApplied)` read one frame after the trigger is red by construction for any visible write, which is the spec-authored assertion of round 4 moved into the predicate.)
   - **Scenarios are replayed from the conformance vectors.** For every vector whose `expected_effects` contains E, the harness replays the event as a trusted CDP input on the construction site's host. The vectors are already required and proven against `decide`.
   - **The cancel counterfactual is derived from the event's actual target.** An author who declares a window or document target would otherwise buy the weaker test. For a cancel with no other placement the witness proves the cancel is *reachable*; that it is *required* is a product requirement, which the `adds:` row and the owner carry.
   - **A control arm.** Every witness is a pair: the same scenario with witness mode off must not throw, and with the effect moved it must throw; a probe that fires in both arms admits nothing. `WitnessViolation` can be constructed only inside `playwright/witness/probes/**` (a tsc-API ban with the machinery of item 0.1), and the static gate checks that both arms exist for each witness.
   - **Determinism.** The delay counts **completed paints** (a rAF, then a post-paint hop, n times), because `afterFrames(1)` called from a task lands before the same paint (`bridge.ts:337-340`) and a one-frame delay would then do nothing for a task-originated effect. The focus and capture probes dispatch their inputs at frame counts, not milliseconds (a wall-clock CDP key at a 33 ms repeat races a 2-3 frame delay). All behaviour observers go through one adapter-owned ResizeObserver dispatcher (behaviours are DOM-less, so they cannot create their own), and the probe hooks in after it, so a behaviour installed later never moves the probe's read ahead of its write.
4. **The platform rule row: the second, closed ground.** The witness cannot see a commit point outside the page or outside the container's engine. Browser-chrome defaults: O1 cancels F6 and V22 cancels Ctrl/Cmd+B, which in Firefox focus the address bar and open the Bookmarks sidebar (W, <https://support.mozilla.org/kb/Keyboard+shortcuts>), and headless Chromium has no such chrome. Engine rules that Chromium does not enforce: WebKit requires a clipboard write inside the user gesture (W, <https://webkit.org/?p=10855>), while Chromium keeps transient activation for seconds, so a call 3 frames late still works there and the witness would demote the effect and ship it broken on Safari and WKWebView (where the call arrives by `evaluate_script`, outside the gesture, I). **Only where no probe in the available engines can observe the commit point** may an effect instead be admitted by **one reasoned row**: a W citation, the engine, a `desktop-pass` or manual check line, and an owner-approved grant row at the merge base (a TSV `effect<TAB>site<TAB>citation<TAB>engine<TAB>check line<TAB>row`, read by `scripts/lib/allow.py`, stale entries fail, never a lane's own decision). **Where Playwright WebKit can observe it** (the clipboard case), the witness must run on that engine before the effect may be demoted. **Witnesses that serve other engines run under fallback emulation** (`stripAnchorSupportsBlock`, `overflow-anchor: none !important` and the A sheet removed; the specs already carry these switches): `stickToEnd` against `overflow-anchor` and the `dragSource` half are judged against the engine the effect exists for, since on a current Chromium anchoring keeps the bottom natively and the delay witness would be green. A witness that turns green later (an engine gains native support) opens a backlog row and is quarantined, and does not block the deploy; **demotion requires green under fallback emulation, or a Firefox or WebKit run** (row 442).
5. **Where a green witness lands.** A green witness sends the effect to R, and R has no `focus` or capture verb (section 5.2), so the landing is stated: a green `focus` or `capture` witness adds a **caller-listed verb row keyed to the witness id** (as `focus_prevent_scroll` is), which `FORBIDDEN_VERBS` admits only from that row, and a green witness may not send the effect to a banned verb (it routes to the focus owner, or to rsx). Demotion is one effect at a time, re-running the remaining witnesses on the demoted tree, because single-effect knockouts miss redundant pairs (L6's document-level Escape `prevent` and L2's rsx `oncancel` `prevent` on a modal `<dialog>` each stop the close: both knockouts are green and demoting both breaks it); the gate records the order.
6. **Bridge internals are admitted like behaviours.** Admission covers **every effect the shipped TypeScript applies outside a verb row**, behaviour or internal: the runtime modality writer (a capture `pointerdown`/`keydown` writer of `html[data-dx-modality]` that the ring CSS and `openFocus` read in the same event), the executor's exit wait, G's watchdog and the `pageObserver` discovery, the toggle-event suppression, the epoch minters, the focus owner and the transition port. Each gets its witness pair in the same harness (the watchdog: dropped, so the CSS fail-open alone, red with `animation: none !important`; the exit wait: Rust waits for a `finished` fact, red because an invisible modal holds the page inert; the modality writer: Rust writes it from a root handler, red because a ring flashes after a mouse click), and the identifier scan of `bridge.ts` maps every effect site to a verb row or a witnessed internal. Still outside, honestly: class (c) (`PREPAINT_JS`, `index.html`, `theme_seed`, where no counterfactual exists before wasm loads) and the hub's one `addEventListener`, which is mechanism with no effect of its own.
7. **The order counterfactual is built page-side, in the channel wrapper** (`bridge.ts:342-360` is already the seam), so phase 0 needs no patched build. In witness mode a fact is held until the next trusted event of a Dioxus-delegated type has finished dispatch and is then released; across sessions it is released in reverse scope-height order. On web the Dioxus handler runs inside dispatch (`dioxus-web-0.7.9/src/dom.rs:88-116`), so this reproduces desktop's "event inline, fact later". Row 442's desktop-cadence build remains the fidelity check, and a second SSG build per deploy (a fourth 3.6 GB tree) is not needed. `reconcile` is decided **per kind**: a delayed popover open paints nothing wrong (`display: none`), a delayed `indeterminate` paints the wrong glyph (off-trajectory, red), and `defaultChecked` never paints. A Rust `transaction` is a list of closed verb rows and has no op that runs a behaviour program, so where the executor is a `transaction`, `openFocus` either becomes an op of it or the open step keeps its focus part page-side.
8. **Witnesses run; they are not records.** Each witnessed effect is a `witness(kind, effect)` test that wraps `test.fail()` and passes only if the error is the probe's typed `WitnessViolation` (a timeout or a locator error fails the witness, which removes the trivially red route; Playwright 1.60 fails a test whose status differs from the expected one, `workerProcessEntry.js:2555`, so the wrapper is sound). They run in `test:changed` and in the deploy's release suite, and `tools/select.mjs` gets a rule that maps each `playwright/witness/**` spec to its behaviour's files (a change to `bridge/behaviours`, `conformance/behaviours` or `ts/witness.ts` otherwise maps to shared plumbing, the broad set, once more than 30 components use the bridge). **Witness mode is not in the release bundle:** it lives in a separate bundle behind a non-default cargo feature (the `legacy-impl` pattern), because a global switch that disables `preventDefault` must neither ship to users nor be reachable by a page script, and its bytes would count against the ratchet; the deploy suite builds the witness variant. Behaviours `export const decide` and the adapter registers them, because `ts/lib/register.ts:8` reads `window.__dxBridge` and breaks the DOM-less compile. **A lane cannot admit its own behaviour:** the witness test (or the platform rule row, or `verdict.json`) must exist at the merge base under the grant-row rule, and a witness for a not-yet-built variant lands first as a `test.fixme` keyed to the variant's existence in `behaviours.gen.ts`, hash-checked at the merge base, which the lane then flips to live.
9. **Cost (I):** about 45-50 witnesses, 90-100 tests with the control arms, about 5-8 worker-minutes (3-4% of the suite: 3.1 s per test at two workers plus a fresh page per arm, inside the 4,787 s headroom of section 5.4), plus the `select.mjs` rule and the `playwright/durations.json` entries that item 0.6 and each consuming row add.

Round 3's two grounds (a detected effect, or a late-arm witness on a whole variant) and round 4's single ground (the witness alone) are both superseded by the sentence above. Admission subsumes the next-frame special case, riders, `hotkey{prevent: false}`, the order condition's page-side owners and the unchecked "capture phase" reason. It does not subsume the fidelity of the desktop latency and reorder models before row 442, or the owner's budget. **Consequence for phase 0:** item 0.6 owns the prototype reconciler and the first two witnesses (`witness(hotkey, prevent)` as a `test.fixme` until item 0.3 builds the variant, and `reconcile`'s, per kind), because a lane cannot admit its own behaviour (point 8); item 0.4 builds the executor those witnesses select.

What admission decides, per effect (the witnesses are run by item 0.6 and the first consumers): `hotkey` (`prevent`): L6's one web caller is a plain `div` dialog (`dialog.rs:442`, `DialogContentNonModal`), on which Escape has no in-page default action, so its witness needs the nesting scenario from the vectors (the div layer over a native dialog or popover, whose close request is observable); O1 (F6) and V22 (Ctrl/Cmd+B) cancel browser-chrome actions that no in-page or headless probe observes, so each is a **platform rule row**. `scrollLock` (`prevent`), `otpFilter` (`prevent`, `setValue`), `dropAnywhere` (`prevent`; its `dataTransfer` half has its need on Firefox, so it is a platform rule row or a row-442 witness, expected green on Chromium), `pan` (`capture`, `release`, `prevent` for C4's click suppression) and `dialogKeyForward` (reserved: `prevent` under `defaultAction`, `stop` under `outcomeOrder`) are expected to be red under their counterfactuals. `settle`, `stickToEnd` (judged under fallback emulation), `openFocus`, `scrollOwner` and `roving` (the `scrollTo`, `scrollIntoView` and `focus` effects) are admitted only if their probes go red. `scrollStep` is a `transaction` (`scrollBy` with snap suspended in one JavaScript turn, plus `listen(scrollend)`) unless its witness is red; `settle` must show its witness (W3's loop spans many frames, so its row is next-frame unless the witness says otherwise); `place` exists only if its witness is red, and `wheelBand` only if the owner's C5 verdict has the reason `lag` or `order`; `reconcile` is decided first, per kind (above). A clipboard write (V14, a copy button) is a platform rule row on WebKit's gesture rule, and a registry behaviour only if the owner wants a library copy button (`copyText`, section 2.2 registry notes). The size of the budget the witness uses is the owner's number and is not decided here.

**Verbs, the move to rsx, and composition order.**
- **Verbs are single member calls.** Each row of a closed table (`METHODS`, `PROPS`, the property setters, `EVENTS` getters) is one arrow function whose body is one member call or one member read on its declared receiver kind, with arguments drawn only from typed fields, **and at most one guard `if`** (the landed `showPopover` row guards on `typeof` and `:popover-open`, and `close` branches on an argument; anything larger is a registry program with a row and vectors); a gate checks every row on the canonical form (section 5.3). **A program is a behaviour, not a verb:** L16's open-focus policy (`dxOpenFocus`, 114 lines that branch on modality, editability and author choice) is the case `openFocus` exists for. **Reducers** (emit only when a named derived key changes, RTL normalisation of scroll facts, pointer-type change, W8's wheel-intent classification) are a closed `REDUCERS` table of the same shape, an option of `listen`/`observe`, never a behaviour; a reducer that needs state over a stream is `stickToEnd`'s or Rust's.
- **When Dioxus delivers it, a behaviour moves to rsx.** Every variant declares its reason as data (window target, missing event, listener option; a "capture phase" reason is checked by its witness, whose counterfactual is the bubble install at the element), and a `cargo test` reads the locked `dioxus-html` event list and fails when a "missing event" reason has appeared (0.8's `onbeforeinput` moves `otpFilter`'s cancel half).
- **Composition order.** `prevent` is monotone, so preventers commute. A behaviour that reads `defaultPrevented` (V22) is bubble-phase and installed at a (target, phase) strictly after every behaviour that may prevent the same type: readers at window-bubble, preventers at capture, element or document-bubble. One cross-behaviour vector file (`scrollLock` held plus a `hotkey` on a scroll key) covers it.
- **An rsx handler takes only `prevent_default`** (section 1.4, item 4), and a gate says so: clippy `disallowed_methods` on the `DataTransfer` setters (`set_data`, `clear_data`, `set_effect_allowed`, `set_drop_effect`) by def path, because on desktop they are silent no-ops with three shipping sites, and on the `MountedData` writes (`set_focus`, `scroll`, `scroll_to`, `scroll_to_with_options`), which the order contract routes through the focus owner and the scroll owner. `stop_propagation()` is not a commit effect either: it affects vdom bubbling only (section 1.2), so a dialog's `onkeydown` that calls it cannot hide the key from a document `hotkey`.

**How a behaviour is built.**
- **A pure `decide(config, memory, snapshot, event) -> Decision<E>` plus a thin DOM adapter** that builds the snapshot and applies the effects. `Decision<E>` is generated from the Rust effect set of the construction site, so returning an undeclared effect is a `tsc` error (admission, point 4). Conformance vectors are `{config, snapshot, event, expected_effects}` triples run by `bun test` against `decide()`; `cargo test` reads the same file against the generated types and, where a behaviour has a Rust twin (C5's classifier), against it. **Vectors prove `decide`; the DOM effects are proven by specs.** Without the split the vectors would test serde field names and nothing about decisions. `bun` may be absent: the gate then prints "bun tests: skipped (no bun)", never a pass.
- **The adapter is wider than lane 3.0's skeleton** (that adapter takes one event per install and a `{prevent, stop, attrs, send}` decision, which fits `hotkey` only: about 985 of the roughly 1,000 behaviour lines need more, [execution F2](./board-2026-10-26-r2/execution.md)). It is extended without changing the construct, by the row that first needs each extension (item 0.3 for `hotkey`, then each behaviour's row, section 5.0): a list of `{target, event, capture, passive}` per behaviour, a per-install memory object passed to `decide`, snapshot readers chosen from a closed list (`scrollableAncestor(axis, dir)`), and a closed effect vocabulary (`capture(pointerId)`, `release`, `scrollBy`, `setVar`, `setValue` with selection, `focus`, `after(frame|ms)` which re-enters `decide`; the complete list, generated from Rust, is in admission point 2).
- **The Rust enum and the TypeScript registry stay one to one by generation, not by parsing.** `cargo test` writes and compares the committed `behaviours.gen.ts` (kind union, verb enums, field names, effect sets, vector schema version); the registry macro collects one Rust file and one vectors file per behaviour (`bridge/behaviours/<kind>.rs`, `primitives/conformance/behaviours/<kind>.json`) and a missing sample or vector is a compile error, so no central match is edited by two lanes at once (the as-built `info()`, `declared()`, `module()` and `samples()` are four no-wildcard matches in one file, `bridge/behaviours.rs:124-200`); `bun test` asserts `Object.keys(HANDLERS)` equals the generated kinds. No `String`-typed field of `Behaviour` may be code.
- **Phase, target and passivity are declared**, never inferred: `capture-at-el`, `bubble-at-doc` or `window`. `defaultPrevented` is legal only in a bubble-phase behaviour. The `stop` effect is legal only in `capture-at-el` (desktop never forwards `stopPropagation`, and a window-capture stop would starve Rust's own handlers on web). Non-passive `wheel`/`touchmove`/`touchstart` exist only while a behaviour whose effect set contains `prevent` is installed, and go with the last one. The listener-inventory baseline is unchanged.
- **Every behaviour has a fail-open path and an epoch: a lease, mandatory for `prevent` and `stop`.** A behaviour that prevents an event and then relies on Rust to act must stop preventing when Rust stops answering (WCAG 2.1.2: a wedged Rust runtime must not trap the keyboard). The built mechanism is a **lease**: Rust renews it at half its length with a `sleep` loop, and an unrenewed lease expires on the page. A lease is a heartbeat, which also covers a stalled render, a hidden webview and a dead channel with no per-event traffic, where a per-event acknowledgement would not; it covers "Rust stopped", not "Rust is alive and wrong". It is **mandatory for any variant whose generated effect set contains `prevent` or `stop`** (a gate on the generated file; the landed lane-3.0 branch makes it an optional `lease_ms`, so a `prevent` variant with none passes every gate), is sized above one render plus its acknowledgement in the worst case, and a hidden webview expires it by design and the next renewal reinstalls it. A spec at the stuck-channel setting (the bridge-latency harness's `__dxBridgeDelayFrames = "never"`, landed on lane/js-bridge-3-0; the desktop-cadence harness repeats it as `N=never` once row 442 lands) asserts per `prevent` behaviour that Escape on an open dialog still closes it natively. The watchdog is page-side because a stalled render stops every Rust timer (section 1.4, item 7). Every Rust write carries `based_on`, and the slot owner drops a stale one (order contract, section 2.2).
- **Lifetime belongs to the Rust scope that installed the behaviour, with a page-side backstop.** The registry holds rules in a `WeakMap` or on the element, never in a strong `Map<id, rule>`; a `WeakMap` releases memory, not a `window` listener's registration, so every behaviour also checks `host.isConnected` (the element it is installed for) at install and on each delivered event and tears itself down when the host is gone. A leak spec mounts and unmounts a host 200 times and asserts the registry is empty, plus a "host removed without a teardown message" case.
- **Public API.** The hooks and behaviour types are public in `dioxus-primitives`: preview components (V22, V17) and installed components use them. `check-installed-paths` and `cargoDependencies` expectations cover them, and an installed component's Rust files contain no sink (section 5.3).

**What a behaviour is not.** A stateful heuristic over a stream (C5's trackpad classifier, W8's mode machine) is R, not a behaviour: both are passive or paint-safe, so they can answer late. W8's same-frame follow is the one part that is not R, and it is `stickToEnd`. If Rust loses C5's measurement, the heuristic becomes the named behaviour `wheelBand`, admitted by a verdict with the reason `lag` or `order` (admission, point 3). A new behaviour is a backlog row that **exists at the merge base, is open and names the kind in its `adds:` front matter** (section 5.3), a named variant, a vector, a witness test, a spec tag and a budget row; a new verb (one table line that passes the single-member-call check) is not.

### 2.3 (G) Paint-safe gate: turn "same frame" into "bounded latency", hardened three times

Same-frame is *sufficient* but not *necessary*. What is necessary is that **no frame paints a wrong state**. If the unsettled state is invisible or pinned, Rust can measure and write whenever the answer arrives. The construction after round 1 ([root-and-timing 2](./board-2026-10-26/root-and-timing.md), [block-mapping F5](./board-2026-10-26/block-mapping.md), [ux-a11y-perf F2, F7](./board-2026-10-26/ux-a11y-perf.md)) and round 2 ([platform-desktop 3-5](./board-2026-10-26-r2/platform-desktop.md), [blank-slate 5](./board-2026-10-26-r2/blank-slate.md), [execution F9](./board-2026-10-26-r2/execution.md)):

1. **The gate is the absence of a Rust answer, derived from `open`, on the surfaces where Rust owns the position.** A panel is pending while it is open, not placed by the platform, and not yet answered: `html:not([data-dx-anchor="a"]) :popover-open:not([data-dx-placed])`, with a `dialog[open]` twin only for a dialog that Rust places (none today; a CSS-centred modal is never gated). **The engine predicate is the page-owned probe attribute `html[data-dx-anchor]`** (section 2.1): the probe classifies, the attribute is written at bridge load and at first idle by the probe's closed setter row, and its absence counts as fallback, so the gate is armed before the probe answers. `data-dx-anchored` (written by `top_layer/attributes.rs:142-159`) is a vdom attribute that Rust writes **unconditionally** for every anchored popup today, so it cannot carry the engine tier (a client-only probe result cannot reach it without a signal round trip, and the first popup can precede the probe). It **becomes conditional**: Rust writes it only while the probe signal says `a`, so the engine sheet's anchoring rules and the gate agree, and it is no longer the gate's predicate. A surface that Rust places on every engine (Select's item-aligned list, S1; the iOS keyboard clamp) declares `engine: always` (item 5) and its pending selector drops the `html:not(...)` term, so the engine predicate never leaves it ungated. Pending needs no write, so every Rust-placed open path is gated by default.
   - **The clear is the executor's open step,** one JavaScript turn that clears `data-dx-placed`, calls `showPopover()`/`showModal()` and reads the rects (section 2.2: the executor is the only show writer). It is not a `beforetoggle` listener: `beforetoggle` does not bubble, is absent for `<dialog>` on Chrome before 132, Firefox before 133 and Safari up to 18.7, and a document capture listener would be a page-lifetime listener outside the registry and `listener-inventory.spec.ts`. Every library open is Rust-driven; native `popovertarget` appears only in preview demos with no placement attribute. If the owner wants native opens gated too, that is a registry behaviour (`gate`) with a vector, a budget row and an inventory entry.
   - `toggle` is a queued task that runs after a paint, so it cannot start a gate.
2. **The pending style selects its own animation and leaves no enter keyframe applying.** The theme's enter animation is `forwards` and runs `opacity 0 -> 1` (`dx-components-theme.css:1775-1818`); an animation declaration outranks a normal one, so a one-line `opacity: 0` hides only while the animation is paused at t = 0, where it also keeps the 0% keyframe's `scale` (S1 would read a transformed rect). Pending therefore selects **its own fail-open animation name** (`dx-gate-failopen`: delay `--dx-gate-timeout`, `forwards` fill, one keyframe `to { opacity: 1 }`), with `opacity: 0; pointer-events: none` before it. No enter keyframe applies while pending, so the geometry is untransformed. **Not `animation: none`:** that would kill the fail-open. `animation-play-state: paused` is rejected for the same reason. When Rust answers, the placed state selects the enter animation by name; the swap restarts it from 0, so the fade is clean (a live `animation-delay` change would instead jump a running animation 20 to 60 percent in). The reduced-motion rule shortens durations only (`dx-components-theme.css:1785-1790`) and must not touch the delay.
3. **Fail open twice: in CSS and on the page.** The CSS animation of item 2 opens the panel after the timeout (at most about 100 ms for a placement-critical gate; lane 3.PL fixes the number by measurement). Host CSS can defeat it: the theme itself ships `[data-dx-motion-key] *, ... { animation: none !important }` under `prefers-reduced-motion: reduce` (`dx-components-theme.css:2421-2432`), which matches popups rendered as descendants of a motion-key host (the popup-boundary class), and common user resets do the same. So the gate has a **page-side watchdog timer** of the same length that clears the pending state. **The watchdog belongs to the gate, not to the executor:** the bridge's one boot-installed `pageObserver` scans for every node that enters a declared pending state, so it also covers the states no open step reaches (O3's pre-measure state, V19's pre-measure state, W8's opening position) and keeps working when the executor is a Rust transaction. It is page-side because a Rust timer cannot be the alternative: a wedged or unacknowledged render stops every task (`webview.rs:563-572`).
4. **One epoch rule** (the order contract, section 2.2; on the wire the field is `gen`). The command attribute carries `(scope, state, based_on)`; the executor's open step reports `applied{gen, rects}`, `gen` being the slot's page epoch at the open; Rust answers with `data-dx-placed` carrying that `gen` as its `based_on`, and the page drops (removes, in the same microtask checkpoint as the observer that sees it) a `placed` whose `gen` is older than the slot's last page transition (a dismissal or a reopen since the open) before paint, on the fail-open path too. A stale answer would otherwise be visible the moment its attribute exists, because the CSS shows the panel on `[data-dx-placed]`. A Rust decision that follows a transition it has seen is a changed attribute value, so a record exists without `volatile` (section 2.2). This is the same race class as `__dxDialogGen` in `lib.rs` and the "no cleanup of data-placed-side" comment in `anchor_fallback.rs`, with one epoch mechanism for commands and the gate. **Writers:** Rust writes the command and the answer; the page's only write to an attribute Rust owns is the removal of a stale answer, by generation. The invariant is fixed here; lane 3.PL settles the literal wiring with the first-frame spec. Spec: open, close, open within one task, at the delay settings N = 0 and N = 2, a stale answer, and unmount before the answer.
5. **Two paint tiers, by what a wrong paint costs.**
   - **Placement-critical: gated.** Only where Rust owns the position: engines below a floor or failing the boot probe (the fallback engine), and the iOS keyboard clamp (row 210). `opacity: 0` until placed.
   - **Decoration: never gated.** The placed side, arrow offset, `transform-origin` and available height open with the neutral defaults and update when Rust answers, after the tooltip's `:not([data-placed-side])[data-side]` precedent. The enter animation is origin-independent for its first frames (opacity first), so a late origin never shows as a wrong-corner pop. Without the split every popup open would pay two to four frames on desktop (I), on the engines where A already did the work.
   - **The per-surface list.** The theme's enter animation belongs to `[data-dx-surface="floating"][data-state="open"]`; the navbar, the navigation menu and the toast animate differently (`navbar/style.css:147,219`, `navigation_menu/style.css:194,218`, `toast/style.css:176,216`), so the name swap of item 2 is declared per surface in a list that lane 3.PL owns and the gate checks. Every gated surface declares its paint tier, its **`engine: always|fallback`** (`always` for the iOS keyboard clamp, which no engine probe removes; `fallback` for placement that A does where the probe passes), its timeout and its animation names.
   - **The scrim** of a gated dialog is not part of the pending style; it either shows for up to the timeout with no panel or is gated with it. 3.PL declares which.
6. **Gate only what is pending, never a visible panel.** Re-placement on resize or keyboard paints a frame late, a stated degradation (the reserved `place` behaviour is the exit, section 2.2). Where A places the panel, only the Rust-dependent part is gated.
7. **Show plus measure is the executor's open step, which returns the rects** (section 1.4): they are read page-side in the same JavaScript turn and reported with `applied{gen, rects}`, not through `MountedData`, so a getter that never completes (Dioxus #5734, reported on Ubuntu desktop) is not on the critical path. There is no separate measured-show verb for a reconciled element: `show_popover_measured` and `show_modal_measured` are internal to the executor.
8. **Pending states are opacity-only.** A pending selector may declare `opacity`, `pointer-events`, the fail-open animation name and the delay, and nothing that leaves the accessibility tree or blocks focus: not `visibility`, `display`, `hidden`, `inert` or `content-visibility`. Focus must enter an `opacity: 0` panel (`modality.rs:108-165` has no visibility test), a toast's `role="alert"` insertion must still be announced (`toast.rs:1517-1535`), and VoiceOver reading a panel from its frame is on the manual checklist. A click in the panel's future area during the pending window falls through to the page (and light-dismisses a `popover=auto`): negligible at 0-2 frames, real during a 100 ms fail-open.

**Latency.** On web, for a pre-paint trigger (UA events, timers, rAF and ResizeObserver callbacks): zero extra frames, all microtasks. Post-paint triggers (`onvisible`, `toggle`, `close`) already cost a frame. On desktop (web-verified; desktop inferred): at least one frame, typically two, and one per sequential awaited read (section 1.4). **On the Apple-desktop fallback engine G costs two to three frames plus IPC** (event, render, rAF edit, acknowledgement, the open step, the reply over IPC, render, rAF) **against today's in-turn placement**, and Safari 26 WKWebView is the current WebView for months, so G is the default experience there and a strict slowdown. Before 3.PL starts, `g-latency` is measured on a WebKit desktop build and the fallback engine's default is decided between G and the reserved `place` behaviour (an in-turn re-place); both are mappings of T8, not a change of construct.

**Not for continuous loops.** A lagging write during scroll or drag *is* a wrong paint. G is for open-time, insert-time and swap-time work only. A same-frame write that tracks a stream (W8's follow-bottom) is not G: it is A where the platform does it and `stickToEnd` everywhere, idempotent with A (section 2.2). Continuous tracking goes to A. B and R run on the main thread and are a frame or more behind the compositor, so they are never "frame-exact" against scroll.

**Proof.** A first-frame spec asserts the panel is `opacity: 0` with no enter keyframe applied while pending, that no frame paints `placed` with stale geometry, and that a modal dialog and an A-placed menu are never hidden; `g-latency` measures frames from input to first visible panel (at most 1 at N = 0, at most 3 at N = 2); the stuck-channel run shows the fail-open, **including a case with `animation: none !important` on an ancestor** (the watchdog opens it); a boot-probe spec runs the probe set against a forced-failing engine and asserts the pre-probe default is fallback; an executor spec covers a vetoed close, a stale epoch and an `applied{gen, rects}` for each gated surface, and a watchdog spec covers a pending state that no open step reaches (O3, V19, W8's opening position).

### 2.4 (C) Running Rust in the page

- **C1, Dioxus's own sync event path (V).** It works on web and desktop/mobile, as section 1.2 shows. **It is the first row of the placement rule's default-action deadline**: use it where the decision's only commit-time effect is `prevent_default()` and Dioxus delivers the event and every field the decision reads (this is already the house style: 133 `prevent_default()` calls in `primitives/src`). As a *trampoline* for window/document/capture cases, where the bridge re-dispatches a cancelable synthetic event to a vdom "port" element and reads `dispatchEvent()`'s return value, it is **rejected**:
  1. The synthetic event must be a type Dioxus converts (keydown, or a `CustomEvent` `resize` with a fake `detail`), which is an abuse.
  2. Other capture listeners see it, so the modality writer would mark keyboard modality.
  3. Desktop pays one blocking XHR per event, which is unacceptable for wheel or touchmove at 60-120 Hz.
  4. `stopPropagation` reaches the DOM on no renderer.
  5. Desktop is not in CI.

  Dioxus 0.8.0-alpha.1 adds `onbeforeinput` (audit section 3, W). With it, S11's cancel half becomes a plain rsx handler once fields and sync cancel are verified (I).
- **C2, a Rust kernel compiled to page-side wasm (I).** Every target webview runs wasm (Baseline high). **Against it:** Chrome refuses synchronous `new WebAssembly.Module` for buffers over 4 KB on the main thread (W, web.dev "Loading WebAssembly modules efficiently"), so loading is async; it needs a second build artefact plus a reproducibility gate; every input still needs JavaScript glue. **Verdict:** not now, and **not C5's exit**: if Rust loses the C5 measurement, C5 becomes a named behaviour admitted by a `lag` or `order` verdict (section 2.2, admission; section 4).
- **C3, worklets and workers.** AnimationWorklet and the Layout API have not shipped. A paint worklet is Chromium-only and cannot cancel events. Workers have no DOM. Rejected.
- **C4, "the bridge is microtask-synchronous on web" (V components, I end to end).** True for UA-dispatched events and rendering-step callbacks. **Not a construction:** it fails on desktop/mobile and for script-dispatched events, and would break if dioxus-web re-enabled its idle/rAF scheduling (the TODO at `lib.rs:250-262`). Its one use is to explain why G costs nothing extra on web, and why a Chromium-only CI cannot reveal desktop latency bugs (section 5.6).

**Nothing in class (d) stays as a bespoke per-component script.** What stays page-side is the bridge, the transport seam, class (c) (pre-wasm `PREPAINT_JS`, the `index.html` scripts, the inline copy buttons: they must run before wasm) and the **closed registry** of section 2.2. The modality writer's runtime copy is part of the bridge's load, not a script of its own.

The switch is one function with two `cfg` bodies and everything else is unconditional, and the cargo gates gain a `-p dioxus-primitives` clippy and test arm without the feature (or `cargo clippy -p dioxus-primitives --no-default-features --features web`).
- **Removal is keyed to the measurement's verdict, not to a date and not to the stamp's existence.** The owner's measurement leaves `research/measure/<port>/verdict.json` (`{"verdict": "pass" | "fail", "reason": "parity" | "lag" | "order" | "integrity", "devices": [...], "traces": [...]}`; the raw traces sit beside it as `<arm>-<device>.json.gz`, the kit writes it from the owner's dump, and only the owner commits it). Each legacy file is an allowlist entry with its row; the gate fails when the port's verdict is `pass` and the legacy file is still tracked. A `fail` verdict deletes nothing. A `fail` with the reason `lag` or `order` is the admission witness of the named behaviour that replaces the Rust arm (for C5 `wheelBand`), which is promoted into the registry (its row, `adds:` front matter, vectors) instead of removing the legacy file; a `fail` with `parity` or `integrity` means the Rust arm is to be fixed and the legacy arm stays frozen without being promoted. A failed measurement can never force the fallback to be deleted. A calendar `expires:` date would turn `run-gates.sh` red for every branch in the repo after the date, including ones that touch nothing near the carousel, and a late measurement would trigger it. `js_macros.rs` is deleted by the legacy removal lane, not by a main-loop cleanup after the ports.

## 5. The proposal

### 5.0 Scope: what is built now (owner decision pending)

Round 3's coherence member separated two goals this plan had merged. The **construct** is what makes the class unable to recur; the **port** removes the existing instances. The construct needs neither batches 1 to 4 nor the feel-critical ports: every legacy block can sit behind a per-site `#[expect]` and a frozen baseline row until it is touched (section 5.3, items 1 and 12).

**The construct:** the one eval sink (the `Program`-typed transport of lane 3.0), the ratchet with grant rows, the deadline rule with its four rules, admission per effect, by counterfactual witness or platform rule row (with the witness harness, item 0.6), the order runtime (item 0.7), a legacy-literal freeze, and **two proof ports** that exercise both kinds: a listener (dead JavaScript, `hotkey` for L6) and a command (the executor for T4 to T7, whose witness decides whether it is a page reconciler or a Rust `transaction`).

- **Scope 2. - **Scope 3. Construct only, port on touch:** the legacy-literal freeze makes an edit of a legacy script a port, so nothing else is scheduled.

### 5.2 The bridge surface is closed

Lane 3.0 builds the verbs; these rules close them, and the row that first needs a missing verb adds it with its own grant (3.0b is the gate half of item 0.1, not a verb sweep) ([gates-and-proof 2](./board-2026-10-26/gates-and-proof.md), [root-and-timing 5, 6](./board-2026-10-26/root-and-timing.md), [simpler-alternative 5](./board-2026-10-26/simpler-alternative.md), and in round 2 [enforcement 1, 6](./board-2026-10-26-r2/enforcement.md), [execution F1, F2, F16](./board-2026-10-26-r2/execution.md), [core-construct 2, 3](./board-2026-10-26-r2/core-construct.md), [platform-desktop 6, 8](./board-2026-10-26-r2/platform-desktop.md)):

- **No `el[method](...args)`.** `call`, `get`, `set` and `listen` take **closed Rust enums** (`Method::ShowPopover`, `Prop::Rect`, ...) mapped through **closed TypeScript tables** (`const METHODS = { showPopover: ... }`), dispatched with an own-property check, with a **receiver kind per row** (an element method cannot be called on `window`). Otherwise `call(window, "setTimeout", ["code"])` is an eval. `set` of a custom property accepts only names that start with `--dx-`. Parity between the Rust enums and the tables is the generated golden file of section 2.2, not a text parse.
- **A verb is one member call.** Each row is one arrow function whose body is one member call or one member read on its declared receiver kind, arguments from typed fields (admission, section 2.2). The landed rows already hold logic (`showPopover` guards on `typeof` and `:popover-open`; `close` branches on an argument), so the gate caps a row at one expression plus at most one guard `if`; anything larger is a registry program with a row and vectors.
- **The transport is typed, not a string seam.** A `pub(crate)` `open(body: &str)` would let any module run an arbitrary script with no `eval` identifier in its file: a renamed sink, not a closed one ([enforcement 1](./board-2026-10-26-r2/enforcement.md)). **As landed on `lane/js-bridge-3-0`,** `Program` is an enum (`Serve`, `Pump`, `Legacy(&str)`) whose scripts are built inside `bridge/transport.rs`, and the transport is `pub(in crate::bridge)`; `Legacy(&str)` carries the `js_listener.rs` script bodies, is constructed only in `bridge/legacy.rs`, and goes with that module. **Planned (item 0.1):** `Program::Frozen{module}`, the closed list of frozen module ids; the sink gate's check that every argument is a `Program` constant plus `serde_json` output; and a shrink-only callers table with one reasoned row for `js_listener.rs`.
- **Ordering of element operations is a property of the transport, not a lane rule.** Element operations issued while a handler runs are queued and flushed with `dioxus_core::queue_effect`, after the edits of the render that issued them (the mechanism dioxus-web uses for its head insertions, `dioxus-web-0.7.9/src/document.rs:1,125-161`), through one pump, so they are FIFO. Commit-sensitive work never needed "issue now": it lives in behaviours. `transaction(ops[])` stays for atomic results, `commit()` is **dropped** (section 1.4), the web-only flush between renders is a forced style read, and ref-counted installs and removals cannot reorder, so a non-passive listener cannot leak (rows 149/159). A stuck-render spec with the bridge-latency harness (`?dx-bridge-delay`, `__dxBridgeDelayFrames`) covers it. **As built (lane 3.0), only element operations share the pump:** every hook's `Session::open` opens its own `Program::Serve` eval and sends its commands from an effect, `JsListeners` opens one eval per script, and `ensure_module`/`ensure_installed` are separate evals; order across them is the order of the `evaluate_script` calls, and `pending_effects` pops the lowest scope height first, so a root-owned flush effect runs ahead of its descendants' effects. The consequence is small (installs and writes are issued from effects after the acknowledgement, and webview evals are ordered), so the claim is "element operations are FIFO", here, in `js-interop.md` and in the transport doc, and not "all Rust-to-JS traffic"; carrying session commands as pump messages is the alternative if a case needs it. **`MountedData` is a second Rust-to-page channel the pump does not order** (on desktop each call is its own webview query, `dioxus-desktop-0.7.9/src/query.rs:45-60`): a decision may not depend on a `MountedData` call arriving before or after a bridge message. The order contract (section 2.2) is the rule for both channels, and `onmounted` is also a cost class of the hot-events gate. **Page-to-Rust facts are not carried by sessions:** every one goes through the one inbound pump (section 2.2, order contract), so sessions keep only their outbound commands.
- **`passive` derives from the behaviour.** `listen`/`subscribe` streams fields, so it cannot cancel: it is always passive for `wheel`, `touchstart`, `touchmove` and `scroll`, and the TypeScript ignores a request for otherwise. A listener is non-passive only while an installed behaviour's effect set contains `prevent`.
- **Event volume derives too, and a stream is bounded per frame.** `pointermove`, `mousemove`, `wheel`, `scroll`, `touchmove`, `resize`, `drag` and `dragover` have no raw mode: a frame-coalescing mode, or a flush per event task for C5, which needs every event with its own timestamp (batched, not coalesced: its notch and decay rules compare consecutive events). `sample(el, fields, until)` is armed only while a gesture or condition holds; C5's `pointermove` must not live for the carousel's whole mount (`wheel.rs:578`). **As built, `listen` and `sample` are latest-wins per frame: at most one message per frame per stream, with no acknowledgement** (`observe` has no coalescing); the "one message in flight" wording of earlier versions is withdrawn. A batched mode carries a cap and a drop-oldest rule that records the loss; high-rate Rust output goes through `set` (CSS custom-property batches), not a message per frame. An in-flight window (Rust acknowledges a stream sequence number) is added only if `bridge-cost`'s "Rust busy 30 ms at 120 Hz" case shows the backlog matters; a stream that must order against vdom events carries a sequence number or has both sides on the bridge (L30's start, move and end all go through one bridge session, so it is ordered; mixing a bridge move with a vdom `onpointerup` is not, and facts of two sessions are not ordered against each other either, so the facts one decision combines share one session or one inbound pump, section 2.2, rule d).
- **Hot events stay off the vdom, counted per event name.** A vdom `on*` handler is for an event that needs Rust's synchronous `prevent_default`, or that fires at human rate. `scroll`, `resize` on many elements, `pointermove`, `wheel`, `touchmove`, `mousemove` and drag events go through bridge `listen`/`observe`/`sample`, async and batched. A reducer option (`emit` only when a named derived key changes, a row of the closed `REDUCERS` table of section 2.2) keeps a stream from posting a message per event. Dioxus registers one root listener per bubbling event name with no options, so one `onpointermove` or `onwheel` anywhere makes that event a blocking, non-passive request app-wide: the gate counts **event names across the app** (a per-event-name allowlist, not per file) and adds `onmounted` as a cost class (a per-row handle needs a batched observe alternative or one container handle). It applies to W1, W8, O3, lane 2C's S2/S3 and every site listed under lane 3.HV (section 5.4), and its scope includes `preview/src/components/**`. Enforcement is section 5.3, item 8.
- **Closed tables carry the rows the later lanes need; the row that first needs a verb adds it, with its own grant.** There is no pre-granted sweep: a row nothing uses is dead surface. Known needs ([execution F1](./board-2026-10-26-r2/execution.md)):
  - events: `reset` (L26), `beforematch` (L24, W4, V7), `scrollend` (C2, C3), `dragend`, `invalid` (V20);
  - methods: `reportValidity` and `requestSubmit` (S18), `dispatchEvent` (V7), `getAnimations` (L5), `focus_prevent_scroll` (L20, caller-listed);
  - props: image `complete`/`naturalWidth` (S10), `checkVisibility` (S16), `validity` (S17), `location.search` and `localStorage` (row 443's `?dx-impl` read), `querySelectorAll` order (S7);
  - property setters for non-`--dx-` names (`indeterminate`, `defaultChecked`, `documentElement.dataset`): S8 and S9 are the command kind instead, V10 and the boot probe's `html[data-dx-anchor]` write are closed `documentElement.dataset` rows; `scrollTop`/`scrollLeft` (W2, S4, V6, L13) are **writes of the scroller's `scrollOwner`**, which carry `based_on` (section 2.2, order contract; a verb row has no input classifier, so they are not setter rows);
  - an `observe(..., publish)` option (S14);
  - anything else is added by the first row that needs it. V5 (cookie, BroadcastChannel), V8 (`postMessage`), V9 (`fetch`) and V14 (clipboard) have no verb: each takes a reasoned preview-only allowlist entry, decided now by the owner, not by a lane (V14's `code_block` component takes a callback, so the installed component carries no sink).
- **Commit-sensitive effects are not verbs.** `setPointerCapture`, `releasePointerCapture`, a `focus` for the next keystroke, `preventDefault`, `DataTransfer` and clipboard writes, activation-gated APIs: effects of a named behaviour. Lane 3.0's tables, as landed on `lane/js-bridge-3-0`, ship no gesture verbs and no `commit`; a `FORBIDDEN_VERBS` list (item 0.1) enforced on both the Rust `Method` enum and the TypeScript keys keeps a lane from adding them back. **The ban is split, so it does not strand L20:** `FORBIDDEN_VERBS` bans `setPointerCapture`, `releasePointerCapture`, `commit`, plain `focus`, and `showPopover`/`showModal` on reconciled kinds; the closed table gains one row `focus_prevent_scroll` (one member call, `el.focus({preventScroll: true})`), which lane 3.CA adds with its grant (it is not in lane 3.0's tables), for a focus that no keystroke waits on, legal only from the caller rows of a reasoned TSV (section 3.2: L20's two sites). A focus that a keystroke waits on is `roving`, `openFocus` or `settle`'s `focus`, never this verb. A green `focus` or `capture` witness adds a caller-listed row keyed to the witness id (admission point 5), never a general verb.
- **Reduced motion.** The behaviours read `matchMedia('(prefers-reduced-motion: reduce)')` synchronously at execution time for every animated effect (`settle` smooth, `scrollStep`, spring); `use_media_query` defaults to "reduce" until its first answer; the G timeout is a CSS delay the reduced-motion rule does not touch.
- **One transport seam.** Hooks never call `document::eval`. `bridge/transport.rs` owns the eval call (the only one outside the two named exceptions of section 4), the delay hook of the measurement kit, a Blitz "unsupported" answer and a future web-sys backend behind the same seam (Dioxus PR #5194, which also removes the strict-CSP `unsafe-eval` requirement on web). **The bridge is evaluated through the transport after boot, as built**: loading by `asset!` plus `document::Script` with a ready handshake was not adopted (it needs a provider in every app, #5919, #5183), so `ensure_installed` evals the bundle at the first use, and the bridge exists only after wasm boot and the first effect. Consequences the plan accepts: no page-side code (the boot probe, the page reconciler's discovery, pre-hydration queueing) can start earlier, so server-rendered pages rely on the install-time level read and the page-side report queue (section 2.2, "Hydration and the pre-install window"); every consumer needs `unsafe-eval` on web (a strict-CSP app needs the web-sys backend); the bundle is parsed on first use per webview. It tears down over the existing channel (#4064).
- **Whether the verbs collapse** to two generic entry points (`subscribe` and `run(ops[])`) is left to the first lane that finds the tables too narrow; the closure rules apply either way. The typed Rust hooks keep the leptos-use / dioxus-sdk names (`use_window_listener`, `use_media_query`, `use_resize_observer`), without a dioxus-sdk dependency.

### 5.6 Proof and measurement

**The latency session, before anything else: one real desktop latency distribution.** The next-frame row needs a budget, the desktop-cadence build needs its delay N and jitter, and the pass criteria below need a baseline, and none of them depends on any port.
