## Executive summary (for the owner)

**The question.** The earlier plan kept two kinds of JavaScript as bespoke modules, because the bridge to Rust is asynchronous. The first kind is a decision made inside an event, such as "cancel this wheel". The second is a measure-then-place step that must finish within one frame, such as popup placement. You asked whether that is really true, or whether those two can also be bridged or abstracted.

**The root, in one sentence.** The browser takes its irreversible decisions at fixed points: the end of event dispatch (the default action), gesture start, input routing, the paint after layout, and the compositor frame. A value can affect one of them only if it is computed on the page's own thread before that point, from data that is already there. Everything else follows from this.

**What that means for Dioxus (verified in the 0.7.9 sources; web-verified, desktop inferred).**
- Dioxus's own event handlers already run synchronously, on web *and* on desktop/mobile. On desktop the webview blocks on a synchronous request to Rust for every event. So `prevent_default()` in a Rust handler works on both, and 133 handlers in this repo rely on that. `stop_propagation()` reaches the DOM on neither.
- What is **not** synchronous is the bridge. Messages from JS to Rust go over `dioxus.send`, and Rust's replies go back the same way. On desktop and mobile that crosses to another process, and edits reach the webview only in a rAF. On web it only queues microtasks: these happen to finish before paint, but nothing guarantees it, so nothing should be built on it.
- So the real rule is not "async can't work". It is this: **never ask Rust at the moment of commit. Publish what the decision needs before the event, and decide locally.**

**Four constructions, applied per decision in this order (section 5.1).**
1. **Delete what is dead.** About 16 eval sites sit in `#[cfg(not(feature = "web"))]` arms that every supported build compiles only for Blitz, where `document::eval` is a no-op. They include the whole focus trap and its only TypeScript file. Label's double-click script is a no-op next to the shipped CSS.
2. **(A) Let the browser decide.** CSS anchor positioning has been in all three engines since January 2026 (Chrome 125, Firefox 147, Safari 26), and `overflow-anchor` since September 2026. Baseline dates each engine's first release, and those releases carry placement bugs, so A is used **behind per-feature floors and a boot probe**; an engine that fails the probe is a fallback engine. A never carries a correctness claim alone: it keeps a Rust invariant or a Rust "verify the outcome" step behind it.
3. **(B) A placement rule indexed by deadline and kind, and a closed registry of named behaviours.** Each decision is classified by what a late answer costs (this event's default action, this event's task, the paint, the next frame, nothing), then by kind: a *listener* reacts to events, a *command* mirrors Rust state into the page.
   - A decision whose only commit-time effect is `prevent_default`, on an event and fields Dioxus delivers, is an rsx handler (and the serialized event stays small: Android drops a payload event over about 12 KB, so submit, input, change, paste and drop are not rsx-cancel candidates on mobile).
   - A decision with a commit-sensitive effect Rust cannot take in time is one named, typed behaviour: `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`, `settle`, `openFocus`, `stickToEnd`, `reconcile`, and `scrollStep` and `roving` only if their witness is red. **Admission has two checked grounds, never a declaration:** a structural effect the gate detects in the code (`preventDefault`, `stopPropagation`, a `dataTransfer` write, pointer capture, an activation-gated API), or a late-arm witness (the adapter delays the behaviour's effects by its row's deadline and the behaviour's spec must go red; for the next-frame row the witness is the owner's measurement verdict). There is no allowlisted-module category.
   - A command (popover or modal open, `indeterminate`, `defaultChecked`) is published by Rust as a volatile `data-dx-*` attribute carrying a Rust-minted generation and applied by **one document-scoped reconciler installed at boot**, in a fixed order; it reports browser-initiated changes and, on a gated surface, `applied{gen, rects}`, so there is one show writer.
   - A next-frame stream goes through the bridge under a latency budget the owner sets from one real desktop latency distribution; a named behaviour only where the measured lag exceeds it. Never a vdom handler. **Rust decides over the bridge only when the decision is commutative** with the Dioxus events around it (an absolute set, never a step or toggle from a current value the page also changes).
   - Three construction rules sit beside the table: a transition caused by a page event is applied on the page first and Rust accepts a newer epoch only; a roving-focus widget uses `aria-activedescendant` where its pattern allows and one `roving` behaviour otherwise; a decision includes computing its inputs, and its outputs are separate decisions.
4. **(G) A paint-safe gate, hardened twice.** The unsettled state is invisible until Rust answers. A separate fail-open animation plus a page watchdog open it if Rust never does; the reconciler's open step clears the pending flag, shows, reads the rects and reports them with the generation Rust minted. The tier is classified by a page-owned probe attribute, not by a vdom attribute. Only placement-critical work on engines where the platform did not place the panel is gated; decoration (placed side, arrow, available height) never is.

R (no real sync need: plain bridge verbs plus Rust) covers the rest.

**Several premises of the first version failed against the code.** The "wheel band" in the carousel never cancels anything: it is passive. The scroll lock's wheel test is a pure DOM test, but it is a stateful program, not a predicate. Escape in nested layers already cancels unconditionally, and the "topmost layer" decision is already made in Rust, asynchronously. The drawer drag and the virtual scroll bridge already stream to Rust asynchronously. Only OTP filtering, the scroll lock and the carousel's mouse drag make a real conditional cancel.

## 1. Root cause

### 1.1 The two commit points (W, platform semantics)

1. **Default actions are decided when dispatch ends.** `preventDefault()` only sets the event's *canceled flag*. The browser reads that flag after the last listener returns. A call after dispatch has finished does nothing. Inside a passive listener the call is ignored: the *in-passive-listener* flag is set around the callback, and the microtask checkpoint runs while it is still set. A wheel or touchmove listener that is not passive also makes the compositor wait for the main thread. This is the cost this repo measured in rows 149/159 (`scroll_lock.rs` module docs, V).
2. **Pixels are committed after style and layout in the "update the rendering" step.** Inside one rendering opportunity, the order is: run rAF callbacks → style and layout → ResizeObserver callbacks (which may loop back to layout) → paint. A microtask checkpoint follows each callback. A DOM write lands in the frame being drawn only if it happens before paint, which means inside an rAF or ResizeObserver callback, or in microtasks queued by one. A write that arrives in a later task misses that frame. If the pre-write state was painted, the user sees the flash.

**Invariant (the root):** *A decision can affect a commit only if it is computed on the page's main thread before that commit, from inputs present there at that time.* "Present" means event fields, the DOM, and anything Rust **published into the DOM beforehand**. Rust's own memory is not present, and neither is a message that is still in flight.

**The root, restated (board).** Irreversible decisions are taken at fixed points, each from state present there: the end of dispatch (default action), gesture start (`touch-action`, listener passiveness), input routing (focus), an activation window, paint, and the compositor frame. Section 1.4 lists what that does to the bridge verbs.

### 1.2 Where Dioxus 0.7.9 is synchronous, per renderer (V)

| path | web (wasm, same thread) | desktop / mobile (wry webview, `mobile = ["dep:dioxus-desktop"]`, `dioxus-0.7.9/Cargo.toml:122-125`) |

**What the table says (I).** The asynchronous hop is *the bridge*, not Dioxus's event path. On desktop and mobile it is a real cross-process hop. On web it is a microtask hop: for UA-dispatched events and rendering-step callbacks, that hop *happens* to finish before both commits. It is not a contract. It breaks for events dispatched from script, which get no checkpoint until `dispatchEvent` returns. It also breaks if dioxus-web re-enables its idle/rAF scheduling, or if any hop ever uses a macrotask. So: **on web the premise is mostly false in practice, on desktop it is true, and a design for all renderers must assume it is true.** Post-paint triggers are the other hole in "zero frames on web": IntersectionObserver callbacks (and so `onvisible`), popover `toggle` and dialog `close` are queued tasks that run after a paint, so a chain that must finish before paint starts from a pre-paint trigger (`beforetoggle`, a rAF or ResizeObserver callback).

| event routing | an event is routed by `data-dioxus-id` to the **current** vdom, which can be one render ahead of the DOM: a render in flight is not yet applied, and ids come from a reclaiming slab (`dioxus-core diff/node.rs`, `dom.reclaim`; I), so a click on the old, still visible element can reach the handler of the element that reused its id, and an rsx handler reads Rust state newer than what the user saw. Events route to the vdom ahead of the DOM | the DOM and the vdom agree at the event |
| Rust to page | **one `evaluate_script` per message**, with the JSON inside the script text (`query.rs:104-106`, `rustSend({data})`); the order of two messages is the order of the `evaluate_script` calls, which each platform backend provides and no Dioxus code guarantees (I) | the eval body runs synchronously at the call |
| bridge flushes | ack-gated like tasks: a verb flush is an effect, and effects run only after the acknowledgement (the `edits.rs` comment "We don't run the virtual dom while this is true to avoid running effects before the dom has been updated"), so a handler's bridge write waits for the render it caused | the next `wait_for_work` |
| a failed edit application | an exception inside the rAF callback means `markEditsFinished()` never runs (`native.ts` `rafEdits`, no try/catch): **no acknowledgement and a permanent stall** of every task, effect and Rust timer; only a page-side fail-open recovers, and `__dxBridgeStats` reports an unacknowledged render older than a few frames as a diagnostic | the exception is logged; the run loop continues |
| Windows file drop | with the default config (`disable_file_drop_handler: false`, `config.rs:127`) WebView2's HTML5 drag events are replaced by synthetic ones: `dragover` only when the element under the pointer changes, no `dataTransfer`, a fake `file.txt` on drop (`webview.rs:329-347`, `launch.rs:61-90`, `native.ts:256-326`) | native drag events |
| release builds | `disable_context_menu` defaults to `!cfg!(debug_assertions)` (`config.rs:117`): a document `contextmenu` listener calls `preventDefault()` before any component code (`webview.rs:441-456`), so the desktop listener inventory differs from the web baseline | none |

What follows (I, from the V chain above):
1. **Two Rust renders never land in one frame on desktop.** Render k+1 is sent only after render k's rAF callback has acknowledged, so row 421's "height, style flush, flag" order is automatic there. **Web is the renderer that needs the separation**: successive renders are successive microtasks inside one frame. So the first version's `commit()` verb (rAF plus forced style flush) is dropped: on desktop it is redundant, and on web it costs a whole frame when called from a rAF or ResizeObserver callback. Web keeps a "flush between renders" helper that is a forced style read, never a rAF.
2. **G costs at least one frame on desktop, typically two,** and one more for every sequential awaited read: render (mount plus pending) lands in frame N, the acknowledgement arrives, an effect runs the eval (`showPopover`), a measuring query, render (done), frame N+1 or N+2. "Show plus measure" is therefore **one JavaScript turn that returns the rects**, the reconciler's open step (section 2.3), so a gated open costs exactly one round trip and one frame.
3. **An eval issued from an event handler runs before the edits of the render that handler caused** (task before the rAF on desktop; the body runs synchronously and the render follows in a microtask on web). An eval issued from an effect runs after its render on both. Lane rule: a bridge op that depends on a render's DOM is issued from an effect or `onmounted`, never from the handler that caused the render.
4. **The root has more commit points than two.** Gesture arbitration at pointerdown/touchstart (`touch-action` and listener passiveness are read when the gesture starts; pointer capture applies at the next pointer event and throws `NotFoundError` for a released touch pointer), input routing (a key goes to whatever has focus at dispatch), activation windows (`DataTransfer`, `clipboardData`, transient-activation APIs), the compositor (threaded scroll updates pixels without the main thread, so only A tracks scroll frame-exactly), and post-paint deliveries (IntersectionObserver callbacks and so `onvisible`, popover `toggle` and dialog `close` are queued tasks, not rendering-step callbacks). Hence **commit-sensitive effects are never async `call` verbs**: `setPointerCapture`, `releasePointerCapture`, a `focus` meant for the next keystroke, `DataTransfer` and clipboard writes, activation-gated APIs exist only as effects of a named behaviour. **An rsx handler takes exactly one commit-time effect, `prevent_default`** (round 2, [core-construct 1](./board-2026-10-26-r2/core-construct.md)): on desktop everything else a Rust handler does reaches the page later (`MountedData::set_focus` is a webview query that runs after the handler's synchronous request returns, `element.rs:137-160`; renders land in the next rAF; `dioxus-html` has no pointer-capture API). A G chain starts from a pre-paint trigger: the reconciler's open step, which is one JavaScript turn (`toggle` is a post-paint task, and `beforetoggle` does not exist for `<dialog>` on Chrome before 132, Firefox before 133 and Safari 18.x, exactly the engines that need G).
5. **The platform half is mostly unproven.** Android sends the event in a base64 header (16 KB per header, `native.ts:575-587`); edits are rAF-bound, so a hidden or throttled webview stalls every render. Synchronous XHR to a custom scheme on WKWebView is W: WebKit bug 186902 ("WKURLSchemeHandler doesn't handle sync XHR") is RESOLVED FIXED (r233113, 2018-06-22). WebKitGTK stays I. V for the code path, I for the rest.
6. **A hot vdom listener costs a blocking round trip per event, and Dioxus pays per event name, app-wide.** Every Dioxus listener on desktop is one synchronous XHR, `onresize` included (a `CustomEvent` per ResizeObserver entry, `core.ts:54-72`), so one frame with 50 resized rows (`virtual_list.rs:486`, `table_rows.rs:289`, `virtual_grid.rs:1526` attach `onresize` per row) is 50 blocking round trips inside the rendering step. Because a bubbling event has one root listener per name, a single `onpointermove` or `onwheel` anywhere makes that event a blocking request across the whole app, and `onmounted` is a blocking request inside the edit application (table above). A vdom listener is for an event that needs Rust's synchronous `prevent_default`, or that fires at human rate; frame-rate streams go through the bridge (section 5.2). The existing frame-rate vdom handlers are the lane 3.HV (section 5.4).
7. **Fail-opens are page-side, and streams need back-pressure.** While a render is unacked no Rust task runs, so any timeout that must fire while Rust is stalled (G's fail-open, a behaviour's lease) lives on the page. One bridge message costs two JSON parses and at least three event-loop turns on desktop, a few hundred microseconds of main-thread time (`native_eval.ts:49-56`, `webview.rs:308`, `app.rs:309`, `query.rs:39`; I): about 120 messages per second per stream at 120 Hz is acceptable if `sample`/`subscribe` are **latest-wins on the page, at most one message per frame per stream** (the built behaviour; there is no acknowledgement window), batched modes carry a cap and a drop-oldest rule that records the loss, and high-rate Rust output goes through `set` (CSS custom-property batches), not a message per frame. The channel is unbounded, so a stall builds a backlog that replays afterwards; an in-flight window (Rust acknowledges a stream sequence number) is added only if `bridge-cost`'s "Rust busy 30 ms at 120 Hz" case shows the backlog matters, and a stream that must order against vdom events carries a sequence number or has both sides on the bridge.
8. **A bridge fact and a Dioxus event are two unordered inputs on desktop.** A Dioxus event is handled inline at once (`webview.rs:191`, routed at `protocol.rs:62-63`); a bridge fact is posted to the event loop (`webview.rs:315`) and consumed by a task that runs only inside `poll_vdom`, which returns early while a render is unacknowledged (`webview.rs:564`). A fact posted in an earlier page task can therefore be applied after a Dioxus event from a later task, up to one acknowledgement plus any Rust busy time later; on web the fact's handler runs in the microtasks of its own task, before any later event. The same input sequence resolves differently on the two renderers, which a Chromium-only CI cannot see. This is an ordering class, not a latency one: section 2.2 states the condition (a Rust decision over the bridge must be commutative with the events around it), with the instances.

## 2. Constructions, from the root

The invariant leaves these ways to satisfy it. They are applied per decision in the order of section 5.1 (a block may use several, for different decisions):

| | how it satisfies "decide at the commit, from data present" | logic lives in |
|---|---|---|
| **delete** | The block runs on no supported renderer (a `not(web)` arm compiled only for Blitz, or a script a shipped CSS rule already makes a no-op). | nowhere |
| **rsx** | The target is inside a Dioxus element, Dioxus has the event and every field the decision reads, the serialized event stays small (Android), and the only commit-time effect is `prevent_default()`: the handler is synchronous on web and on desktop/mobile and `prevent_default()` reaches the native event. | Rust |
| **A** platform-declarative | The browser owns the decision inside its own pipeline. A keeps a Rust invariant or a Rust verification step behind it. | the browser (no code) |
| **R** no real sync need | The block was never on a commit path (it reads and reports, runs a command, or drives a passive effect that may answer late). | Rust plus plain bridge verbs |
| **G** paint-safe gate | Removes the deadline for one-shot work: CSS keeps the unsettled state invisible, so a late answer paints nothing wrong. | Rust |
| **B** a closed registry of named, scoped behaviours | The decision has a commit-sensitive effect (cancel, capture, focus routing, a same-frame write) that Rust cannot take in time, or it is a command Rust mirrors into the page: one named behaviour decides locally from published config, admitted by a detected effect or a witness. | Rust owns config and lifetime; one tested TypeScript module owns the decision |
| **C** run Rust in the page | C1: the Dioxus sync event path. C2: a Rust kernel compiled to page-side wasm. C3: worklets. | Rust |

There is no "residue" row: what stays page-side is the registry (section 4), reported as a number.

### 2.2 (B) The placement rule (by deadline and kind) and the closed registry of named behaviours

**Why not a predicate language behind one delegated interpreter.** The first version of this document put every in-listener decision behind one capture-phase listener reading `data-dx-rule*` attributes, with four rule families. Four board members broke that form independently ([block-mapping F2, F6-F8](./board-2026-10-26/block-mapping.md), [simpler-alternative 3-4](./board-2026-10-26/simpler-alternative.md), [root-and-timing 3](./board-2026-10-26/root-and-timing.md), [ux-a11y-perf F5](./board-2026-10-26/ux-a11y-perf.md)):
- `closest('[data-dx-rule]')` finds only rules on the target's ancestor chain, which are exactly the events a Dioxus element handler already decides synchronously with full Rust state, on every renderer including Blitz. The sites that need page-side code (document Escape, F6, "outside the menu", window scroll lock, window Cmd+B, document `dragover`) have no such ancestor.
- At document capture nothing has run yet, so a `defaultPrevented` predicate (V22, L23 read it today because they run last) is always false, and a `stopPropagation` there cuts off every element listener and the Dioxus root. Dioxus delegates in the bubble phase (`core.ts:109-130`).
- A page-lifetime non-passive `wheel`/`touchmove` listener brings back rows 149/159 and fails `playwright/oracle/tier2-html/listener-inventory.spec.ts` (the multiset of listeners on window/document/html/body must equal the baseline taken before the first open).
- The families were unions of today's blocks: one user each for `can-scroll`, the regex filter and the metrics publisher, three different programs under "reveal/settle", four output modes under "pan". The interpreter would be about as long as the blocks it absorbed, plus a language, a serialisation format and a parity gate. Call the JavaScript that stays what it is: named modules.

**Why not a rule indexed by listener location (round 2).** Round 1's replacement sorted by where a listener sits: an rsx handler inside a Dioxus element, a named behaviour for a window, document or capture target or an event Dioxus lacks, a bridge stream for a continuous event. Five round-2 members found the same flaw from three sides ([core-construct 1](./board-2026-10-26-r2/core-construct.md), [blank-slate 1-2](./board-2026-10-26-r2/blank-slate.md), [platform-desktop 1](./board-2026-10-26-r2/platform-desktop.md)):
- **The plan contradicted its own rule.** The behaviour arm named `close` and `beforematch` and the capture phase, yet L2, W4, T12 and L3/L7/L8/L9 were mapped to bridge `listen`. C4 fitted all three arms, L11 and S2/S3 two, with no precedence.
- **"Synchronous on every renderer" holds only for `prevent_default`.** On desktop `set_focus` is an async webview query (`dioxus-desktop-0.7.9/src/element.rs:137-160`), renders land in the next rAF, and `dioxus-html` has no pointer-capture API.
- **The same gesture was placed two ways** (drawer drag R, toast swipe `pan`), and a same-frame layout write (W8 follow-bottom) was answered 1-2 frames late on WKWebView before Safari 27 by the Rust invariant alone.
- **Commands had no arm.** `showPopover`/`hidePopover`, `showModal`/`close`, `indeterminate` and `defaultChecked` were one-off bridge calls fired from effects, with a lane rule and no construction behind it.

The root sorts by **which commit point a decision feeds and by when it must land**, so the rule is rebuilt on that.

**The placement rule: classify each decision by its deadline, then by its kind.** Decided per decision (a block may have several decisions, each with its own row: T8, W8), and enforced by the gates of section 5.3. For one decision, read the table top to bottom; the first row whose deadline the decision has is its placement.

| deadline (what a late answer costs) | placement | examples |
|---|---|---|
| **this event's default action** (cancel or not) | an **rsx handler** if Dioxus delivers the event, every field the decision reads (`ToggleData`, `FocusData`, `CancelData` and `SelectionData` are empty and `MouseData` has no `detail`, so decisions on those do not qualify) **and the serialized event stays small**: on Android a payload event travels in a request header of about 12-16 KB and a failed request silently loses the cancel (`native.ts` `handleVirtualdomEventSync`; the page navigates), so `submit`, `input`, `change`, `paste` and `drop`, which carry user text or form values, are not rsx-cancel candidates on mobile (cancel declaratively with `method="dialog"`, `inputmode` or CSS, or page-side; `DemoForm` is immune by construction); otherwise a **named behaviour** | L1 (`onkeydown` on the `<dialog>`), L2 (`oncancel`); `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`'s click suppression |
| **this event's task** (pointer capture, focus routing for the next input) | a **named behaviour's effect**; never an async verb, never rsx `set_focus` on desktop | `pan`'s capture, `openFocus`, `roving`, `settle`'s focus |
| **before paint** (a same-frame layout write) | **A** where the platform does it, behind per-feature floors and a boot probe (section 2.1); otherwise a **named behaviour** (`stickToEnd`; placement on fallback engines if G's invisible pending state is not acceptable); **G** only for one-shot placement where an invisible pending state is acceptable | T8, T11; W8's follow-bottom; S1, O3, V19 |
| **next frame** (drag tracking, momentum, a finger-following value) | **bridge stream plus Rust**, **commutative decisions only** (below), under a latency budget the owner sets once from one real desktop latency distribution (section 5.6); a named behaviour only where the measured lag exceeds that budget, admitted by the `fail` verdict | L30, C3, C5 |
| **none** | **R**: Rust over the bridge (`listen`, `observe`, `sample`, `get`, `call`), **commutative decisions only** | L3, L5, L7-L9, L21, W1, W4, W6, T12, L27 |

An event Dioxus lacks (`close`, `beforematch`) no longer makes a behaviour by itself: a commit-sensitive effect does. Frame-rate events never take a vdom handler whatever their deadline (section 1.4, item 6). A block with several decisions is placed decision by decision; the layer order of section 5.1 is the preference among constructions for one decision, and where it and this table seem to disagree the table decides.

**Conditions on the table.** Five rules the board found the table needed; each is a construction, not a lane note.

1. **Over the bridge, only commutative decisions.** On desktop a bridge fact and a Dioxus event are two unordered inputs (section 1.4, item 8), so a Rust decision that combines fact-fed state with an event is order-dependent, which no latency budget repairs. A decision placed in the next-frame or none rows holds only if every Rust decision that reads fact-fed state is **commutative with the Dioxus events around it**: an absolute set, idempotent, never a toggle or a step from a current value the page also changes. A non-commutative combination is decided where both inputs are ordered: (a) by the platform, for open and close toggles the invoker relationship (`commandfor`, `popovertarget`, which HTML's light dismiss treats as inside its popover); (b) by the owning behaviour, which sees both events in DOM order (the carousel step becomes "step from the settled index the page knows", sent as an absolute target); or (c) only if neither fits, by delivering the low-rate fact on the vdom's own ordered path (an `input` event on a hidden port element whose value carries it: one blocking request per fact on desktop, never for streams). **Instances in the mapping:** the carousel's previous and next buttons step from Rust's `selected` (`nav.rs:111`), which the scroll-tracking facts write (`content.rs:469-481`, C3 as R), so a tap right after a fling steps from the pre-settle index; the slider's window pointer bridge (L21 as R) against an arrow key handled inline; `hotkey{Escape}` against an Enter typed right after it. The desktop-cadence build reorders facts against events and gets one spec per instance. Pure streams whose consumer is latest-wins (W1's windowing is absolute) are exempt.
2. **Two deadlines in one gesture: a decision includes computing its inputs; its outputs are separate decisions.** A decision takes the deadline of its earliest effect and includes everything it reads; the effects it causes later are decisions of their own, each placed by its own row. C4's cancel of the committed `pointermove` reads "committed", which is computed from the move stream (the slop threshold), so the recogniser stays on the page (the default-action row); its per-move `scrollBy`, coasting and rubber band are next-frame decisions placed by that row, and O5's `css-var` output likewise. O5 and L30 are one gesture class and are judged together against the provisional one-frame budget (section 2.2, admission) until the owner's budget exists.
3. **Page-owned transitions, accepted by epoch.** Published state is a floor, not the truth. A behaviour applies at once, in its own per-install memory, every transition its own events cause, and reports it; it accepts Rust's published value only when that value's epoch is newer than the local transition. `stickToEnd` detaches in the page, on the user's wheel, touch or key toward the start or a `scrollTop` decrease it did not write itself (follow only if the viewport was at the end before this growth, computed from `scrollTop`, `clientHeight` and `scrollHeight` the callback already has); Rust mirrors the detach and re-arms through the attribute. Without this, every growth callback in the two to three frames before the republished mode lands writes `scrollTop = scrollHeight` against the user's input (the "cannot scroll up while it streams" defect, worst on the engines that take this path), and "a late release" is a write against the user, not a late arm. The reconciler applies the same rule to a browser-initiated close (below), and `pan` and `settle`'s takeover follow it. Vector: growth after a wheel-up with Rust stalled (`?dx-bridge-delay=never`) must not move `scrollTop`.
4. **Roving focus: `aria-activedescendant` where the pattern allows, else one `roving` behaviour.** Every roving widget is arrow-key driven and arrow keys auto-repeat, so the "unless key repeat" condition holds for all of them (78 `set_focus` sites in 32 primitives files). On desktop `set_focus` is an async webview query and `tabs.rs:389` writes DOM focus back into Rust (`onfocus: ctx.focus.set_focus(Some(index()))`): a late focus event for item k+1 that arrives after Rust moved to k+2 resets the index, a key-repeat step is lost, and a native Enter or Space then activates the stale DOM-focused button. **Construction:** a composite whose ARIA role supports `aria-activedescendant` (listbox, menu, menubar, grid, tree, radiogroup, tablist, combobox popup) keeps DOM focus on the container and renders the active item as `aria-activedescendant` plus `data-highlighted` through the edit stream; key handling stays an rsx `onkeydown` on the container (`prevent_default` only), scrolling the active item into view is next-frame R, and the focus deadline disappears because focus never moves. Where roving `tabindex` must stay (Radix parity for tabs and radio; screen-reader support for `aria-activedescendant` differs, so this is an owner call), one **`roving`** behaviour moves focus in the keydown's task, admitted by its witness. A focus that no keystroke is waiting on (the L20 hand-off, section 3.2) is not roving. The 32 files are in the lane plan and the estimate, not in a "site by site" note.
5. **Android payload events** are the condition in the first row of the table, with the declarative cancels as the replacement; the gate that counts rsx cancels lists the payload event names (section 5.3, item 8).

**Kinds.**
- A **listener** reacts to events. The table above places it.
- A **command** mirrors Rust state into the page. Rust publishes the desired state as a `data-dx-*` attribute (never the native `open` attribute: two writers, `lib.rs:590-606`) and the page applies it. The kinds are popover open, modal open, `indeterminate` and `defaultChecked`.
  - **One document-scoped reconciler, installed at boot.** `reconcile` is a single observer installed with the bridge (`subtree`, `childList`, and an `attributeFilter` over the command attributes), not one observer per element. Eight of the eleven popover consumers (tooltip, hover card, select list, combobox list, popover, navbar, navigation menu, toast) mount their panel in the render that opens it (`use_animated_open`, then `if render()`), so the element arrives already carrying its attribute, and an observer attached afterwards by an effect, or by Rust over the bridge, sees no attribute change and saves nothing over today's effect-driven open. A `childList` record for the inserted node is delivered at the microtask checkpoint after the rAF callback that applied the edits (`native.ts:444-458`), before style, layout and paint, so the open lands in the frame the edit lands; the same discovery serves server-rendered markup. The reconciler reads the level at install for markup already in the page and at every added node that carries a command, so a command that is lost, early or reordered converges, including when the runtime loads late (#5919). A per-element attribute observer stays only for always-mounted or animated-exit content (`use_popover_shown_while_mounted`). Its cost (nodes scanned on a churning virtual list, observer count, records) is a `bridge-cost` case, and the observer count is an inventory beside `listener-inventory.spec.ts`.
  - **Volatile attributes carrying a Rust-minted generation.** Dioxus writes an attribute only when its value changed (`dioxus-core` `diff/node.rs:416-470`), and a browser-initiated change (light dismiss, Escape) changes the DOM, not the attribute: a controlled `open` that vetoes `on_open_change(false)` leaves the attribute `true`, no record exists, the DOM stays closed while Rust says open, and a later re-attach would reopen a panel the user dismissed (with its enter animation and a focus move). So command attributes are **`volatile`** (rewritten on every render of their scope, so a record exists even for an equal value), the value carries `(state, gen)` with `gen` minted by Rust, and the reconciler records "the browser diverged at gen g" and re-applies only for a newer `gen`. Rust either adopts the browser's state or vetoes by bumping `gen`, a deliberate and visible reopen. Every report carries the generation it answers and Rust drops an older one, which also closes the window in which a streamed report is handled after a later click. This is G's generation (section 2.3): one mechanism for commands and for the gate.
  - **One reconciler per element, in a fixed order.** Several kinds can sit on one element (a `<dialog popover>` is the non-modal Popover of DatePicker and ColorPicker, `popover_sync.rs:300-305`, and `showModal()` throws `InvalidStateError` on a showing popover), so the reconciler owns all of an element's kinds and applies them closes before opens, `hidePopover` before `showModal`, focus last. `openFocus` runs inside the open step, so "same eval as `showModal()`" holds by construction.
  - **The only caller of show and hide for its element.** It suppresses the toggle events it caused and reports **browser-initiated changes** (light dismiss, Escape) back to Rust, reading `newState` on the page: `ToggleData` is empty and the HTML spec coalesces `toggle` tasks (a show and a hide before the task runs fire one event with old equal to new), so "Rust knows which state it asked for" misreads a light dismiss that follows an open. **On a gated surface its open step also clears the pending state, shows, reads the rects and reports `applied{gen, rects}`**: there is one show writer, which removes the contradiction between "the reconciler is the only caller" and a separate measured-show verb. `show_popover_measured` and `show_modal_measured` leave the public API for reconciled kinds, and `FORBIDDEN_VERBS` lists `showPopover` and `showModal` on them.
  - **Hydration and the pre-install window.** A hydrated page produces no attribute record (the hydration rebuild runs with `skip_mutations`), so convergence rests on the level read at install. The bridge loads after boot (section 5.2), so a server-rendered default-open panel is applied at install and reports queue on the page until the channel opens: a dismissal before the channel exists is not lost and the level does not reopen it. Behaviours have the same window on SSG pages: `otpFilter` sanitises the current value at install, and `reconcile` applies `indeterminate` at install.
  - It removes the lost or early command class, the stale toggle echo (row 115) and the two-writer `<dialog open>` trap.
  - One-shot commands (focus a cell, scroll an item into view, measure now) stay bridge calls carrying an element id as data; they have no level to reconcile.

**Admission.** A named behaviour is admitted on one of two grounds, and the gate checks both; a declaration admits nothing.
1. **A structural effect, detected.** The behaviour's code contains `preventDefault`, `stopPropagation` (`capture-at-el` only), a `dataTransfer` write, pointer capture (`setPointerCapture`, `releasePointerCapture`) or a call of an activation-gated API. The gate finds it with the TypeScript compiler API (symbol resolution over the adapter and `decide`, section 5.3 item 4) and compares the detected set with the effect set in the generated `behaviours.gen.ts`: a declared effect the code does not contain, or a contained one the declaration omits, is red. These effects are wrong when late by construction, because dispatch has ended.
2. **A late-arm witness.** `sameFrameWrite` and `focus` cannot be detected (any program that writes the DOM can declare them), and a next-frame fallback has no commit effect by definition, so they are admitted only by a witness. The adapter has a test mode that delays every effect of one behaviour by the deadline of its row (one event task, one frame, or the owner's next-frame budget, provisionally one frame until rows 442 and 443 set it), and the behaviour's spec tag must go red in that mode. The gate checks the committed witness record (spec tag, delay, recorded red result) against the generated file, and `test:changed` runs the witness spec when the behaviour changes. If the spec stays green under the delay, the decision is R and the variant cannot be added. **For the next-frame row the witness is the owner's measurement verdict** (`research/measure/<port>/verdict.json` with `"verdict": "fail"`, section 4): C5's fallback, if Rust loses the measurement, is a named behaviour admitted by that stamp, not a module outside the registry. **There is no allowlisted-module category.**

What admission decides today: `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere` and `pan` pass on a detected effect; `settle`, `stickToEnd`, `openFocus` and `reconcile` pass only by a witness; `scrollStep` is a `transaction` (`scrollBy` with snap suspended in one JavaScript turn, plus `listen(scrollend)`) unless its witness is red; `settle` must show its witness (W3's loop spans many frames, so its row is next-frame unless the witness says otherwise); `roving` and the reserved `place` exist only if their witness is red, and `wheelBand` only if the owner's C5 verdict is `fail`; `dialogKeyForward` is reserved on a structural effect. The size of the budget the witness uses is the owner's number and is not decided here.

**Verbs, the move to rsx, and composition order.**
- **Verbs are single member calls.** Each row of a closed table (`METHODS`, `PROPS`, the property setters, `EVENTS` getters) is one arrow function whose body is one member call or one member read on its declared receiver kind, with arguments drawn only from typed fields; a gate checks every row on the canonical form (section 5.3). **A program is a behaviour, not a verb:** L16's open-focus policy (`dxOpenFocus`, 114 lines that branch on modality, editability and author choice) is the case `openFocus` exists for.
- **When Dioxus delivers it, a behaviour moves to rsx.** Every variant declares its reason as data (window target, missing event, capture phase, listener option), and a `cargo test` reads the locked `dioxus-html` event list and fails when a "missing event" reason has appeared (0.8's `onbeforeinput` moves `otpFilter`'s cancel half).
- **Composition order.** `prevent` is monotone, so preventers commute. A behaviour that reads `defaultPrevented` (V22) is bubble-phase and installed at a (target, phase) strictly after every behaviour that may prevent the same type: readers at window-bubble, preventers at capture, element or document-bubble. One cross-behaviour vector file (`scrollLock` held plus a `hotkey` on a scroll key) covers it.

**How a behaviour is built.**
- **A pure `decide(config, memory, snapshot, event) -> effects` plus a thin DOM adapter** that builds the snapshot and applies the effects. Conformance vectors are `{config, snapshot, event, expected_effects}` triples run by `bun test` against `decide()`; `cargo test` reads the same file against the generated types and, where a behaviour has a Rust twin (C5's classifier), against it. **Vectors prove `decide`; the DOM effects are proven by specs.** Without the split the vectors would test serde field names and nothing about decisions. `bun` may be absent: the gate then prints "bun tests: skipped (no bun)", never a pass.
- **The adapter is wider than lane 3.0's skeleton** (that adapter takes one event per install and a `{prevent, stop, attrs, send}` decision, which fits `hotkey` only: about 985 of the roughly 1,000 behaviour lines need more, [execution F2](./board-2026-10-26-r2/execution.md)). It is extended without changing the construct (by 3.0b in the full port, by the row that adds the consumer under the default scope of section 5.0): a list of `{target, event, capture, passive}` per behaviour, a per-install memory object passed to `decide`, snapshot readers chosen from a closed list (`scrollableAncestor(axis, dir)`), and a closed effect vocabulary (`capture(pointerId)`, `release`, `scrollBy`, `setVar`, `setValue` with selection, `focus`, `after(frame|ms)` which re-enters `decide`).
- **The Rust enum and the TypeScript registry stay one to one by generation, not by parsing.** `cargo test` writes and compares the committed `behaviours.gen.ts` (kind union, verb enums, field names, effect sets, vector schema version); a Rust `fn sample(b: &Behaviour)` with no wildcard arm names a vector for every variant (clippy `wildcard_enum_match_arm` denied on it); `bun test` asserts `Object.keys(HANDLERS)` equals the generated kinds. No `String`-typed field of `Behaviour` may be code.
- **Phase, target and passivity are declared**, never inferred: `capture-at-el`, `bubble-at-doc` or `window`. `defaultPrevented` is legal only in a bubble-phase behaviour. The `stop` effect is legal only in `capture-at-el` (desktop never forwards `stopPropagation`, and a window-capture stop would starve Rust's own handlers on web). Non-passive `wheel`/`touchmove`/`touchstart` exist only while a behaviour whose effect set contains `prevent` is installed, and go with the last one. The listener-inventory baseline is unchanged.
- **Every behaviour has a fail-open path and an epoch: a lease, mandatory for `prevent` and `stop`.** A behaviour that prevents an event and then relies on Rust to act must stop preventing when Rust stops answering (WCAG 2.1.2: a wedged Rust runtime must not trap the keyboard). The built mechanism is a **lease**: Rust renews it at half its length with a `sleep` loop, and an unrenewed lease expires on the page. A lease is a heartbeat, which also covers a stalled render, a hidden webview and a dead channel with no per-event traffic, where a per-event acknowledgement would not; it covers "Rust stopped", not "Rust is alive and wrong". It is **mandatory for any variant whose generated effect set contains `prevent` or `stop`** (a gate on the generated file; the landed lane-3.0 branch makes it an optional `lease_ms`, so a `prevent` variant with none passes every gate), is sized above one render plus its acknowledgement in the worst case, and a hidden webview expires it by design and the next renewal reinstalls it. A spec at the stuck-channel setting (`__dxBridgeDelayFrames = "never"`) asserts per `prevent` behaviour that Escape on an open dialog still closes it natively. The watchdog is page-side because a stalled render stops every Rust timer (section 1.4, item 7). Every answer from Rust carries the epoch of the install, and a stale one is dropped.
- **Lifetime is the owner's, with a page-side backstop.** The registry holds rules in a `WeakMap` or on the element, never in a strong `Map<id, rule>`; a `WeakMap` releases memory, not a `window` listener's registration, so every behaviour also checks `owner.isConnected` at install and on each delivered event and tears itself down when the owner is gone. A leak spec mounts and unmounts a host 200 times and asserts the registry is empty, plus an "owner removed without a teardown message" case.
- **Public API.** The hooks and behaviour types are public in `dioxus-primitives`: preview components (V22, V17) and installed components use them. `check-installed-paths` and `cargoDependencies` expectations cover them, and an installed component's Rust files contain no sink (section 5.3).

**What a behaviour is not.** A stateful heuristic over a stream (C5's trackpad classifier, W8's mode machine) is R, not a behaviour: both are passive or paint-safe, so they can answer late. W8's same-frame follow is the one part that is not R, and it is `stickToEnd`. If Rust loses C5's measurement, the heuristic becomes the named behaviour `wheelBand`, admitted by that `fail` verdict (admission, ground 2). A new behaviour is a backlog row that **exists at the merge base, is open and names the kind in its `adds:` front matter** (section 5.3), a named variant, a vector, a spec tag and a budget row; a new verb (one table line that passes the single-member-call check) is not.

### 2.3 (G) Paint-safe gate: turn "same frame" into "bounded latency", hardened twice

Same-frame is *sufficient* but not *necessary*. What is necessary is that **no frame paints a wrong state**. If the unsettled state is invisible or pinned, Rust can measure and write whenever the answer arrives. The construction after round 1 ([root-and-timing 2](./board-2026-10-26/root-and-timing.md), [block-mapping F5](./board-2026-10-26/block-mapping.md), [ux-a11y-perf F2, F7](./board-2026-10-26/ux-a11y-perf.md)) and round 2 ([platform-desktop 3-5](./board-2026-10-26-r2/platform-desktop.md), [blank-slate 5](./board-2026-10-26-r2/blank-slate.md), [execution F9](./board-2026-10-26-r2/execution.md)):

1. **The gate is the absence of a Rust answer, derived from `open`, on the surfaces where Rust owns the position.** A panel is pending while it is open, not placed by the platform, and not yet answered: `html:not([data-dx-anchor="a"]) :popover-open:not([data-dx-placed])`, with a `dialog[open]` twin only for a dialog that Rust places (none today; a CSS-centred modal is never gated). **The tier predicate is the page-owned probe attribute `html[data-dx-anchor]`** (section 2.1): the probe classifies, the attribute is written synchronously at bridge load, and its absence counts as fallback, so the gate is armed before the probe answers. `data-dx-anchored` (written by `top_layer/attributes.rs:142-159`) is a vdom attribute that Rust writes **unconditionally** for every anchored popup today, so it cannot carry an engine tier (a client-only probe result cannot reach it without a signal round trip, and the first popup can precede the probe). It **becomes conditional**: Rust writes it only while the probe signal says `a`, so the engine sheet's anchoring rules and the gate agree, and it is no longer the gate's predicate. Pending needs no write, so every Rust-placed open path is gated by default.
   - **The clear is the reconciler's open step,** one JavaScript turn that clears `data-dx-placed`, calls `showPopover()`/`showModal()` and reads the rects (section 2.2: the reconciler is the only show writer). It is not a `beforetoggle` listener: `beforetoggle` does not bubble, is absent for `<dialog>` on Chrome before 132, Firefox before 133 and Safari up to 18.7, and a document capture listener would be a page-lifetime listener outside the registry and `listener-inventory.spec.ts`. Every library open is Rust-driven; native `popovertarget` appears only in preview demos with no placement attribute. If the owner wants native opens gated too, that is a registry behaviour (`gate`) with a vector, a budget row and an inventory entry.
   - `toggle` is a queued task that runs after a paint, so it cannot start a gate.
2. **The pending style selects its own animation and leaves no enter keyframe applying.** The theme's enter animation is `forwards` and runs `opacity 0 -> 1` (`dx-components-theme.css:1775-1818`); an animation declaration outranks a normal one, so a one-line `opacity: 0` hides only while the animation is paused at t = 0, where it also keeps the 0% keyframe's `scale` (S1 would read a transformed rect). Pending therefore selects **its own fail-open animation name** (`dx-gate-failopen`: delay `--dx-gate-timeout`, `forwards` fill, one keyframe `to { opacity: 1 }`), with `opacity: 0; pointer-events: none` before it. No enter keyframe applies while pending, so the geometry is untransformed. **Not `animation: none`:** that would kill the fail-open. `animation-play-state: paused` is rejected for the same reason. When Rust answers, the placed state selects the enter animation by name; the swap restarts it from 0, so the fade is clean (a live `animation-delay` change would instead jump a running animation 20 to 60 percent in). The reduced-motion rule shortens durations only (`dx-components-theme.css:1785-1790`) and must not touch the delay.
3. **Fail open twice: in CSS and on the page.** The CSS animation of item 2 opens the panel after the timeout (at most about 100 ms for a placement-critical gate; lane 3.PL fixes the number by measurement). Host CSS can defeat it: the theme itself ships `[data-dx-motion-key] *, ... { animation: none !important }` under `prefers-reduced-motion: reduce` (`dx-components-theme.css:2421-2432`), which matches popups rendered as descendants of a motion-key host (the popup-boundary class), and common user resets do the same. So the reconciler's open step also arms a **page-side watchdog timer** of the same length that clears the pending state. It is page-side because a Rust timer cannot be the alternative: a wedged or unacknowledged render stops every task (`webview.rs:563-572`).
4. **One generation, minted by Rust with the command.** The command attribute carries `(state, gen)` (section 2.2); the reconciler's open step stamps the open with that `gen` and reports `applied{gen, rects}`; Rust answers with `data-dx-placed` carrying the `gen` it measured, and the page drops (removes, in the same microtask checkpoint as the observer that sees it) a `placed` older than the current `gen` before paint, on the fail-open path too. A stale answer would otherwise be visible the moment its attribute exists, because the CSS shows the panel on `[data-dx-placed]`. Command attributes are `volatile`, so an equal-value republish still produces a record. This is the same race class as `__dxDialogGen` in `lib.rs` and the "no cleanup of data-placed-side" comment in `anchor_fallback.rs`, with one generation mechanism for commands and the gate. **Writers:** Rust writes the command and the answer; the page's only write to an attribute Rust owns is the removal of a stale answer, by generation. The invariant is fixed here; lane 3.PL settles the literal wiring with the first-frame spec. Spec: open, close, open within one task, at the delay settings N = 0 and N = 2, a stale answer, and unmount before the answer.
5. **Two tiers, by what a wrong paint costs.**
   - **Placement-critical: gated.** Only where Rust owns the position: engines below a floor or failing the boot probe (the fallback), and the iOS keyboard clamp (row 210). `opacity: 0` until placed.
   - **Decoration: never gated.** The placed side, arrow offset, `transform-origin` and available height open with the neutral defaults and update when Rust answers, after the tooltip's `:not([data-placed-side])[data-side]` precedent. The enter animation is origin-independent for its first frames (opacity first), so a late origin never shows as a wrong-corner pop. Without the split every popup open would pay two to four frames on desktop (I), on the engines where A already did the work.
   - **The per-surface list.** The theme's enter animation belongs to `[data-dx-surface="floating"][data-state="open"]`; the navbar, the navigation menu and the toast animate differently (`navbar/style.css:147,219`, `navigation_menu/style.css:194,218`, `toast/style.css:176,216`), so the name swap of item 2 is declared per surface in a list that lane 3.PL owns and the gate checks (every gated surface declares its tier, timeout and animation names).
   - **The scrim** of a gated dialog is not part of the pending style; it either shows for up to the timeout with no panel or is gated with it. 3.PL declares which.
6. **Gate only what is pending, never a visible panel.** Re-placement on resize or keyboard paints a frame late, a stated degradation (the reserved `place` behaviour is the exit, section 2.2). Where A places the panel, only the Rust-dependent part is gated.
7. **Show plus measure is the reconciler's open step, which returns the rects** (section 1.4): they are read page-side in the same JavaScript turn and reported with `applied{gen, rects}`, not through `MountedData`, so a getter that never completes (Dioxus #5734, reported on Ubuntu desktop) is not on the critical path. There is no separate measured-show verb for a reconciled element.
8. **Pending states are opacity-only.** A pending selector may declare `opacity`, `pointer-events`, the fail-open animation name and the delay, and nothing that leaves the accessibility tree or blocks focus: not `visibility`, `display`, `hidden`, `inert` or `content-visibility`. Focus must enter an `opacity: 0` panel (`modality.rs:108-165` has no visibility test), a toast's `role="alert"` insertion must still be announced (`toast.rs:1517-1535`), and VoiceOver reading a panel from its frame is on the manual checklist. A click in the panel's future area during the pending window falls through to the page (and light-dismisses a `popover=auto`): negligible at 0-2 frames, real during a 100 ms fail-open.

**Latency.** On web, for a pre-paint trigger (UA events, timers, rAF and ResizeObserver callbacks): zero extra frames, all microtasks. Post-paint triggers (`onvisible`, `toggle`, `close`) already cost a frame. On desktop (web-verified; desktop inferred): at least one frame, typically two, and one per sequential awaited read (section 1.4). **On the Apple-desktop fallback tier G costs two to three frames plus IPC** (event, render, rAF edit, acknowledgement, the open step, the reply over IPC, render, rAF) **against today's in-turn placement**, and Safari 26 WKWebView is the current WebView for months, so G is the default experience there and a strict slowdown. Before 3.PL starts, `g-latency` is measured on a WebKit desktop build and the fallback tier's default is decided between G and the reserved `place` behaviour (an in-turn re-place); both are mappings of T8, not a change of construct.

**Not for continuous loops.** A lagging write during scroll or drag *is* a wrong paint. G is for open-time, insert-time and swap-time work only. A same-frame write that tracks a stream (W8's follow-bottom) is not G: it is A where the platform does it, otherwise the named behaviour `stickToEnd` (section 2.2). Continuous tracking goes to A. B and R run on the main thread and are a frame or more behind the compositor, so they are never "frame-exact" against scroll.

**Proof.** A first-frame spec asserts the panel is `opacity: 0` with no enter keyframe applied while pending, that no frame paints `placed` with stale geometry, and that a modal dialog and an A-placed menu are never hidden; `g-latency` measures frames from input to first visible panel (at most 1 at N = 0, at most 3 at N = 2); the stuck-channel run shows the fail-open, **including a case with `animation: none !important` on an ancestor** (the watchdog opens it); a boot-probe spec runs the probe set against a forced-failing engine and asserts the pre-probe default is fallback; a reconcile spec covers a vetoed close, a stale generation and an `applied{gen, rects}` for each gated surface.

### 2.4 (C) Running Rust in the page

- **C1, Dioxus's own sync event path (V).** It works on web and desktop/mobile, as section 1.2 shows. **It is the first row of the placement rule's default-action deadline**: use it where the decision's only commit-time effect is `prevent_default()` and Dioxus delivers the event and every field the decision reads (this is already the house style: 133 `prevent_default()` calls in `primitives/src`). As a *trampoline* for window/document/capture cases, where the bridge re-dispatches a cancelable synthetic event to a vdom "port" element and reads `dispatchEvent()`'s return value, it is **rejected**:
  1. The synthetic event must be a type Dioxus converts (keydown, or a `CustomEvent` `resize` with a fake `detail`), which is an abuse.
  2. Other capture listeners see it, so the modality writer would mark keyboard modality.
  3. Desktop pays one blocking XHR per event, which is unacceptable for wheel or touchmove at 60-120 Hz.
  4. `stopPropagation` reaches the DOM on no renderer.
  5. Desktop is not in CI.

  Dioxus 0.8.0-alpha.1 adds `onbeforeinput` (audit section 3, W). With it, S11's cancel half becomes a plain rsx handler once fields and sync cancel are verified (I).
- **C2, a Rust kernel compiled to page-side wasm (I).** Every target webview runs wasm (Baseline high). **Against it:** Chrome refuses synchronous `new WebAssembly.Module` for buffers over 4 KB on the main thread (W, web.dev "Loading WebAssembly modules efficiently"), so loading is async; it needs a second build artefact plus a reproducibility gate; every input still needs JavaScript glue. **Verdict:** not now, and **no longer C5's exit**: if Rust loses the C5 measurement, C5 becomes a named behaviour admitted by the `fail` verdict (section 2.2, admission; section 4).
- **C3, worklets and workers.** AnimationWorklet and the Layout API have not shipped. A paint worklet is Chromium-only and cannot cancel events. Workers have no DOM. Rejected.
- **C4, "the bridge is microtask-synchronous on web" (V components, I end to end).** True for UA-dispatched events and rendering-step callbacks. **Not a construction:** it fails on desktop/mobile and for script-dispatched events, and would break if dioxus-web re-enabled its idle/rAF scheduling (the TODO at `lib.rs:250-262`). Its one use is to explain why G costs nothing extra on web, and why a Chromium-only CI cannot reveal desktop latency bugs (section 5.6).

## 5. The proposal

### 5.0 Scope: what is built now (owner decision pending)

Round 3's coherence member separated two goals this plan had merged. The **construct** is what makes the class unable to recur; the **port** removes the existing instances. The construct needs neither phases 1 to 4 nor the feel-critical ports: every legacy block can sit behind a per-file `expect` and a frozen baseline row until it is touched, which section 5.3 (item 11) already says of the older gates.

**The construct:** the one eval sink (the `Program`-typed transport of lane 3.0), the ratchet with grant rows, the deadline rule with its conditions, admission by a detected effect or a witness, a legacy-literal freeze, and **two proof ports** that exercise both kinds: a listener (dead JavaScript, `hotkey` for L6, L1 and L2 as rsx) and a command (`reconcile` for T4 to T7).

Numbers (I: the hours are the boards' judgement, not measurements; JS lines are the audit's string extents):

| | construct | full port (the five-phase plan) |
|---|---:|---:|
| agent-hours | about 35-40 | about 235-270 (row 442's 14 h outside) |
| JS lines removed | about 450 | about 4,127 (about 1,290 more relocated into `ts/behaviours`, still counted) |
| lines removed per agent-hour | about 12 | about 15 (step 2 measured about 3: about 130 lines in about 45 h) |

Around those totals:
- Lanes that remove almost no JavaScript (3.0b, 3.FZ, the row 443 kit, row 442, 3.HV, 3.SL) are about **72 hours (27%)**.
- The three feel-critical ports with their support (3.MS, 3.WB, C1; 3.FZ, the kit, row 442, the legacy removal) are about **88 hours for 1,567 lines** (38% of all removal) and carry the largest unknowns: W8 on Safari, C5's possible fallback to the `wheelBand` behaviour, desktop latency.
- 3.PL (28 hours, visible on every popup open) cannot be proven in this container: Chromium is the only engine, so Firefox, WebKit and the forced-failing-engine probe cannot run here.
- 3.HV (10 hours, 0 lines removed) reverses Rust handlers that lane 2C landed, on a desktop cost that is inferred and unmeasured; `check-hot-events` with a shrink-only baseline already stops growth.
- Step 2's lanes ran 1.1 to 2.2 times their estimates.

**Options:**
- **A. Port everything now:** the five-phase plan, about 235-270 hours.
- **B. Construct first, then port the rest as ordinary backlog rows in order of JS removed per agent-hour.** The construct and its two proof ports are phase 0 (section 5.4); every other port is a candidate row, opened one at a time with its grant row and, where it adds a behaviour, its `adds:` row; the three owner-measured ports stay last, one at a time, and only if the owner schedules them. **This is the default, pending the owner's decision.**
- **C. Construct only, port on touch:** the legacy-literal freeze makes an edit of a legacy script a port, so nothing else is scheduled.

What B changes in the rest of this document: the closed-table rows and the behaviour skeletons are added by the row that consumes them, with its own grant (not pre-granted for all of them); the wider adapter is built for the first two consumers (`hotkey`, `reconcile`) and widened per consumer; lane 3.FZ, the `?dx-impl` switch and the `legacy-impl` feature exist only when a measured port is scheduled. **The honest cost of B and C:** the combined JavaScript total does not fall until ports land, because lane 3.0 raises it (the bridge is about 874 lines against a budget of 1,100) and `#! total-raised` stays on the baseline.

### 5.2 The bridge surface is closed

Lane 3.0 builds the verbs and lane 3.0b widens them; these rules close them ([gates-and-proof 2](./board-2026-10-26/gates-and-proof.md), [root-and-timing 5, 6](./board-2026-10-26/root-and-timing.md), [simpler-alternative 5](./board-2026-10-26/simpler-alternative.md), and in round 2 [enforcement 1, 6](./board-2026-10-26-r2/enforcement.md), [execution F1, F2, F16](./board-2026-10-26-r2/execution.md), [core-construct 2, 3](./board-2026-10-26-r2/core-construct.md), [platform-desktop 6, 8](./board-2026-10-26-r2/platform-desktop.md)):

- **No `el[method](...args)`.** `call`, `get`, `set` and `listen` take **closed Rust enums** (`Method::ShowPopover`, `Prop::Rect`, ...) mapped through **closed TypeScript tables** (`const METHODS = { showPopover: ... }`), dispatched with an own-property check, with a **receiver kind per row** (an element method cannot be called on `window`). Otherwise `call(window, "setTimeout", ["code"])` is an eval. `set` of a custom property accepts only names that start with `--dx-`. Parity between the Rust enums and the tables is the generated golden file of section 2.2, not a text parse.
- **A verb is one member call.** Each row is one arrow function whose body is one member call or one member read on its declared receiver kind, arguments from typed fields (admission, section 2.2). The landed rows already hold logic (`showPopover` guards on `typeof` and `:popover-open`; `close` branches on an argument), so the gate caps a row at one expression plus at most one guard `if`; anything larger is a registry program with a row and vectors.
- **The transport is typed, not a string seam.** Lane 3.0's `transport::open(body: &str)` and `request(expression: &str)` are `pub(crate)` and `js_listener.rs` already calls them, so any module can run an arbitrary script through them with no `eval` identifier in its file: a renamed sink, not a closed one ([enforcement 1](./board-2026-10-26-r2/enforcement.md)). `open(program: Program)` and `request(program: Program, args: &impl Serialize)` take a `Program` enum whose variants map to `&'static str` constants private to `bridge/`, and both are `pub(in crate::bridge)`. No `format!` into either except one `encode` function; until `js_listener.rs` retires, a shrink-only callers table in the sink gate carries one reasoned row for it.
- **Ordering of element operations is a property of the transport, not a lane rule.** Element operations issued while a handler runs are queued and flushed with `dioxus_core::queue_effect`, after the edits of the render that issued them (the mechanism dioxus-web uses for its head insertions, `dioxus-web-0.7.9/src/document.rs:1,125-161`), through one pump, so they are FIFO. Commit-sensitive work never needed "issue now": it lives in behaviours. `transaction(ops[])` stays for atomic results, `commit()` is **dropped** (section 1.4), the web-only flush between renders is a forced style read, and ref-counted installs and removals cannot reorder, so a non-passive listener cannot leak (rows 149/159). A stuck-render spec at `?dx-bridge-delay` covers it. **As built (lane 3.0), only element operations share the pump:** every hook's `Session::open` opens its own `Program::Serve` eval and sends its commands from an effect, `JsListeners` opens one eval per script, and `ensure_module`/`ensure_installed` are separate evals; order across them is the order of the `evaluate_script` calls, and `pending_effects` pops the lowest scope height first, so a root-owned flush effect runs ahead of its descendants' effects. The consequence is small (installs and writes are issued from effects after the acknowledgement, and webview evals are ordered), so the claim is "element operations are FIFO", here, in `js-interop.md` and in the transport doc, and not "all Rust-to-JS traffic"; carrying session commands as pump messages is the alternative if a case needs it.
- **`passive` derives from the behaviour.** `listen`/`subscribe` streams fields, so it cannot cancel: it is always passive for `wheel`, `touchstart`, `touchmove` and `scroll`, and the TypeScript ignores a request for otherwise. A listener is non-passive only while an installed behaviour's effect set contains `prevent`.
- **Event volume derives too, and a stream is bounded per frame.** `pointermove`, `mousemove`, `wheel`, `scroll`, `touchmove`, `resize`, `drag` and `dragover` have no raw mode: a frame-coalescing mode, or a flush per event task for C5, which needs every event with its own timestamp (batched, not coalesced: its notch and decay rules compare consecutive events). `sample(el, fields, until)` is armed only while a gesture or condition holds; C5's `pointermove` must not live for the carousel's whole mount (`wheel.rs:578`). **As built, `listen` and `sample` are latest-wins per frame: at most one message per frame per stream, with no acknowledgement** (`observe` has no coalescing); the "one message in flight" wording of earlier versions is withdrawn. A batched mode carries a cap and a drop-oldest rule that records the loss; high-rate Rust output goes through `set` (CSS custom-property batches), not a message per frame. An in-flight window (Rust acknowledges a stream sequence number) is added only if `bridge-cost`'s "Rust busy 30 ms at 120 Hz" case shows the backlog matters; a stream that must order against vdom events carries a sequence number or has both sides on the bridge (L30's start, move and end all go through the bridge, so it is ordered; mixing a bridge move with a vdom `onpointerup` is not).
- **Hot events stay off the vdom, counted per event name.** A vdom `on*` handler is for an event that needs Rust's synchronous `prevent_default`, or that fires at human rate. `scroll`, `resize` on many elements, `pointermove`, `wheel`, `touchmove`, `mousemove` and drag events go through bridge `listen`/`observe`/`sample`, async and batched. A reducer option (`emit` only when a named derived key changes) keeps a stream from posting a message per event. Dioxus registers one root listener per bubbling event name with no options, so one `onpointermove` or `onwheel` anywhere makes that event a blocking, non-passive request app-wide: the gate counts **event names across the app** (a per-event-name allowlist, not per file) and adds `onmounted` as a cost class (a per-row handle needs a batched observe alternative or one container handle). It applies to W1, W8, O3, lane 2C's S2/S3 and every site listed under lane 3.HV (section 5.4), and its scope includes `preview/src/components/**`. Enforcement is section 5.3, item 8.
- **Closed tables carry the rows the later lanes need, added once.** Lane 3.0's tables lack rows that about 18 of the later rows need ([execution F1](./board-2026-10-26-r2/execution.md)); lane 3.0b adds them so behaviour lanes consume rows and never add them (under the default scope of section 5.0 the row that consumes a missing row adds it, with its grant):
  - events: `reset` (L26), `beforematch` (L24, W4, V7), `scrollend` (C2, C3), `dragend`, `invalid` (V20);
  - methods: `reportValidity` and `requestSubmit` (S18), `dispatchEvent` (V7), `getAnimations` (L5), `focus_prevent_scroll` (L20, caller-listed);
  - props: image `complete`/`naturalWidth` (S10), `checkVisibility` (S16), `validity` (S17), `location.search` and `localStorage` (row 443's `?dx-impl` read), `querySelectorAll` order (S7);
  - property setters for non-`--dx-` names (`indeterminate`, `defaultChecked`, `documentElement.dataset.hydrated`): S8 and S9 are the command kind instead, V10 a closed row; `scrollTop`/`scrollLeft` (W2, S4, V6);
  - an `observe(..., publish)` option (S14);
  - anything else goes to a 3.0b queue that the main loop serves at merge time. V5 (cookie, BroadcastChannel), V8 (`postMessage`), V9 (`fetch`) and V14 (clipboard) have no verb: each takes a reasoned preview-only allowlist entry, decided now by the owner, not by a lane.
- **Commit-sensitive effects are not verbs.** `setPointerCapture`, `releasePointerCapture`, a `focus` for the next keystroke, `preventDefault`, `DataTransfer` and clipboard writes, activation-gated APIs: effects of a named behaviour. Lane 3.0's tables ship `setPointerCapture`, `releasePointerCapture`, `focus` and `commit` as verbs, against this rule and against its own transport docs ("not usable at `pointerdown`"); 3.0b removes them, and a `FORBIDDEN_VERBS` list enforced on both the Rust `Method` enum and the TypeScript keys keeps a lane from adding them back. **The ban is split, so it does not strand L20:** `FORBIDDEN_VERBS` bans `setPointerCapture`, `releasePointerCapture`, `commit`, plain `focus`, and `showPopover`/`showModal` on reconciled kinds; the closed table keeps one row `focus_prevent_scroll` (one member call, `el.focus({preventScroll: true})`) for a focus that no keystroke waits on, legal only from the caller rows of a reasoned TSV (section 3.2: L20's two sites). A focus that a keystroke waits on is `roving`, `openFocus` or `settle`'s `focus`, never this verb.
- **Reduced motion.** The behaviours read `matchMedia('(prefers-reduced-motion: reduce)')` synchronously at execution time for every animated effect (`settle` smooth, `scrollStep`, spring); `use_media_query` defaults to "reduce" until its first answer; the G timeout is a CSS delay the reduced-motion rule does not touch.
- **One transport seam.** Hooks never call `document::eval`. `bridge/transport.rs` owns the eval call (the only one outside the three named pre-wasm exceptions of section 4), the delay hook of the measurement kit, a Blitz "unsupported" answer and a future web-sys backend behind the same seam (Dioxus PR #5194, which also removes the strict-CSP `unsafe-eval` requirement on web). **The bridge is evaluated through the transport after boot, as built**: loading by `asset!` plus `document::Script` with a ready handshake was not adopted (it needs a provider in every app, #5919, #5183), so `ensure_installed` evals the bundle at the first use, and the bridge exists only after wasm boot and the first effect. Consequences the plan accepts: no page-side code (the tier probe, the reconciler's discovery, pre-hydration queueing) can start earlier, so server-rendered pages rely on the install-time level read and the page-side report queue (section 2.2, "Hydration and the pre-install window"); every consumer needs `unsafe-eval` on web (a strict-CSP app needs the web-sys backend); the bundle is parsed on first use per webview. It tears down over the existing channel (#4064).
- **Whether the verbs collapse** to two generic entry points (`subscribe` and `run(ops[])`) is lane 3.0b's call; the closure rules apply either way. The typed Rust hooks keep the leptos-use / dioxus-sdk names (`use_window_listener`, `use_media_query`, `use_resize_observer`), without a dioxus-sdk dependency.

### 5.3 Enforcement closes sinks, not spellings

**Status:** the JS-volume ratchet (`scripts/check-js-volume.sh`, with a self-service raise) is the only gate of this section that has landed; every other rule below is **planned** (lane 3.0 and the gate half of 3.0b), and `dev-docs/js-interop.md` keeps the two apart. A JavaScript-bearing string can run only through a short, enumerable list of sinks. The list is the gate; token bans are defence in depth ([gates-and-proof 1-6](./board-2026-10-26/gates-and-proof.md); round 2: [enforcement 1-10](./board-2026-10-26-r2/enforcement.md)).

1. **One eval site.** The identifier `eval` in the Rust code view (comments removed, string contents blanked), including `use ...::eval` aliases, a bare function pointer (`let f = dd::eval`), `.eval(` and the globs `document::*` and `dioxus_document::*`, is allowed only in `bridge/transport.rs`, with an exact site count, and its argument must be a `Program` constant plus `serde_json` output (the constants' sha256 is recorded in the baseline, so a change is a visible diff). Clippy's `disallowed_methods` (`clippy.toml`, resolved by def path, so aliasing, re-exports, trait-method syntax and `concat!` cannot dodge it) lists `dioxus_document::eval`, `Document::eval`, `Script`, `js_sys::eval`, `js_sys::Function::new_*`. The three pre-wasm exceptions (section 4) are allowlist entries. `labs/carousel-lab`, `templates/starter` and `playwright/oracle/attr-synth` are detached crates that clippy never sees and stay on the volume gate.
2. **The other sinks.** `document::Script`, `create_script`, `create_head_element` and `script {}` allowed only as `Script { src: <ASSET_CONST> }` for an allowlisted set of asset constants; `dangerous_inner_html` per file and reason, never on a `script`; rsx string attributes `"on..."`, `href: "javascript:..."`, `srcdoc`; `include_str!`/`asset!` of `.js/.mjs/.cjs/.ts/.tsx` and a **file inventory** of hand-written `.js`/`.ts` (`message_scroller.js` is the one hit, a baseline row removed by the legacy removal); `web_sys`/`js_sys`/`wasm_bindgen`/`wasm_bindgen_futures`/`gloo_events`/`gloo_file`/`evaluate_script` and their `Cargo.toml` entries (a dependency allowlist, with the machinery of `check-cargo-dep-versions`) outside `transport.rs`; a new inline `<script` in any tracked `.html` outside `docs/`, counted per file by body hash. **The landed gate's holes are closed:** the `/vendor/` and `.min.js` exclusions move into a reasoned TSV (stale entries fail) instead of a regex; `.md` and `.svg` are scanned for event-handler tags, `<script` and `javascript:` because `preview/build.rs` passes raw HTML from a `docs.md` or `notes.md` through `push_html` into `dangerous_inner_html` (1,047 tracked `.md`); an untracked file is seen (`git ls-files -co --exclude-standard`); `js_file` counts `ceil(len / 120)` per line, like `js_lit`, so a minified one-line `.ts` cannot hide its size.
3. **Universe by `git ls-files`** with an explicit exclusion list (`playwright/`, `scripts/`, `docs/`, the generated `primitives/src/js/`), never hand-listed roots. **No inline-marker escape:** an exception is a TSV line `path<TAB>sink<TAB>reason<TAB>row`, read by `scripts/lib/allow.py` (reason mandatory, stale entries fail), and an allowlist entry is the owner's decision, never a lane's. 4. **The JavaScript side** is scanned with the TypeScript compiler API, not a spelling denylist ([enforcement 10](./board-2026-10-26-r2/enforcement.md): `e[name]()`, `self['ev'+'al']('1')`, `Reflect.get(e, 'prevent'+'Default')`, `(0, W.eval)('1')` and `(()=>{}).constructor('return 1')()` all pass the lane's regexes, because `bridge.ts` types receivers as `any`). `noImplicitAny` plus typed receivers (`Element`, `Window`, `Event`) makes a computed member access a compile error, and a small `tsc`-API pass bans an `ElementAccessExpression` with a non-literal argument outside `own(TABLE, name)`, any call whose symbol resolves to `eval`/`Function`/`setTimeout`/`setInterval` with a string argument, and `.constructor`. The canonical form (`bun build --minify-syntax --no-bundle`, which folds `"a"+"b"` and `x["y"]`) is what the verb-row cap (section 5.2) and the identifier bans (`preventDefault`, `stopPropagation`, `requestAnimationFrame`, `setTimeout`, `queueMicrotask`, the three observers, `addEventListener`, `import(`) read, **outside file-level allowlist entries** with a per-file budget. **Budgets are a ratchet, not a quota:** each equals the file's current size, moves through the same `Ratchet` class (merge-base compare, grant), and counts bytes or canonical tokens, not physical lines; the landed `BEHAVIOUR_BUDGET = 150` constant and `bridge.ts`'s 1100 against 874 real lines (226 lines of free growth) go. The base is the nearest of `origin/main` and `origin/queue/*` (the row 418 rule `test:changed` already uses), so a grant commit by the main loop on the batch branch counts and a lane's own diff cannot grant itself. The total directive carries its number and `check()` compares it. The red text stops printing the raise command and says "ask the owner for a grant row". The main loop's full `run-gates.sh` sets `RATCHET_REQUIRE_BASE=1`, so "base unavailable" is red there, not a note. ### 5.5 Risks (in order)

1. **Desktop and mobile are unmeasured and not in CI** (no gtk/webkit2gtk here). G latency, R event volume and behaviour timing on WebView2/WKWebView/WebKitGTK are inferred. Mitigation: the desktop-cadence build and one recorded real pass per batch (5.6); the label "web-verified; desktop inferred" until then.
2. **Placement (3.PL)** is visible on every open and is where the plan is most expensive (it now also holds T4-T7 and the G pieces). ### 5.6 Proof and measurement

**Step 0, before anything else: one real desktop latency distribution.** The next-frame row needs a budget, the desktop-cadence build needs its delay N and jitter, and the pass criteria below need a baseline, and none of them depends on any port. So the first measurement is one real session of the **current build** on **one of the owner's devices** (a Mac with WKWebView, or a Windows machine with WebView2, whichever the owner has): the bridge round-trip histogram of `__dxBridgeStats` (send stamp, Rust handler, applied stamp, in frames) plus the wheel-event jitter table C5's property test needs. It is the stats half of the row 443 kit (phase 0, item 0.5) and one owner session, taken once; it is also what fixes the provisional one-frame budget of admission's witness. Three ports' worth of per-device protocol comes after it, not before: three lanes would otherwise be built on a budget that only exists once they are.

**Honest about desktop.** All specs run on Chromium on the web, where the bridge is microtask-fast (section 1.2), and that **hides** every desktop-only latency bug. The first version's slow-channel harness (`window.__dxBridgeDelayFrames = N`) delays only bridge messages: it misses the rAF-bound edit cadence, an eval that runs before its own render's edits, the cross-channel reorder, the cost of a blocking XHR per Dioxus event, and every engine difference, and it delays messages inside a rAF, the best case. It stays as a **bridge-latency harness** (`?dx-bridge-delay=N`, a stuck setting `N = never`), never called a desktop model. A batch merges on "web-verified; desktop inferred", with the stamp a per-batch post-merge debt list (section 5.4). The proof of sameness is built in three steps ([row 442](../backlog/442-desktop-cadence-harness-and-desktop-pass.md)):
1. **A desktop-cadence web build:** a harness-only workspace that patches `dioxus-web` with `[patch.crates-io]` (about 30 lines against 0.7.9: edits flushed in a rAF and awaited before the next render, the hook being the commented-out `wait_for_raf` at `dioxus-web-0.7.9/src/lib.rs:256-262`; the eval body run in a task; `MountedData` getters resolved after a task hop; `dioxus.send` delivered after a task hop with N plus jitter, in arrival order per channel and not across channels). Events stay synchronous. N and the jitter are chosen from the distribution of step 0, not by fiat.
2. **Engines:** Playwright WebKit and Firefox for the named A/G subset (the configs exist; only the deploy wiring is missing).
3. **A recorded real pass per batch, on the devices the owner has:** one WebKitGTK or real-desktop pass (`desktop-pass.md` holds the checklist; one owner session, not a per-OS matrix) leaves `desktop-pass/<tree>.pass` (machine, OS, webview version, numbers), the way `release-suite/<tree>.pass` works for the suite. Until a stamp exists for the tree, rows and lane reports say "web-verified; desktop inferred"; a G or R mapping is never marked done on web evidence alone.
