## Executive summary (for the owner)

**The question.** The earlier plan kept two kinds of JavaScript as bespoke modules, because the bridge to Rust is asynchronous. The first kind is a decision made inside an event, such as "cancel this wheel". The second is a measure-then-place step that must finish within one frame, such as popup placement. You asked whether that is really true, or whether those two can also be bridged or abstracted.

**The root, in one sentence.** The browser takes its irreversible decisions at fixed points: the end of event dispatch (the default action), gesture start, input routing, the paint after layout, and the compositor frame. A value can affect one of them only if it is computed on the page's own thread before that point, from data that is already there. Everything else follows from this.

**What that means for Dioxus (verified in the 0.7.9 sources; web-verified, desktop inferred).**
- Dioxus's own event handlers already run synchronously, on web *and* on desktop/mobile. On desktop the webview blocks on a synchronous request to Rust for every event. So `prevent_default()` in a Rust handler works on both, and 133 handlers in this repo rely on that. `stop_propagation()` reaches the DOM on neither.
- What is **not** synchronous is the bridge. Messages from JS to Rust go over `dioxus.send`, and Rust's replies go back the same way. On desktop and mobile that crosses to another process, and edits reach the webview only in a rAF. On web it only queues microtasks: these happen to finish before paint, but nothing guarantees it, so nothing should be built on it.
- So the real rule is not "async can't work". It is this: **never ask Rust at the moment of commit. Publish what the decision needs before the event, and decide locally.**

**Four constructions, applied in this order per block (section 5.1).**
1. **Delete what is dead.** About 16 eval sites sit in `#[cfg(not(feature = "web"))]` arms that every supported build compiles only for Blitz, where `document::eval` is a no-op. They include the whole focus trap and its only TypeScript file. Label's double-click script is a no-op next to the shipped CSS.
2. **(A) Let the browser decide.** CSS anchor positioning has been in all three engines since January 2026 (Chrome 125, Firefox 147, Safari 26), and `overflow-anchor` since September 2026. A never carries a correctness claim alone: it keeps a Rust invariant or a Rust "verify the outcome" step behind it.
3. **(B) A closed registry of named, scoped behaviours, placed by a three-way rule.** A decision inside a Dioxus element is an rsx handler. A decision on a window, document or "outside" target, on an event Dioxus lacks, or in the capture phase is one named, typed behaviour (`hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`, `settle`, `scrollStep`, and `dialogKeyForward` if the specs need it). Continuous streams go through the bridge, never through vdom handlers. This replaces the first version's predicate DSL behind one delegated interpreter, which four board members independently broke.
4. **(G) A paint-safe gate, hardened.** The unsettled state is invisible until Rust answers, and a CSS-only timeout opens it if Rust never does. Only placement-critical work is gated; decoration (placed side, arrow, available height) never is.

R (no real sync need: plain bridge verbs plus Rust) covers the rest.

**Several premises of the first version failed against the code.** The "wheel band" in the carousel never cancels anything: it is passive. The scroll lock's wheel test is a pure DOM test, but it is a stateful program, not a predicate. Escape in nested layers already cancels unconditionally, and the "topmost layer" decision is already made in Rust, asynchronously. The drawer drag and the virtual scroll bridge already stream to Rust asynchronously. Only OTP filtering, the scroll lock and the carousel's mouse drag make a real conditional cancel.

## 1. Root cause

### 1.1 The two commit points (W, platform semantics)

1. **Default actions are decided when dispatch ends.** `preventDefault()` only sets the event's *canceled flag*. The browser reads that flag after the last listener returns. A call after dispatch has finished does nothing. Inside a passive listener the call is ignored: the *in-passive-listener* flag is set around the callback, and the microtask checkpoint runs while it is still set. A wheel or touchmove listener that is not passive also makes the compositor wait for the main thread. This is the cost this repo measured in rows 149/159 (`scroll_lock.rs` module docs, V).
2. **Pixels are committed after style and layout in the "update the rendering" step.** Inside one rendering opportunity, the order is: run rAF callbacks → style and layout → ResizeObserver callbacks (which may loop back to layout) → paint. A microtask checkpoint follows each callback. A DOM write lands in the frame being drawn only if it happens before paint, which means inside an rAF or ResizeObserver callback, or in microtasks queued by one. A write that arrives in a later task misses that frame. If the pre-write state was painted, the user sees the flash.

**Invariant (the root):** *A decision can affect a commit only if it is computed on the page's main thread before that commit, from inputs present there at that time.* "Present" means event fields, the DOM, and anything Rust **published into the DOM beforehand**. Rust's own memory is not present, and neither is a message that is still in flight.

**The root, restated (board).** Irreversible decisions are taken at fixed points, each from state present there: the end of dispatch (default action), gesture start (`touch-action`, listener passiveness), input routing (focus), an activation window, paint, and the compositor frame. Section 1.4 lists what that does to the bridge verbs.

### 1.2 Where Dioxus 0.7.9 is synchronous, per renderer (V)

| path | web (wasm, same thread) | desktop / mobile (wry webview, `mobile = ["dep:dioxus-desktop"]`, `dioxus-0.7.9/Cargo.toml:122-125`) |

**What the table says (I).** The asynchronous hop is *the bridge*, not Dioxus's event path. On desktop and mobile it is a real cross-process hop. On web it is a microtask hop: for UA-dispatched events and rendering-step callbacks, that hop *happens* to finish before both commits. It is not a contract. It breaks for events dispatched from script, which get no checkpoint until `dispatchEvent` returns. It also breaks if dioxus-web re-enables its idle/rAF scheduling, or if any hop ever uses a macrotask. So: **on web the premise is mostly false in practice, on desktop it is true, and a design for all renderers must assume it is true.** Post-paint triggers are the other hole in "zero frames on web": IntersectionObserver callbacks (and so `onvisible`), popover `toggle` and dialog `close` are queued tasks that run after a paint, so a chain that must finish before paint starts from a pre-paint trigger (`beforetoggle`, a rAF or ResizeObserver callback).

### 1.4 The desktop timing contract (web-verified; desktop inferred)

Desktop's edit cadence is part of the root: it decides what a gate costs, and in which order two renders reach the page. Read from `dioxus-interpreter-js-0.7.9/src/ts/native.ts` and `dioxus-desktop-0.7.9/src/{webview,element}.rs` ([root-and-timing finding 1](./board-2026-10-26/root-and-timing.md)):

| step | desktop / mobile (wry webview) | web (wasm, same thread) |
|---|---|---|
| Dioxus event | synchronous XHR, blocks the webview (`native.ts:353-395, 568-593`) | synchronous inside the DOM event (`dom.rs:88-116`) |
| render to DOM | applied in the **next rAF**, at most one render per frame (`native.ts:444-458`); the webview acknowledges (`:495-499`) and Rust sends no new render before it (`webview.rs:537-590`) | the next microtask |
| tasks and effects | only after the acknowledgement: `wait_for_work` does not run while a render is in flight (`virtual_dom.rs:445-536`) | the next `wait_for_work`, after the flush |
| eval and queries (`evaluate_script`: bridge `call`/`get`, `MountedData` getters) | a webview task on arrival, **unordered with pending edits** (`element.rs:30-80`) | the eval body runs synchronously at the call |
| `dioxus.send` | queued on the event loop (`webview.rs:308-317`, `app.rs:309-319`); a later Dioxus event is handled inline (`protocol.rs:62-63`), so a streamed `pointermove` can be processed after the `pointerup` that followed it | microtask |

What follows (I, from the V chain above):
1. **Two Rust renders never land in one frame on desktop.** Render k+1 is sent only after render k's rAF callback has acknowledged, so row 421's "height, style flush, flag" order is automatic there. **Web is the renderer that needs the separation**: successive renders are successive microtasks inside one frame. So the first version's `commit()` verb (rAF plus forced style flush) is dropped: on desktop it is redundant, and on web it costs a whole frame when called from a rAF or ResizeObserver callback. Web keeps a "flush between renders" helper that is a forced style read, never a rAF.
2. **G costs at least one frame on desktop, typically two,** and one more for every sequential awaited read: render (mount plus pending) lands in frame N, the acknowledgement arrives, an effect runs the eval (`showPopover`), a measuring query, render (done), frame N+1 or N+2. "Show plus measure" is therefore **one bridge transaction that returns the rects**, so a gated open costs exactly one round trip and one frame.
3. **An eval issued from an event handler runs before the edits of the render that handler caused** (task before the rAF on desktop; the body runs synchronously and the render follows in a microtask on web). An eval issued from an effect runs after its render on both. Lane rule: a bridge op that depends on a render's DOM is issued from an effect or `onmounted`, never from the handler that caused the render.
4. **The root has more commit points than two.** Gesture arbitration at pointerdown/touchstart (`touch-action` and listener passiveness are read when the gesture starts; pointer capture applies at the next pointer event and throws `NotFoundError` for a released touch pointer), input routing (a key goes to whatever has focus at dispatch), activation windows (`DataTransfer`, `clipboardData`, transient-activation APIs), the compositor (threaded scroll updates pixels without the main thread, so only A tracks scroll frame-exactly), and post-paint deliveries (IntersectionObserver callbacks and so `onvisible`, popover `toggle` and dialog `close` are queued tasks, not rendering-step callbacks). Hence **commit-sensitive effects are never async `call` verbs**: `setPointerCapture`, `releasePointerCapture`, a `focus` meant for the next keystroke, `preventDefault`, `DataTransfer` and clipboard writes, activation-gated APIs exist only as effects of a named behaviour or as rsx handlers. A G chain starts from a pre-paint trigger (`beforetoggle`, not `toggle`).
5. **The platform half is unproven.** Android sends the event in a base64 header (16 KB per header, `native.ts:575-587`); edits are rAF-bound, so a hidden or throttled webview stalls every render; synchronous XHR to a custom scheme on WKWebView and WebKitGTK was not confirmed by any source found. V for the code path, I for the platform.
6. **A hot vdom listener costs a blocking round trip per event.** Every Dioxus listener on desktop is one synchronous XHR, `onresize` included (a `CustomEvent` per ResizeObserver entry, `core.ts:54-72`), so one frame with 50 resized rows (`virtual_list.rs:486`, `table_rows.rs:289`, `virtual_grid.rs:1526` attach `onresize` per row) is 50 blocking round trips inside the rendering step. A vdom listener is for an event that needs Rust's synchronous `prevent_default`, or that fires at human rate; frame-rate streams go through the bridge (section 5.2).

## 2. Constructions, from the root

The invariant leaves these ways to satisfy it. They are applied in the order of section 5.1, and each block gets the first that works:

| | how it satisfies "decide at the commit, from data present" | logic lives in |
|---|---|---|
| **delete** | The block runs on no supported renderer (a `not(web)` arm compiled only for Blitz, or a script a shipped CSS rule already makes a no-op). | nowhere |
| **rsx** | The target is inside a Dioxus element and Dioxus has the event: the handler is synchronous on web and on desktop/mobile, and `prevent_default()` reaches the native event. | Rust |
| **A** platform-declarative | The browser owns the decision inside its own pipeline. A keeps a Rust invariant or a Rust verification step behind it. | the browser (no code) |
| **R** no real sync need | The block was never on a commit path (it reads and reports, runs a command, or drives a passive effect that may answer late). | Rust plus plain bridge verbs |
| **G** paint-safe gate | Removes the deadline: CSS keeps the unsettled state invisible, so a late answer paints nothing wrong. | Rust |
| **B** a closed registry of named, scoped behaviours | The decision needs a window, document or capture target, an event Dioxus lacks, or a stream: one named behaviour decides locally from published config. | Rust owns config and lifetime; one tested TypeScript module owns the decision |
| **C** run Rust in the page | C1: the Dioxus sync event path. C2: a Rust kernel compiled to page-side wasm. C3: worklets. | Rust |

There is no "residue" row: what stays page-side is the registry (section 4), reported as a number.

- By default the box "will 'shift' to stay within its original containing block": **cross-axis shift**.
- `position-try-order: most-height` sorts the options by available block size: **side by room**.
- The spec text read does not mention the visual viewport. Fixed positioning works against the layout viewport, so an iOS keyboard is not avoided (I).

**What A cannot cover (V/W):**
1. The visual-viewport (keyboard) exclusion of row 210.
2. Publishing the placed side and the anchor offsets for arrows and transform-origin (`@position-try` accepts only inset, margin, sizing, alignment and position properties, not custom properties; anchored container queries are Chrome-only).
3. Engines without anchor positioning.
4. Gestures and height animation within a Baseline policy (`interpolate-size` is Chrome-only). Scroll anchoring *is* covered: `overflow-anchor` is Baseline newly available since 2026-09-14.

**Support policy A needs (proposal).**
- **Web:** "Baseline newly available across Chrome, Firefox and Safari. Older engines must stay *correct* through a feature-detected fallback, but need not be frame-perfect."
- **Desktop and mobile:** WebView2 and Android WebView are evergreen Chromium. WKWebView follows the OS WebKit, so Safari ≥26 is needed for anchor positioning on macOS and iOS (I). **WebKitGTK is unverified:** the 2.50.0 release notes (W) do not mention anchor positioning, so the fallback must stay until a probe on Linux desktop shows support.

**What the A-only run must cover on top of the conformance sweeps** ([ux-a11y-perf F9](./board-2026-10-26/ux-a11y-perf.md)): a 320 x 256 CSS-px viewport at 400% zoom (`max-height: 100%` of a `position-area` region beside the anchor can be about 100 px, where the JavaScript path clamps to the whole visual viewport), an RTL subtree (a physical `span-right` opens rightward in RTL; use the logical `span-inline-end` and drive direction from the same `use_direction` signal the carousel reads), and a keyboard-reduced `visualViewport` with an open combobox (the layout viewport does not shrink, so the list can sit under the keyboard until Rust republishes). A is verified on Chromium only: Firefox and WebKit runs of a named subset are part of [row 442](../backlog/442-desktop-cadence-harness-and-desktop-pass.md).

### 2.2 (B) A closed registry of named, scoped behaviours, and the three-way placement rule

**Why not a predicate language behind one delegated interpreter.** The first version of this document put every in-listener decision behind one capture-phase listener reading `data-dx-rule*` attributes, with four rule families. Four board members broke that form independently ([block-mapping F2, F6-F8](./board-2026-10-26/block-mapping.md), [simpler-alternative 3-4](./board-2026-10-26/simpler-alternative.md), [root-and-timing 3](./board-2026-10-26/root-and-timing.md), [ux-a11y-perf F5](./board-2026-10-26/ux-a11y-perf.md)):
- `closest('[data-dx-rule]')` finds only rules on the target's ancestor chain, which are exactly the events a Dioxus element handler already decides synchronously with full Rust state, on every renderer including Blitz. The sites that need page-side code (document Escape, F6, "outside the menu", window scroll lock, window Cmd+B, document `dragover`) have no such ancestor.
- At document capture nothing has run yet, so a `defaultPrevented` predicate (V22, L23 read it today because they run last) is always false, and a `stopPropagation` there cuts off every element listener and the Dioxus root. Dioxus delegates in the bubble phase (`core.ts:109-130`).
- A page-lifetime non-passive `wheel`/`touchmove` listener brings back rows 149/159 and fails `playwright/oracle/tier2-html/listener-inventory.spec.ts` (the multiset of listeners on window/document/html/body must equal the baseline taken before the first open).
- The families were unions of today's blocks: one user each for `can-scroll`, the regex filter and the metrics publisher, three different programs under "reveal/settle", four output modes under "pan". The interpreter would be about as long as the blocks it absorbed, plus a language, a serialisation format and a parity gate. Call the JavaScript that stays what it is: named modules.

**The placement rule.** Decided per behaviour, and enforced by the gates of section 5.3:

| the target and the event | placement | examples |
|---|---|---|
| **Inside a Dioxus element, an event Dioxus supports, no listener option needed** | an **rsx handler**, Rust logic, no JavaScript. | **A window, document or "outside" target; an event Dioxus lacks (`beforeinput`, `close`, `beforematch`); or the capture phase** | one **named, typed behaviour** from a closed registry (below). Each declares target, phase and passivity. Installation is owned by the Rust scope that needs it and is ref-counted, so a blocking listener exists only while something needs it. | `hotkey` (L6, O1, V22), `scrollLock` (L11, L10), `otpFilter` (S11), `dropAnywhere` (L25), `pan`, `settle`, `scrollStep` |

**How a behaviour is built.**
- **A pure `decide(config, snapshot, event) -> effects` plus a thin DOM adapter** that builds the snapshot and applies the effects. Conformance vectors are `{config, snapshot, event, expected_effects}` triples run by `bun test` against `decide()`; `cargo test` reads the same file against the generated types and, where a behaviour has a Rust twin (C5's classifier), against it. Without the split the vectors would test serde field names and nothing about decisions. `bun` may be absent: the gate then prints "bun tests: skipped (no bun)", never a pass.
- **The Rust enum and the TypeScript registry stay one to one by generation, not by parsing.** `cargo test` writes and compares the committed `behaviours.gen.ts` (kind union, verb enums, field names, vector schema version); a Rust `fn sample(b: &Behaviour)` with no wildcard arm names a vector for every variant (clippy `wildcard_enum_match_arm` denied on it); `bun test` asserts `Object.keys(HANDLERS)` equals the generated kinds. No `String`-typed field of `Behaviour` may be code.
- **Phase, target and passivity are declared**, never inferred: `capture-at-el`, `bubble-at-doc` or `window`. `defaultPrevented` is legal only in a bubble-phase behaviour. The `stop` effect is legal only in `capture-at-el` (desktop never forwards `stopPropagation`, and a window-capture stop would starve Rust's own handlers on web). Non-passive `wheel`/`touchmove`/`touchstart` exist only while a behaviour whose effect set contains `prevent` is installed, and go with the last one. The listener-inventory baseline is unchanged.
- **Every behaviour has a fail-open path and an epoch.** A behaviour that prevents an event and then relies on Rust to act carries an acknowledgement: `send` returns an id, Rust calls `ack(id)`, and an ack outstanding for about one second makes the behaviour stop preventing until the next ack (WCAG 2.1.2: a wedged Rust runtime must not trap the keyboard; a spec at the stuck-channel setting asserts Escape on an open dialog still closes it natively). Every answer from Rust carries the epoch of the install, and a stale one is dropped.
- **Lifetime is the owner's.** The registry holds rules in a `WeakMap` or on the element, never in a strong `Map<id, rule>`; a leak spec mounts and unmounts a host 200 times and asserts the registry is empty.
- **Public API.** The hooks and behaviour types are public in `dioxus-primitives`: preview components (V22, V17) and installed components use them. `check-installed-paths` and `cargoDependencies` expectations cover them, and an installed component's Rust files contain no sink (section 5.3).

**What a behaviour is not.** A stateful heuristic over a stream (C5's trackpad classifier, W8's mode machine) is R, not a behaviour: both are passive or paint-safe, so they can answer late. A new behaviour is a backlog row, a named variant, a vector, a spec tag and a budget row; a new verb (data, one table line) is not.

### 2.3 (G) Paint-safe gate: turn "same frame" into "bounded latency", hardened

Same-frame is *sufficient* but not *necessary*. What is necessary is that **no frame paints a wrong state**. If the unsettled state is invisible or pinned, Rust can measure and write whenever the answer arrives. The construction after the board ([root-and-timing 2](./board-2026-10-26/root-and-timing.md), [block-mapping F5](./board-2026-10-26/block-mapping.md), [ux-a11y-perf F2, F7](./board-2026-10-26/ux-a11y-perf.md)):

1. **The gate is the absence of a Rust answer, derived from `open`.** `:popover-open:not([data-dx-placed]), dialog[open]:not([data-dx-placed])` is pending. Every open path is gated by default (native `popovertarget`, light-dismiss restore, script opens), because pending needs no write. The bridge removes `data-dx-placed` **synchronously in `beforetoggle`** (`newState` open), so a fast reopen can never reuse a stale "placed". `toggle` is a queued task and runs after a paint, so it cannot start a gate.
2. **The pending style never leaves an animation running or paused.** The theme's enter animation is `forwards` and runs `opacity 0 -> 1` (`dx-components-theme.css:1775-1818`), and an animation declaration outranks a normal one in the cascade, so a one-line `opacity: 0` gate only hides while the animation is paused at t = 0, where it also keeps the 0% keyframe's `scale` (so S1 would read a transformed rect). Pending therefore means: `opacity: 0; pointer-events: none` with `animation: none` semantics, that is, no keyframe applies. The literal CSS is settled in lane 3.PL by the first-frame spec (below). `animation-play-state: paused` is rejected (it also pauses the fail-open).
3. **Fail open in CSS, no JavaScript timer.** The enter animation's `animation-delay` carries the gate's timeout (`--dx-gate-timeout`) and its fill is `forwards` only, never `backwards`: nothing applies during the delay, the pending `opacity: 0` holds and the geometry is untransformed (what S1's measurement needs), and after the timeout the enter animation itself plays. When Rust answers earlier, the gate rule stops matching and the delay drops to 0. The reduced-motion rule shortens durations only and must not touch the delay. The timeout for a placement-critical gate is at most about 100 ms (lane 3.PL fixes the number by measurement); the harness's stuck-channel setting must show the panel visible by then.
4. **A generation token.** `data-dx-placed` is written only with the generation of the open that asked, and Rust drops an answer for an older one (the same race class as `__dxDialogGen` in `lib.rs` and the "no cleanup of data-placed-side" comment in `anchor_fallback.rs`). Spec: open, close, open within one task, at the delay settings N = 0 and N = 2, and unmount before the answer.
5. **Two tiers, by what a wrong paint costs.**
   - **Placement-critical: gated.** Only where Rust owns the position: engines without anchor positioning (the fallback), and the iOS keyboard clamp (row 210). `opacity: 0` until placed.
   - **Decoration: never gated.** The placed side, arrow offset, `transform-origin` and available height open with the neutral defaults and update when Rust answers, after the tooltip's `:not([data-placed-side])[data-side]` precedent. The enter animation is origin-independent for its first frames (opacity first), so a late origin never shows as a wrong-corner pop. Without the split every popup open would pay two to four frames on desktop (I), on the engines where A already did the work.
6. **Gate only what is pending, never a visible panel.** Re-placement on resize or keyboard paints a frame late, a stated degradation. Where A places the panel, only the Rust-dependent part is gated.
7. **Show plus measure is one transaction that returns the rects** (section 1.4), read through bridge `get` rather than `MountedData`, so a getter that never completes (Dioxus #5734, reported on Ubuntu desktop) is not on the critical path.
8. **Pending states are opacity-only.** A pending selector may declare `opacity`, `pointer-events` and the delay, and nothing that leaves the accessibility tree or blocks focus: not `visibility`, `display`, `hidden`, `inert` or `content-visibility`. Focus must enter an `opacity: 0` panel (`modality.rs:108-165` has no visibility test), a toast's `role="alert"` insertion must still be announced (`toast.rs:1517-1535`), and VoiceOver reading a panel from its frame is on the manual checklist. A click in the panel's future area during the pending window falls through to the page (and light-dismisses a `popover=auto`): negligible at 0-2 frames, real during a 100 ms fail-open.

**Latency.** On web, for a pre-paint trigger (UA events, timers, rAF and ResizeObserver callbacks): zero extra frames, all microtasks. Post-paint triggers (`onvisible`, `toggle`, `close`) already cost a frame. On desktop (web-verified; desktop inferred): at least one frame, typically two, and one per sequential awaited read (section 1.4).

**Not for continuous loops.** A lagging write during scroll or drag *is* a wrong paint. G is for open-time, insert-time and swap-time work only. Continuous tracking goes to A. B and R run on the main thread and are a frame or more behind the compositor, so they are never "frame-exact" against scroll.

**Proof.** A first-frame spec asserts the panel is `opacity: 0` with no keyframe applied while pending and that no frame paints `placed` with stale geometry; `g-latency` measures frames from input to first visible panel (at most 1 at N = 0, at most 3 at N = 2); the stuck-channel run shows the fail-open.

### 2.4 (C) Running Rust in the page

- **C1, Dioxus's own sync event path (V).** It works on web and desktop/mobile, as section 1.2 shows. **It is the first rung of the placement rule**: use it wherever the listener can be a vdom element listener for a `dioxus-html` event that needs no listener option (this is already the house style: 133 `prevent_default()` calls in `primitives/src`). As a *trampoline* for window/document/capture cases, where the bridge re-dispatches a cancelable synthetic event to a vdom "port" element and reads `dispatchEvent()`'s return value, it is **rejected**:
  1. The synthetic event must be a type Dioxus converts (keydown, or a `CustomEvent` `resize` with a fake `detail`), which is an abuse.
  2. Other capture listeners see it, so the modality writer would mark keyboard modality.
  3. Desktop pays one blocking XHR per event, which is unacceptable for wheel or touchmove at 60-120 Hz.
  4. `stopPropagation` reaches the DOM on no renderer.
  5. Desktop is not in CI.

  Dioxus 0.8.0-alpha.1 adds `onbeforeinput` (audit section 3, W). With it, S11's cancel half becomes a plain rsx handler once fields and sync cancel are verified (I).
- **C2, a Rust kernel compiled to page-side wasm (I).** Every target webview runs wasm (Baseline high). **Against it:** Chrome refuses synchronous `new WebAssembly.Module` for buffers over 4 KB on the main thread (W, web.dev "Loading WebAssembly modules efficiently"), so loading is async; it needs a second build artefact plus a reproducibility gate; every input still needs JavaScript glue. **Verdict:** not now, and **no longer C5's exit**: if Rust loses the C5 measurement, C5 becomes an allowlisted TypeScript module (section 4).
- **C3, worklets and workers.** AnimationWorklet and the Layout API have not shipped. A paint worklet is Chromium-only and cannot cancel events. Workers have no DOM. Rejected.
- **C4, "the bridge is microtask-synchronous on web" (V components, I end to end).** True for UA-dispatched events and rendering-step callbacks. **Not a construction:** it fails on desktop/mobile and for script-dispatched events, and would break if dioxus-web re-enabled its idle/rAF scheduling (the TODO at `lib.rs:250-262`). Its one use is to explain why G costs nothing extra on web, and why a Chromium-only CI cannot reveal desktop latency bugs (section 5.6).

## 5. The proposal

### 5.1 Layers (apply in this order per block)

0. **Delete what is dead.** Eval and JS-listener calls inside any `#[cfg(not(feature = "web"))]` item: every supported build compiles that arm only for Blitz, where `document::eval` is `NoOpDocument.eval` (`dev-docs/reference/platform-rationale.md`, Caveat 2; `templates/starter/Cargo.toml.liquid:17-20` and `preview/Cargo.toml:38-41` switch `web` on for web, desktop, mobile and server). The scan of those arms finds 16 sites (`dialog.rs:478` escape :499, outside-dismiss :500, focus-trap eval :507; `alert_dialog.rs:235` escape :244, scroll lock :251, focus-trap eval :254; `popover.rs:488` scroll lock :512, escape :517, outside :518, focus-trap eval :522; `popover.rs:813` escape :831, outside :832; `dropdown_menu.rs:892` :935; `menubar.rs:974` :988; `context_menu.rs:895` outside :963 and `CONTEXT_MENU_SCROLL_BLOCK_JS` :978), plus `ts/focus-trap.ts` and its generated `js/focus-trap.js` and manifest line, and L23. If the Blitz floor should behave, it uses element handlers there (`onkeydown` Escape on the panel works on Blitz; eval never will). A gate rule closes the class: no `document::eval` or `JsListeners` inside a `not(web)` item.
1. **An rsx handler**, where the target is inside a Dioxus element, Dioxus has the event and no listener option is needed (the first row of the placement rule, section 2.2).
2. **A where the platform decides, within the policy** (section 2.1): anchor positioning for T8/T11, `overflow-anchor` for W8, `scroll-padding` for covers (W3/W7), scroll-driven fade depth (S14, already in place), `linear()` springs (C4). A always has a Rust invariant or verification behind it.
3. **R where the "sync" label is false.** The block only reads and reports, runs a command, or drives a passive effect that may answer late: W1, C3, C5, L21, L30, W8's mode machine, and the async (b) rows. Logic in Rust over plain bridge verbs; frame-rate streams only through the bridge.
4. **G for one-shot layout work**, gated by the absence of a Rust answer: T8's fallback and the keyboard clamp, T11's fallback, S1, O3, V19.
5. **A named behaviour** (section 2.2), only when none of the above applies: `hotkey`, `scrollLock`, `otpFilter`, `dropAnywhere`, `pan`, `settle`, `scrollStep`.

**What this subsumes (I):**
- All 22 (d) blocks and all 3,894 (d) lines leave per-component scripts; the 13 class-(1) `preventDefault` sites become rsx handlers (L1, L2), registry behaviours (L6, O1, V22, L10, L11, L25, S11, C4, V17) or deletions (L4, L23).
- The geometry copies (the fixed probe pasted into `select/components/list.rs:102` and `scroll_clamp.rs:58`) become one Rust helper.
- The `__dxWhenIdle` / `__dxCancelSnapRestore` cross-eval expandos, and the L1 expandos.
- Most `listener-ok:` / `blocking-ok:` markers, because listeners live only in registry modules and are derived (section 5.2).

**What it does not subsume:** class (c); the desktop latency of G and R (bounded, unmeasured: web-verified; desktop inferred); the quality of Safari 27's new scroll anchoring for W8 (its Rust invariant is the exit); the feel of C4's spring if `linear()` is not close enough; C5's lag, which carries its measured TypeScript fallback.

### 5.2 The bridge surface is closed

Lane 3.0 builds the verbs; these rules close them ([gates-and-proof 2](./board-2026-10-26/gates-and-proof.md), [root-and-timing 5, 6](./board-2026-10-26/root-and-timing.md), [simpler-alternative 5](./board-2026-10-26/simpler-alternative.md)):

- **No `el[method](...args)`.** `call`, `get`, `set` and `listen` take **closed Rust enums** (`Call::ShowPopover`, `Call::Focus { prevent_scroll }`, `Get::Rect`, ...) mapped through **closed TypeScript tables** (`const CALLS = { showPopover: (el) => el.showPopover(), ... }`), dispatched with an own-property check, with a **receiver kind per row** (an element method cannot be called on `window`). Otherwise `call(window, "setTimeout", ["code"])` is an eval. `set` accepts only custom properties that start with `--dx-`. Parity between the Rust enums and the tables is the generated golden file of section 2.2, not a text parse.
- **`passive` derives from the behaviour.** `listen`/`subscribe` streams fields, so it cannot cancel: it is always passive for `wheel`, `touchstart`, `touchmove` and `scroll`, and the TypeScript ignores a request for otherwise. A listener is non-passive only while an installed behaviour's effect set contains `prevent`.
- **Event volume derives too.** `pointermove`, `mousemove`, `wheel`, `scroll`, `touchmove`, `resize`, `drag` and `dragover` have no raw mode: a frame-coalescing mode, or a flush per event task for C5, which needs every event with its own timestamp (batched, not coalesced: its notch and decay rules compare consecutive events). `sample(el, fields, until)` is armed only while a gesture or condition holds; C5's `pointermove` must not live for the carousel's whole mount (`wheel.rs:578`).
- **Hot events stay off the vdom.** A vdom `on*` handler in `primitives/src` is for an event that needs Rust's synchronous `prevent_default`, or that fires at human rate. `scroll`, `resize` on many elements, `pointermove`, `wheel`, `touchmove`, `mousemove` and drag events go through bridge `listen`/`observe`/`sample`, async and batched. A reducer option (`emit` only when a named derived key changes) keeps a stream from posting a message per event. This applies to W1, W8, O3, and to lane 2C's S2/S3. `scripts/check-hot-events.sh` (a grep with a reasoned allowlist; a Rust-side sibling of `check-blocking-scroll-listeners.sh`) enforces it.
- **Ordering.** `transaction(ops[])` runs several operations in one JavaScript turn and returns results ("show plus measure" returns the rects; T5, T7, L16). `commit()` is **dropped** (section 1.4); the web-only flush between renders is a forced style read. An op that depends on a render's DOM is issued from an effect or `onmounted`.
- **Commit-sensitive effects are not verbs.** `setPointerCapture`, `releasePointerCapture`, a `focus` for the next keystroke, `preventDefault`, `DataTransfer` and clipboard writes, activation-gated APIs: effects of a named behaviour or rsx handlers.
- **Reduced motion.** The behaviours read `matchMedia('(prefers-reduced-motion: reduce)')` synchronously at execution time for every animated effect (`settle` smooth, `scrollStep`, spring); `use_media_query` defaults to "reduce" until its first answer; the G timeout is a CSS delay the reduced-motion rule does not touch.
- **One transport seam.** Hooks never call `document::eval`. `bridge/transport.rs` owns the eval call (the only one), the delay hook of the measurement kit, a Blitz "unsupported" answer and a future web-sys backend behind the same seam (Dioxus PR #5194, which also removes the strict-CSP `unsafe-eval` requirement on web). The bridge loads through `asset!` plus `document::Script` with a bounded ready handshake (#5919) and tears down over the existing channel (#4064).
- **Whether the verbs collapse** to two generic entry points (`subscribe` and `run(ops[])`) is lane 3.0's call; the closure rules apply either way. The typed Rust hooks keep the leptos-use / dioxus-sdk names (`use_window_listener`, `use_media_query`, `use_resize`), without a dioxus-sdk dependency.

### 5.3 Enforcement closes sinks, not spellings

A JavaScript-bearing string can run only through a short, enumerable list of sinks. The list is the gate; token bans are defence in depth ([gates-and-proof 1-6](./board-2026-10-26/gates-and-proof.md)).

1. **One eval site.** The identifier `eval` in the Rust code view (comments removed, string contents blanked), including `use ...::eval` aliases, `.eval(` and the glob `document::*`, is allowed only in `bridge/transport.rs`, with an exact site count, and its argument must be a declared constant plus `serde_json` output (the constants' sha256 is recorded in the baseline, so a change is a visible diff). Clippy's `disallowed_methods` (`clippy.toml`, resolved by def path, so aliasing, re-exports, trait-method syntax and `concat!` cannot dodge it) lists `dioxus_document::eval`, `Document::eval`, `Script`, `js_sys::eval`, `js_sys::Function::new_*`; `transport.rs` carries `#[expect(clippy::disallowed_methods, reason = ...)]`.
2. **The other sinks.** `document::Script`, `create_script`, `create_head_element` and `script {}` allowed only as `Script { src: <ASSET_CONST> }` for an allowlisted set of asset constants; `dangerous_inner_html` per file and reason, never on a `script`; rsx string attributes `"on..."`, `href: "javascript:..."`, `srcdoc`; `include_str!`/`asset!` of `.js/.mjs/.cjs/.ts/.tsx` and a **file inventory** of hand-written `.js`/`.ts` (`message_scroller.js` is the one hit, a baseline row that expires with W8); `web_sys`/`js_sys`/`wasm_bindgen`/`evaluate_script` and their `Cargo.toml` entries outside `transport.rs`; a new inline `<script` in any tracked `.html` outside `docs/`, counted per file by body hash.
3. **Universe by `git ls-files`** with an explicit exclusion list (`playwright/`, `scripts/`, `docs/`, the generated `primitives/src/js/`), never hand-listed roots (which is why `labs/`, `templates/` and `cli/` were never scanned). **No inline-marker escape:** an exception is a TSV line `path<TAB>sink<TAB>reason<TAB>row`, read by `scripts/lib/allow.py` (reason mandatory, stale entries fail), and an allowlist entry is the owner's decision, never a lane's.
4. **The JavaScript side** scans the canonical form (`bun build --minify-syntax --no-bundle` folds `"a"+"b"` and `x["y"]`), bans the identifiers `preventDefault`, `stopPropagation`, `requestAnimationFrame`, `setTimeout`, `queueMicrotask`, `ResizeObserver`, `MutationObserver`, `IntersectionObserver`, `addEventListener`, `eval`, `Function` and the forms `import(`, `new Function`, `.constructor`, `.on*=`, computed access on globals and computed calls, **outside file-level allowlist entries** with a per-file line budget (`path<TAB>max_lines<TAB>row`). A new `ts/` file needs a budget row and must be reachable from the registry index.
5. **Shrink-only means against the merge base.** `scripts/lib/ratchet.py` compares a baseline with `git show $(git merge-base HEAD origin/main):<baseline>` (it says "ratchet base unavailable, compared with the tree only" when there is no ref). A deliberate raise carries `# raised: row N: <reason>` and is printed in the run-gates summary as `RATCHET RAISES:`; a new allowlist line prints `ALLOWLIST ADDED`. This is visibility, not prevention. **The JS-volume ratchet lands before any port** (lane R): per tracked file the sink count, the lines of JavaScript inside Rust string literals, the lines of hand-written `.ts`/`.js`, the body bytes of each inline `<script>`, and the comment lines that call eval a "house pattern"; totals are computed, and a port that moves lines from a Rust string into a new `.ts` must still lower the sum.
6. **Registry and behaviour rules** (section 2.2): generation parity and the no-wildcard sample function; `defaultPrevented` only in bubble-phase behaviours; `stop` only in `capture-at-el`; blocking types only inside the lazy attach function; no `String` field of `Behaviour` is code; every G gate declares its tier and timeout, and a pending selector declares only `opacity`, `pointer-events` and the delay.
7. **No dead JavaScript:** no eval or JS listener inside a `#[cfg(not(feature = "web"))]` item (lane 3.DJ).
8. **Installed components contain no sink**: `check-installed-paths` extends to the S1/S2 list, because a user's app has no `transport.rs` allowlist (`form` and `code_block` carry eval today).
9. **One gate owner.** The sink gate, the budgets and the parity test belong to lane 3.0 (the bridge lane already owns the seam and the registry skeleton): the old plan gave `check-bridge-rules.sh` to 3.0 and to 3.B1. If 3.0 merged without them, a follow-up lane **3.0b** takes them. Behaviour lanes add vectors, spec tags and budget rows, and never edit a gate script. ### 5.5 Risks (in order)

1. **Desktop and mobile are unmeasured and not in CI** (no gtk/webkit2gtk here). G latency, R event volume and behaviour timing on WebView2/WKWebView/WebKitGTK are inferred. Mitigation: the desktop-cadence build and one recorded real pass per batch (5.6); the label "web-verified; desktop inferred" until then.
2. **Placement (3.PL)** is visible on every open and is where the plan is most expensive. The A arm is verified on Chromium only: Firefox and WebKit runs of a named subset, the Rust verification step, the first-frame spec and the tier split are the guards. Focus into an `opacity: 0` panel must keep `touch-open-focus` and `modal-initial-focus` green.
3. **Registry creep:** a new behaviour is a backlog row, a variant, a vector, a spec tag and a budget row. If a decision needs arithmetic or state over a stream, it goes to Rust (R, or G where a paint is at stake), not into a behaviour.
4. **Gesture feel (`pan`, C4's spring, C5):** per-component baselines before each port, hand checks on a trackpad and a touch device, and `touch-action` published by the behaviour.
5. **The scroll anchoring of W8** (Safari 27 is weeks old; Chromium's heuristics under token-rate streaming): the always-on Rust invariant is the answer; the five scenarios of 5.6 are the proof.
6. **`scrollLock` is stateful and had no spec for its distinguishing behaviour.** Characterisation specs come first, against today's JavaScript.
7. **WebKitGTK anchor-positioning support is unknown,** so the Rust placement arm cannot be dropped for Linux desktop until a probe confirms it.

### 5.6 Proof and measurement

**Honest about desktop.** All specs run on Chromium on the web, where the bridge is microtask-fast (section 1.2), and that **hides** every desktop-only latency bug. The first version's slow-channel harness (`window.__dxBridgeDelayFrames = N`) delays only bridge messages: it misses the rAF-bound edit cadence, an eval that runs before its own render's edits, the cross-channel reorder, the cost of a blocking XHR per Dioxus event, and every engine difference, and it delays messages inside a rAF, the best case. It stays as a **bridge-latency harness** (`?dx-bridge-delay=N`, a stuck setting `N = never`), never called a desktop model. The proof of sameness is built in three steps ([row 442](../backlog/442-desktop-cadence-harness-and-desktop-pass.md)):
1. **A desktop-cadence web build:** a harness-only workspace that patches `dioxus-web` with `[patch.crates-io]` (about 30 lines against 0.7.9: edits flushed in a rAF and awaited before the next render, the hook being the commented-out `wait_for_raf` at `dioxus-web-0.7.9/src/lib.rs:256-262`; the eval body run in a task; `MountedData` getters resolved after a task hop; `dioxus.send` delivered after a task hop with N plus jitter, in arrival order per channel and not across channels). Events stay synchronous. N and the jitter are chosen from one measured desktop distribution, not by fiat.
2. **Engines:** Playwright WebKit and Firefox for the named A/G subset (the configs exist; only the deploy wiring is missing).
3. **A recorded real pass per batch:** one WebKitGTK or real-desktop pass (`desktop-pass.md` holds the checklist) leaves `desktop-pass/<tree>.pass` (machine, OS, webview version, numbers), the way `release-suite/<tree>.pass` works for the suite. Until a stamp exists for the tree, rows and lane reports say "web-verified; desktop inferred"; a G or R mapping is never marked done on web evidence alone.

**Specs the board added** (budgeted in `playwright/durations.json`): `bridge-cost.spec.ts` (a relative cost spec on `playwright/frame-cost.ts` and the `check-timing-relative.sh` convention: per-event cost with 0, 10 and 50 installed behaviours against a no-op listener on the same page, valid on debug builds); `g-latency.spec.ts` (frames from input to the first visible panel); the registry-leak spec; the first-frame and open/close/open specs; the stuck-channel fail-open spec; `scroll-main-thread` test 3 extended to `window`; carousel (wheel, drag), message-scroller (stream) and toast (stack of 5) subjects in `main-thread.spec.ts`, whose 50 ms and 200 ms bounds are about 20-100 times too coarse to see a one-to-three-millisecond per-frame regression, hence a relation spec per port with `frameCostMeter` on the two arms of the A/B switch. Coverage is measured at runtime (`window.__dxBehaviourCoverage` in debug builds, a post-suite check that every variant ran), not by grepping for a tag. `tools/select.mjs` maps `ts/**`, `bridge/*.rs` and `behaviours.gen.ts` to a fixed core set (`main-thread`, `scroll-main-thread`, `listener-inventory`, `bridge-cost`, `g-latency`), and timing results from debug builds are not evidence.

**C5's proof.** The committed trackpad recordings are weak evidence: 11 bursts (9 real, 2 synthetic), one MacBook trackpad in Firefox 156, no per-event timestamps (events spaced uniformly), only the first 80 deltas logged. The expected outputs are captured from today's JavaScript, so a `cargo test` replay proves "Rust computes what JavaScript computed on that timeline". Hence a **property test** under jitter drawn from the spread of real 60 Hz and 120 Hz streams, per-frame batches and 0, 1 and 2 frames of delay (same release kind; release time within the injected delay plus one frame); the **old JavaScript engine is kept as a test oracle fixture** until the desktop measurement has run; the classifier takes `now` from its input (`std::time` and `web_time` are banned in `wheel_band.rs`); and the replay harness's phase is fixed (it samples the band in the same rAF that dispatches, so the Rust arm would be read one frame stale: the sampler runs in a rAF registered after the bridge's, or one frame later, parameterised by N).

## 6. Not verified / caveats

- Nothing was built or run. All latency figures (G on desktop, IPC cost, the cost of a blocking request per Dioxus event) are estimates, and every desktop claim is **web-verified; desktop inferred**.
- The "microtask-synchronous on web" chain (section 1.2) is verified piece by piece (eval channel resolve, `queueMicrotask` executor, run loop without idle/rAF), not end to end. The desktop timing contract (section 1.4) is read from the Dioxus sources, not observed on a webview.
- Chromium is the only engine installed here. A's Firefox, WebKit, iOS 26 and Safari 27 claims (anchor positioning, `position-area` shift, `overflow-anchor` quality) are unverified until the Firefox/WebKit runs of row 442 exist. Firefox once reported anchor support and failed (`anchor_fallback.rs:21-28`), so T8 keeps its outcome check.
- The spec quotes come from a WebFetch summary of the TR page (W). Engine behaviour for `position-area` shift and `max-height: 100%` should be confirmed in the 3.PL spec on Chromium, and by a probe on Firefox and Safari.
- The web-features `overscroll-behavior` entry now records the post-Chrome-144 semantics, so Safari is listed as unsupported even though it implements the older semantics (W, `lists.w3.org/Archives/Public/public-css-archive/2025Dec/0150.html`, MDN page).
- WebKitGTK: only the 2.50.0 release notes were read (W; the 2.52.0 notes are also silent). Anchor positioning is not mentioned, which neither confirms nor rules it out.
- Synchronous XHR to a custom scheme on WKWebView and WebKitGTK, and the Android header limit (16 KB per header), were not confirmed by any source found; the "synchronous on desktop" claim is V for the code path and I for the platform.
- The trampoline (C1 for window-level listeners) was evaluated on paper and rejected; it was not prototyped.
- The pending-state CSS of G (item 2 of section 2.3) states an invariant (no keyframe applies while pending, the panel visible by the timeout) and names the construction; the literal rules are settled by lane 3.PL's first-frame spec, and the gate's timeout number by measurement.
- `bun` may be absent where the gates run (`check-js-bundle.sh` already degrades to "rebuild check skipped"); the behaviour vectors say "skipped" in that case.
- Line counts are the audit's (string extents, comments included), and are meant for ranking only. The hour figures are inferred (section 5.4).
