## 2. Root cause of the blue ring (candidates a-d)
(b) CONFIRMED, and it is the visible ring. No dialog/alert/sheet/drawer/popover panel sheet resets `outline` (grep: dialog/style.css has none; sheet:125 and drawer:338 reset the close BUTTON only; the focus-outline-reset gate only checks rules that paint a ring box-shadow, so a ring-less focus TARGET is outside it). Forced test (ring.js): once the panel matches `:focus-visible`, computed `outline: auto 1px` paints on dialog, alert_dialog, sheet, drawer, modal popover. On iOS that UA ring is the system blue.
(a)/(c) is WHY it matches on iOS. iOS-like run: after a tap with nothing focused, `dialog.focus()` makes the panel `:focus-visible` = true on every panel (dialog, alert_dialog, sheet, popover, select list) -> outline auto. Plain Chromium touch (tap focuses the button first) -> fv=false -> no ring; that is why modal-initial-focus.spec passes ("panel paints no ring" asserts fv=false) and why this was never seen. Chromium's rule (script focus with no prior pointer-focus counts as keyboard-ish) reproduces; WebKit's heuristic is not verifiable here, but the owner's screenshot behaviour matches and the mechanism is the same shape. UNVERIFIED on WebKit: whether Safari matches exactly the same cases.
Other ring sources: DropdownMenu trigger (set_focus onclick), Menubar trigger, Checkbox, DatePicker nav-prev, Select list: all script focus of a non-editable -> `:focus-visible` -> the library's box-shadow ring (or UA outline on tabindex=-1 containers).
(c) HOLE in the row-206 gate (stale.js, iOS-like): iOS keeps focus on a text input when a button is tapped, so `opener` = that input, which ALWAYS matches `:focus-visible` -> `byKeyboard` true -> showModal focuses the first field -> keyboard rises. Measured: Sheet opened by tap with a stale focused input -> `INPUT#sheet-demo-name` focused. Related: after a keyboard open + Escape, focus returns to the trigger which stays `:focus-visible` (documented "known limit").
(d) explicit focus: only Command (autofocus + backstop). `grep autofocus` in preview/src: only command's prop passthrough. Primitive/Popover/DatePicker field focus is browser-native, not explicit.
Keyboard pop sources on touch today: Command (design), non-modal Popover with a field (unintended, browser default), the stale-opener hole, Combobox (inherent).

## 3. Proposed construction (one modality source, three consumers, one gate)
A. ONE modality writer. New `primitives/src/modality.rs` + JS const `MODALITY_JS`: a page-lifetime capture listener pair (pointerdown -> `touch|pen|mouse`; keydown of a non-modifier key -> `keyboard`) that writes `<html data-dx-modality="keyboard|mouse|touch">`. Single writer like theme-mode-writer (`apply_mode`): installed (idempotent, `listener-ok`) from `PREPAINT_JS` (theme.rs, copy in preview/index.html) AND prepended into every eval that needs it (the `TOP_LAYER_INK_STYLES_INJECT_JS` pattern) so apps without the prepaint still get it. Never read `:focus-visible` or `document.activeElement` for the decision. Fallback when no event was seen yet (default_open, programmatic open): `matchMedia('(any-pointer: coarse) and (hover: none)')` -> `touch`, else `mouse`. This fixes the stale-input hole and removes the iOS dependency. (Row 206 rejected a tracker installed by Dialog roots for install-order; installing at the document head and as an inject prefix removes that objection.)
B. ONE open-focus policy `dxOpenFocus(panel, firstControl)` in the same JS, used by: `use_dialog_open_driver` (replace the `:focus-visible` gate, lib.rs:545-570), `use_popover_sync` for non-modal popovers/date-picker (apply the same inert-children-around-showPopover trick, top_layer.rs), Command. Rule: keyboard -> browser default (first control / search input, unchanged). mouse -> panel (row 206) except Command keeps its input. touch/pen -> panel/container; an `autofocus` target wins ONLY if non-editable; an editable `autofocus` (Command input) is ignored on touch: drop the `autofocus` attribute and the `set_focus` backstop on touch (command.rs:446-518 reads modality), the user taps the search field to type (differs from shadcn: Radix FocusScope focuses it; Base UI's Dialog/Popover default `initialFocus` focuses the popup on touch and the first tabbable otherwise, from memory, not in /home/user/shadcn-ui/ui which has no Base UI sources and no touch handling in its registry).
C. ONE ring rule, by construction. (1) Theme: a programmatically focused container is not a control and never rings: `:where(dialog, [popover], [role=listbox], [role=menu], [tabindex="-1"])[class*="dx-"]:focus { outline: none }` (precedent: `main[tabindex="-1"]:focus`, main.css:140). (2) Ring tokens are modality-aware: `:root[data-dx-modality="mouse"], :root[data-dx-modality="touch"] { --dx-ring-focus: 0 0 #0000; --dx-ring-focus-inset: 0 0 #0000; --dx-ring: 0 0 #0000 }`. All 31 sheets that paint non-field rings already consume these tokens (check-css-state-recipes forbids hand-written rings), so triggers, checkboxes, nav-prev, etc. cannot ring after a pointer; `--dx-ring-field` is resolved at :root and keeps text fields ringing on tap (shadcn parity, and no input is focused at open any more). Keyboard modality restores everything (a Tab keydown precedes the focus). Forced-colors rule untouched.
Subsumes: Dialog/AlertDialog/Sheet/Drawer/modal Popover panel ring, Select list ring, stale-input keyboard, non-modal Popover field focus, Command keyboard, DropdownMenu/Menubar/Checkbox/DatePicker script-focus rings. Does NOT subsume: Combobox (the input IS the trigger; tapping it opening the keyboard is the user's action), a text field the user taps, forced-colors outline.
Files: primitives/src/{lib.rs (driver), top_layer.rs, command.rs, modality.rs (new), theme-facing preview/src/theme.rs + preview/index.html (PREPAINT_JS, byte-identical)}, preview/assets/dx-components-theme.css, preview/src/components/command/component.rs, scripts/check-open-focus.sh (new) + run-gates.sh + CLAUDE.md gate list.
Gate `check-open-focus.sh`: no `autofocus` attribute and no `.set_focus(true)`/`.focus(` in primitives/src or preview/src outside modality.rs / the policy helper, except lines with `focus-ok: <reason>` (roving focus in collection.rs, Escape restore); no `:focus-visible` read in an open path; stale entries fail. Pattern as the other check-*.sh.
Spec `playwright/touch-open-focus.spec.ts`: hasTouch+isMobile context with the iOS-like init script above (the emulation that reproduced the ring here), overlays DERIVED like modal-consumers.ts plus a popover-family list (popover, select, date_picker, dropdown, menubar, command). For each: tap open; assert activeElement not input/textarea/contenteditable (except combobox), outline-style none, box-shadow not the ring token; stale-focused-input case; reopen-after-close case; keyboard counterpart still lands on the first control / search input.
Must stay green: modal-initial-focus.spec.ts (EDIT the Command tap case: tap now expects the panel; mouse/keyboard cases unchanged), oracle-focus-restore.spec.ts, oracle/tier1-apg/keyboard-matrix.spec.ts, focus-ring.spec.ts (keyboard rings), popover/select/date-picker/menubar specs, theme-mode-writer gate untouched. Because this is a class (3+ instances: panel ring, trigger ring, script-focus), propose it as one change, not per-component patches.
