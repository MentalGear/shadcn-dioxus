# Functional core and a graph as the single source of truth: evaluation of 2026-11-19

The owner's question: "i wonder whether we can bring in fp's concept, small pure functions, and maybe a graph , so that
also the analysis tool later on does not create a new one but can the SSOT that exists. Evaluate value, practicality,
effort and optimal solve-by-construction alternatives." Read as three linked questions: Q1, should the code move to
small pure functions behind an imperative shell, and how far; Q2, should the repo hold one graph of its own structure as
a first-class artefact; Q3, could MentalGear/code-analyser read that graph instead of deriving its own from a
`rust-analyzer scip` index.

**The source suggests a sharper reading.** The repo already holds several declared graphs, each the truth for what it
declares (section 2), and none of them covers functions. The analyser's SCIP graph is the only derived one, and every
gate derives its own facts about the code by regex. So the useful question is not "which hand-held graph" but "which
one extraction of the code do the gates and the analyser share, and which declared tables does it check". Measured on
`b7b83ed` (the code graph on `0df1782`, whose `.rs` files are identical). Measurements are marked **measured**, with the
method; evaluations, estimates and the recommendation are **judgement**. Nothing was built with cargo.

## 3. Purity census (measured)

**Method.** A stdlib token scanner over non-test Rust (comments and strings blanked; files declared
`#[cfg(test)] mod x;`, `#[cfg(test)]` items and `#[test]` functions excluded). Every `fn` with a body is one record:
COMPONENT (`#[component]` or returns `Element`, row 533's definition); HOOK (named `use_*` or calls one); EFFECTFUL (its
signature or body names a reactive type such as `Signal`, `Memo`, `Callback`, `Event<..>`, `Eval`, a signal method
`.read()`, `.set()`, `.write()`, `.peek()`, `.call()`, a runtime call such as `spawn` or `consume_context`, `document::`,
`bridge::`, `web_sys`, time or randomness, IO or logging, a `RefCell`/`Cell`/`static` it touches, a method on or a
parameter of a struct whose fields hold reactive types, or a same-file callee that is EFFECTFUL); UNKNOWN (passes, but
calls a name defined elsewhere in the crate and never PURE there); PURE otherwise. A signal read counts as effectful: it
needs a runtime and subscribes the caller.

Pure and effectful code are mixed inside modules and files: 42 primitives files hold only PURE or UNKNOWN functions,
142 hold at least one HOOK, EFFECTFUL or COMPONENT.

**Error rate.** Two stratified samples of 30 non-component functions each (12 PURE, 12 EFFECTFUL, 4 HOOK, 2 UNKNOWN by

## 5. Recommendation (judgement)

**One construction: one parsed item table of the workspace, generated by the gates, which the gates and the analyser
read; core modules declared in it and held pure; branchy handler decisions pulled into pure outcome functions,
counted down.** In this order:

1. **The item table.** A `syn` binary in `scripts/attr-spread-collision-checker` writes, per function: path, module,
   lines, `cfg`, class (this census's rules on the AST, with names resolved through `use` and the module tree), callees,
   and per component its markup and handler lines. It is a generated artefact under the target directory, never
   committed and never hand-edited.
2. **Gates on it.** Row 533's long-function count reads it (the row needs "a script" because clippy cannot skip
   components); a purity gate holds the declared core modules (a TSV, shrink-only for exceptions) free of the effectful
   classes; the handler-line count (1,685) and the Playwright-only hook count become shrink-only ratchets through
   `scripts/lib/ratchet.py`. The text-pattern gates move onto the table as they next need work.
3. **The shell rule, applied by the ratchet.** A handler or effect that branches calls a pure function returning an
   outcome value (the `KeyOutcome` form) and applies it; the calendar's two key handlers are the first instance.
4. **The analyser reads the table** for an item and purity layer and for the declared-versus-derived check of
   `componentDependencies`, through `.codegraph/project.py` (`extend`, `KEY_INPUTS`); SCIP stays its source of
   type-resolved file edges. This step changes the owner's "one analysis source" decision and goes to the owner.

**First step, one lane, proves or kills the idea:** step 1 alone, for primitives and cli, plus the long-function count
of row 533 on it. **Proof:** it reproduces 17 and 5; it agrees with the 60 hand-read functions and the 17 long ones on at
least 57 of 60 and 17 of 17; it lists `sleep.rs`'s `gloo_timers` call (behind `cfg(target_family = "wasm")`, absent from
the SCIP graph); it runs in under 10 s warm on the workspace; UNKNOWN stays under 2 % of functions. **Kill:** if it
needs type inference to classify (UNKNOWN above 10 %), or runs above 60 s, stop at row 533's count and keep the analyser
on SCIP alone.

**Residue.** A signal read is classed effectful by policy, so a context method that only reads stays shell; names
resolve without types, so a call through a trait or a closure parameter can stay UNKNOWN; SCIP stays slow for the
file-level references; runtime type panics and the overlay memory growth (row 534) are untouched; the purity gate
guards modules, not single functions inside mixed files.

**Not done, and why.** A: no crate split of primitives now; the measured gap is logic never extracted, and the move
would collide with the port editing the same files; reconsider if the purity gate starts paying exceptions. E: no
hand-written graph. No replacement of SCIP: `syn` has no type resolution, so it cannot give the analyser its 9,545
references resolved to an owner through macro output. No code generated from transition tables beyond the kernel: the outcome enums carry the same
checkable form at lower cost.

## 6. Direct answers (judgement)

- **Q1.** Yes for decisions, no for a rewrite: half of the non-component code in primitives is already pure (54 % of
  functions, a lower bound), and the logic worth moving is the branchy decisions inside hooks and `rsx!` handlers (about
  a fifth of a sampled component body). Pull those into pure outcome functions under a shrink-only count, and declare the
  already-pure modules as core under a parsed gate, rather than split crates.
- **Q2.** Not a hand-held graph: the declared tables stay the truth for what they declare, and the structure of the code
  is a generated item table that gates rebuild every run. That table is the graph; it is never committed, so it cannot
  drift.
- **Q3.** Partly: the analyser can read the item table and the declared tables for the item, purity and declared-edge
  layers and keep SCIP for type-resolved file references, which a `syn` table cannot replace. Adding the table as a
  second source changes the owner's "rust-analyzer is the one analysis source" decision, so that step is the owner's.
