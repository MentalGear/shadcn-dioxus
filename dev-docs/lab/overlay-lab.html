    T1 · Combobox under the keyboard

    A text input anchors a 12-fruit list. CSS + outcome check is the shipped engine: anchor() + flip-block places it, and a port of anchor_fallback.rs measures the result and hands over to its JS placer (sticky) when the engine has no anchor positioning or the CSS result is off its promised spot, outside the visual viewport or on the input. JS-event is that same JS placer forced on, re-placing on scroll, resize, visualViewport events and a ResizeObserver (rAF-throttled). JS-sampled forces the JS placer and re-places every frame in which a signature of viewport, anchor and panel changes. Every frame records gap to the input (expected 4px), drift, who placed it, and px of the list below the visible viewport (the keyboard).

    Phone: pick an arm, put the input low on screen, tap it (keyboard opens, list opens). Type to filter, then scroll the page with a finger while the keyboard stays up. Repeat for each arm. Desktop: no keyboard: only drift is meaningful; scroll and resize the window with the list open.

    T8 · Keyboard drift: Combobox vs Popover, by visualViewport offset handling

    NOT RUN

    Settles why a Combobox list drifts on iOS while a Popover holding a field does not, when both are on the JS placer. The Combobox host (an in-page input that takes focus) and the Popover host (a button, with the field inside the fixed panel) sit side by side. Each host opens three panels at once, all anchored to the same element and measured every frame: (i) offsets handled as anchor_fallback.rs does today (rects minus vv.offset*, written back plus the offset), (ii) offsets never used (pure layout coordinates), (iii) offsets added to layout rects (double count). The solid panel is the one you interact with; the other two are dashed, click-through ghosts (hide them if they distract, they are still measured). Per frame: vv.offsetTop/height, anchor rect, panel rect, gap, whether the panel is pinned by top or bottom, how far the fixed box landed from what was written, and whether the anchor was still moving (lag) or at rest (a stuck panel), and whether a re-placement ever ran after the anchor's last move. Pin is an experiment knob: the engine pins a panel that sits above its anchor by its bottom edge and every other panel by its top; forcing one side on every panel shows whether the pin side, rather than the host, decides who drifts.

    Phone: pick the live variant and the Popover kind, move the row low, tap the Combobox input (keyboard), type, then scroll the page with a finger while the keyboard stays up. Do the same with the Popover (tap the button, then the field inside). Repeat per live variant if you like; all three are recorded every time. Desktop: no keyboard; only drift on scroll is meaningful.

    T3 · Context menu at the pointer (point anchor)

    NOT RUN

    A persistent 0x0 popover=manual anchor is moved to the pointer; the menu is a popover anchored to it with top/left:anchor() and flip-block/flip-inline fallbacks. If anchor positioning is missing, or no menu corner lands on the pointer inside the visual viewport, the JS placer puts a corner on the pointer, flips when it does not fit and clamps into the visual viewport. Records which corner lands on the pointer, who placed it, whether the menu stays inside the visual viewport, and whether the first-frame rect differs from the settled one (flash).

    T5 · Item-aligned Select as a generalised placement

    The generalised model is Placement { content_anchor: selected option, side: Over, align: center, gap: 0 }: the list opens over the trigger so the selected option's centre lands on the trigger's centre. 40 options in 5 groups with non-uniform row heights. Model, CSS first: JS measures the option's centre offset c inside the list and writes top: calc(anchor(center) - c px) with c as a literal number (no var(), no clamp()); the outcome check measures where the list landed and hands over to the JS placer (sticky) if the declaration is rejected, lands off target by more than 2 px, or leaves the visual viewport. Clamp is a separate step: when the unclamped top would leave the margins, JS writes a literal clamped top and the generic "keep the content anchor nearest its target" step scrolls the list. Model, JS only: the same formula forced onto the JS placer. Legacy: the shipped ITEM_ALIGNED_JS (no scroll tracking; the real Select closes on scroll). Every open also computes what the legacy script would produce from the same geometry and records the difference.

    All arms: move the trigger to the top, middle and bottom of the screen and select first / middle / last. Error is the selected option centre minus trigger centre; a list clamped at a screen edge cannot always align.

    T6 · Oversize panel

    NOT RUN

    A panel taller than either side of its anchor, placed by CSS: position-area + @position-try --t6b/--t6t with max-height: calc(100% - 16px), position-try-order: most-height, margin-block: 8px, overflow-y:auto. The JS placer takes over (and switches position-area off) when anchor positioning is missing or the CSS result is off its promised spot or outside the visual viewport. Records who placed it, the side chosen, height, room each side, inside-viewport and anchor overlap. Known caveat: most-height prefers the larger side even when the preferred (bottom) side fits; use "6 items" to expose it.

    Both: scroll the tall area, open each anchor with the panel at 30 and at 6 items. The buttons scroll an anchor to a spot on the screen.
