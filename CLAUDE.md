# Claude Code notes for this repository

- **Session start: read [`dev-docs/STATUS.md`](./dev-docs/STATUS.md) first** (current round, what is merged and deployed, what runs, the next round, owner inputs pending; the main loop keeps it current), then [`dev-docs/README.md`](./dev-docs/README.md) for the map of the docs. The backlog (`dev-docs/backlog.md` row N) is one file per row under `dev-docs/backlog/`; the index is generated: edit the row file, run `scripts/backlog-index.sh`, commit both.
- **Use subagents as much as is possible and safe — this is the default, not an optimization.** Any work that can be split into lanes with disjoint file sets should be, and the lanes should be dispatched in ONE batch so they run concurrently, never one after another. The main loop's job is to scope the lanes, review what comes back, and run the checks — not to do the work itself. Serialize only for a real reason, and name it: two lanes would edit the same files, one genuinely needs another's output, or a shared resource allows a single holder (the cargo lock, one dev server, one port). When a resource is the constraint, still parallelize the *editing* and serialize only the build or test step at the end. Before dispatching, tell each lane explicitly which files it owns and which it must not touch; before starting a batch, capture whatever baseline the work will later be verified against, since it cannot be recovered afterwards.
- Prefer **Sonnet subagents** for delegated work (implementation, research, validation runs); keep the main loop for review, delegation, and high-level decisions. Escalate a subagent to a stronger model only when a task has repeatedly failed or is unusually judgment-heavy.
- **Haiku subagents fit read-only inventories and audits, and small mechanical edits for a lane or task with a closed file list and a verifying gate; they do not fit debugging, primitives/shared code, new gates or specs, or long lanes that wait on shared resources.** A lane is the work stream (file set, worktree); the agent is the Haiku or Sonnet subagent that executes it -- never "a Haiku lane". Evidence and the running log are in [`dev-docs/agent-model-fit.md`](./dev-docs/agent-model-fit.md): add a row per delegated lane. Every lane agent gets [`dev-docs/lane-rules.md`](./dev-docs/lane-rules.md) (worktree, global build lock, mtime touch, merge the session branch and run the full gates before handback, web-request rules) plus its own prompt; session tooling: `scripts/lane-ssg.sh`, `scripts/gate-at.sh`, `scripts/lane-cargo.sh` (every lane cargo command), `scripts/lane-lock.sh --status` (the build lock is a FIFO ticket queue, gates first, `LANE_SLOTS` slots, `LANE_SLOTS=1` while Playwright runs). Gate procedure for lanes (owner 2026-10-18, lane-rules "Gate procedure"): lanes run only the fast gates (`run-gates.sh --skip` the cargo ones, no lock) plus their build and specs; the main loop runs the ONE full `run-gates.sh` per merge batch on the merged tree and pushes only a commit that passed it; the build lock is taken first-come, first-served with merge gates first; 4-5 lanes per batch, since one lock finishes about three full gate runs an hour.
- Never write feedback about the default "commit nag" stop hook in the chat. When the hook flags uncommitted or unpushed changes that belong to an in-flight agent or are otherwise intentionally staged for a later commit, just continue silently; only act on it when the changes are genuinely finished work that should be committed and pushed.
- Whenever a preview deploy is ready (Pages publish succeeded), always post the site link in the chat: https://mentalgear.github.io/shadcn-dioxus/ (with the main commit it was built from).
- **When the same problem shows up more than once, stop patching instances.** Two or more occurrences means there is a class, not a coincidence: deconstruct down to the root cause, then propose the best-fit fix *by construction* — one that makes the whole class unable to recur — rather than fixing the instances one at a time. Say plainly which instances the construction subsumes, and which (if any) it does not.
- Delegate debugging to Sonnet subagents too (reproduce, bisect, root-cause, propose the construction); the main loop reviews the evidence and decides. Do not run long hands-on debugging loops in the main conversation.
- Commits: use the `commit-guide` skill/guide when it is available in the session; when it is not loaded (e.g. this remote environment), say so once and follow the convention already used in this repo — Conventional Commits `type(scope): subject`, a body that explains the why and the evidence, the attribution trailers. Deviate only for a valid concern, and state it.
- Before trusting a `dx serve` dev-server result while verifying a UI fix, read [`dev-docs/dx-serve-hot-reload.md`](./dev-docs/dx-serve-hot-reload.md) — hot reload works, but a plain HTTP 200 does not prove your latest edit is actually being served, and two specific test-methodology mistakes (grepping minified CSS, `elementFromPoint` after a `pointer-events: none` fix) have already produced false "regression" alarms this session.

- **Pre-merge install check: `scripts/registry-install-smoke.sh`** (not in `run-gates.sh`: a cold `cargo check` of dioxus plus the primitives takes minutes and ~several GB). Run it whenever a `component.json` or a component's `component.rs`/`mod.rs`/`style.css` changes, or a component is added or renamed. It copies the working tree into a throwaway `file://` git registry (rewriting `REGISTRY_GIT_URL` in the copy, otherwise component dependencies and the `dioxus-primitives` crate would come from github.com's main, not this tree), renders `templates/starter` as the user's app with its `dioxus-primitives` line stripped (the install must add every crate itself), runs `dx components add <every member> --git file://…` (or `--cli <shadcn-dioxus binary>`; `--only a,b` for a subset, `--target wasm32-unknown-unknown` for the shipped target), then `cargo check` with `CARGO_INCREMENTAL=0` and a scratch absolute `CARGO_TARGET_DIR`, and deletes everything on exit (needs ~6 GB free; `--keep` to inspect). Green is `registry-install-smoke: OK -- N/N components installed`; `check-installed-paths.sh` is its fast static approximation, so a red there is cheaper to find first.

The *isolation* half earns its keep independently: a no-`--base-path` build made in the shared `target/` — which `scripts/deploy-preview.sh` also writes to WITH `--base-path shadcn-dioxus` (then `dioxus-components`, before the 2026-10-10 repo rename) — emitted 89 `/dioxus-components/` references (then the base path) per page and turned a green 57-test suite entirely red, while the same build into a fresh isolated tree emitted zero (`dev-docs/backlog.md` row 100). `rm -rf public` cannot fix that, because the tree is the problem, not its output. One construction, two failure classes. Build SSG only through `scripts/build-ssg.sh [debug|release] [--base-path P]` — it enforces the absolute isolated dir, wipes a stale `public/` (dx 0.7.9 `--ssg` leaves every route but `index.html` stale in a reused tree, `dev-docs/backlog.md` row 116) and refuses a base-path mismatch — and copy warm trees with `scripts/lane-target.sh create <name>` rather than building cold. Run lane `cargo` with **`CARGO_INCREMENTAL=0`**: incremental state regrew a target dir by ~10-13 GB per lane-hour and filled the disk (`dev-docs/backlog.md` row 168); `scripts/run-gates.sh` defaults it off and `lane-target.sh create` exports it with the target dir, so only a hand-exported `CARGO_TARGET_DIR` needs it said (opt back in with `LANE_CARGO_INCREMENTAL=1`, then `lane-target.sh prune`). Lanes that share or copy a target across worktrees must touch their sources before every cargo/dx run, because cargo judges workspace-crate freshness by mtime and a lane with older files silently builds another tree's code (`dev-docs/backlog.md` row 216).
- **Functional specs may run on debug SSG builds; timing specs only on release.** `oracle/tier2-html/main-thread.spec.ts` (and any latency threshold) gives false reds on debug — measured 64/153/141/113 ms long tasks on debug versus 0 on release (`dev-docs/backlog.md` row 116). The Playwright configs ignore main-thread on known-debug builds (`PW_BUILD_PROFILE`, read off the build when unset; `PW_FORCE_TIMING_SPECS=1` overrides), so a green run on debug says nothing about timing.
- A fresh remote container is bootstrapped by the SessionStart hook (`scripts/session-setup.sh`: dx 0.7.9, wasm32, dx tools, `npm ci`, `cargo fetch`; ~8 s, ~1 s when already set up). If `dx` is missing, run it by hand — never `cargo install dioxus-cli` (~21 min) or hand-seed the dx tools.
- Lanes/worktrees must symlink or `npm ci` (never `npm install`) the Playwright/stylelint `node_modules` — a fresh `npm install` in a worktree has already pulled a Playwright build expecting a Chromium revision this environment doesn't have installed, while `npm ci` from the committed lockfile (or a symlink to the main checkout's own `node_modules`) matches what's actually on disk (`dev-docs/backlog.md` row 72).
- A new component directory needs `preview/build.rs` **rewritten, not just touched**, before the `dx serve` watcher will regenerate the docs (`touch` is the cargo-side remedy for a stale `OUT_DIR`, `dev-docs/backlog.md` row 92, but it was not enough for the dx watcher; two lanes hit it on 2026-10-04). Change the file's bytes (e.g. edit a comment) and confirm the new component's docs appear before trusting what the dev server shows.
